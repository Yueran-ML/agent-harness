# Columbina 设计文档

日期：2026-10-09
状态：四个部分均已由作者确认。第 1 阶段已完成，第 3.4 节和第 4 节已按实现结果修订。

Columbina 是一个用 Python 从零实现的插件化 Agent harness。实现路线对齐 DeepSeek Harness，并吸收 Claude Code 和 Codex CLI 的做法。本文是实施计划的依据。

## 1. 定位与目标

### 1.1 定位

Columbina 是一个能安装、能日常使用、做得扎实的开源 harness。它是工程项目，不是研究项目。基准的用途是验收和回归，不是检验假说。

### 1.2 完成标准

1. 可安装。一条命令装好，Windows、Linux、macOS 三个平台的持续集成全绿。
2. 可用。用 DeepSeek Flash 能在终端里完成真实的编码任务。会话可恢复、可分叉。进程被杀后重启不丢状态。
3. 可扩展。新增一个工具插件不超过 30 行。有插件开发指南和三个示例插件。
4. 兼容。`AGENTS.md`、`SKILL.md`、MCP、Claude Code 格式的 `hooks.json` 直接可用。
5. 安全。有权限规则、审批和容器沙箱。
6. 可观测。每个会话能查 token、缓存命中率、耗时、各工具的调用次数与失败率。`columbina doctor` 自检环境。

### 1.3 明确不做

- 文件监听式热重载、每个能力拆成三个包、多代会话格式迁移链。
- 三家各自的原生沙箱（Seatbelt、Landlock、Windows 受限令牌）。隔离交给容器。
- 常驻子代理、代理团队、工作流引擎、模型写代码调工具的模式。
- 把会话日志上传给模型提供方，以及任何匿名标识请求头。
- LSP、浏览器或电脑操作、定时任务。

三家都没有、Columbina 需要的两项，做成可开关的插件：

- 回合预算。DeepSeek Harness 和 Codex 的循环都没有内置步数上限。无人值守运行必须有。
- 工具调用修复。两家都不修畸形 JSON，只把错误返回给模型。弱模型上修不修差别可能很大，所以做成开关。

Columbina 与 DeepSeek Harness 的另一处不同：后者没有内置终端界面，Columbina 先交付终端 CLI。

## 3. 架构总览

### 3.1 数据流

```
用户 / 基准任务
      │  followup / steer / inject / cancel
      ▼
   Agent ──────► ctx.llm（适配器：OpenAI Chat、Ollama 原生、脚本化、回放）
      │  ▲
      ▼  │ 工具结果
   ctx.tools 管线：前置拦截 → 守卫 → 审批 → 环绕执行 → 后置拦截 → 最终不变式
      │
      ▼
   Session（只追加的事件日志，唯一事实来源）
      │
      ├──► 消息投影：日志 → 下一次请求的消息列表
      ├──► 状态投影：inbox、待办、用量、重试计数
      ├──► 持久化：JSONL
      └──► 前端：CLI、无界面、之后的 JSON-RPC 服务与桌面应用
```

规则只有一条：模型能看到的，必须先写进日志。任何一次请求都能由日志重建。

### 3.2 技术栈

- Python 3.11 及以上，asyncio。
- 运行依赖：`httpx`、`pydantic` v2、`PyYAML`、`rich`、`prompt_toolkit`。第 6 阶段加官方 `mcp` SDK。
- 开发依赖：`pytest`、`pytest-asyncio`、`hypothesis`、`ruff`、`pyright`、`coverage`。
- 环境与构建用 `uv`，构建后端 `hatchling`，`src/` 布局。
- 数据目录 `~/.columbina/`，可用环境变量 `COLUMBINA_HOME` 改。

### 3.3 包结构

单一发行包，导入名 `columbina`。每个子包是一个或一组插件。

  llm/             词汇、分片装配、运行时、错误码、重试、token 估算

### 3.4 组合清单

应用由 YAML 清单组合出来，清单是插件条目的列表。条目有四个字段：`id`、`plugin`、`config`、`disabled`。`plugin` 是导入路径，写成 `package.module` 或 `package.module:attribute`。

| 清单 | 内容 | 用途 |
|---|---|---|
| `minimal` | 会话、模型、工具管线、循环、一个工具 | 最小可行脚手架，也是性能基准的对象 |
| `base` | 全部共用插件 | 其余清单的第一层 |
| `headless` | `base` 加一次性运行器 | 脚本和自动化 |
| `cli` | `base` 加终端界面 | 日常使用 |
| `bench` | `base` 加基准运行器，审批为"从不"，带回合预算 | 验收基准 |

补丁按 `id` 定位条目，可以整体替换它的 `config`、把它设为 `disabled`，或插入新条目。叠加顺序是清单、用户目录下的补丁、命令行 `--patch`。

第 3 阶段结束时有三份清单。`minimal` 里的工具只有只读的 `read`。`base` 建立在 `minimal` 之上，加上沙箱、审批、权限、其余五个工具、系统提示、指令文件、运行时上下文和重试。`headless` 建立在 `base` 之上，只加一次性运行器。`cli` 和 `bench` 随各自的阶段加入。清单里有条目加载不了时程序不启动。去掉权限插件或沙箱插件而留下命令工具，启动器会指出命令工具在等哪个服务，退出码为 2。

第 5 阶段给 `base` 加了五项：token 估算、溢出存盘、结果上限、压缩和待办。`cli` 多了 `/compact`、`/todos`、`/fork` 三条命令。两个前端的模型配置写明上下文窗口，默认是 DeepSeek Flash 的 1048576，这个数取自服务自己的报错。环境变量 `COLUMBINA_CONTEXT_WINDOW` 可以改它。`--model` 只换模型的名字，窗口不跟着变，所以换成窗口更小的模型时要一并给出它的窗口。

清单和补丁是同一种格式，叫做层。一层是一组操作：`insert` 插入条目，带 `id` 的操作修改已有条目。一层可以用 `extends` 写明它建立在哪一层之上。配置里的字符串可以用 `${NAME}` 和 `${NAME:-default}` 引用环境变量。

## 4. 内核

内核是 Cordis 五个概念的 Python 复刻，共 8 个模块、约 2000 行。它的精确语义以 `2026-10-09-columbina-stage1-kernel.md` 里的"内核语义速查"为准。

### 4.1 概念

1. 上下文是服务仓库。服务名是带类型的 `ServiceKey[T]`。`ctx.provide(KEY, service)` 注册服务，`ctx.use(KEY)` 取必需的服务，`ctx.get(KEY)` 取可选的服务。
2. 插件声明依赖。插件是带 `apply(ctx, config)` 的可调用对象或模块，可带 `name`、`inject`、`Config`。`inject` 里的服务没到齐，插件实例停在挂起状态。某个依赖消失时，依赖它的插件自动卸载，依赖回来后自动重新加载。插件只能 `use` 自己提供的服务，或者自己及外层插件声明过的服务。
3. 事件带类型。每个事件在声明时固定分发方式，只带一个载荷对象，用错方式调用直接报错。
4. 五种分发方式。`emit` 同步广播，忽略返回值。`parallel` 并发执行并等待全部结束。`serial` 按序等待，第一个非空返回值胜出。`bail` 是同步版的 `serial`。`waterfall` 是环绕式中间件，监听器收到载荷和 `next`。调用 `next(payload)` 继续，不调用即短路，多次调用即重试。
5. 注册可撤销。`ctx.effect(fn)` 执行 `fn` 并收集它返回的撤销函数。`ctx.on()`、`ctx.provide()`、`ctx.plugin()` 本身都是 effect。

### 4.2 插件实例

`ctx.plugin(plugin, config)` 返回一个 `Fiber`。状态为 `PENDING`、`LOADING`、`ACTIVE`、`FAILED`、`UNLOADING`、`DISPOSED`。`await fiber.dispose()` 逆序撤销全部 effect，递归卸载子插件，等清理真正结束后才返回。处于 `UNLOADING` 时拒绝新建 effect。每次状态变化都发出 `FIBER_STATE_CHANGED` 事件。

配置用 pydantic 模型校验，校验在创建 `Fiber` 时进行。校验失败时插件实例进入 `FAILED`，启动器打印错误并以非零码退出。

### 4.3 作用域

每个 Agent 有自己的作用域上下文 `agent.ctx`，由 `ctx.scope(key)` 创建。经它做的注册只对该 Agent 可见，随 Agent 销毁撤销。经带作用域的上下文分发事件时，只放行全局监听器和作用域匹配的监听器。子代理靠这个得到不同的工具集。

### 4.4 监听器异常

`emit` 和 `parallel` 的监听器抛异常时，分发器记录日志并继续，不影响其他监听器。`serial`、`bail`、`waterfall` 是决策链，异常向调用方传播。

### 4.5 取消与重入

- 等待方被取消不会打断加载、卸载或清理。异步的清理在内核自己的任务里进行。
- 提供方卸载前，先等依赖它的插件卸载完。服务被撤回期间名字保留，直到依赖方卸载完成。
- `apply` 和 disposer 不能等待一个正在等它们的 Fiber。这种情况下 `dispose()` 只发出请求，`settled()` 立即返回，应用级的 `ctx.settled()` 抛 `LifecycleError`。

模型运行时、工具管线和循环等待别人的代码时，都经 `columbina.cancellation.guard`。别人的代码指适配器的流、工具体和各拦截点的监听器。`guard` 靠当前任务被请求取消的次数分清四种情况。

- 当前任务确实被取消，取消原样向外传播。
- 被等待的代码自己抛出了取消，这算它出错。`guard` 把它换成普通异常 `CancelledFromInside`，异常文本写明等的是什么。
- 清理时的异常顶替了取消，`guard` 记下这个异常，再把取消重新抛出。
- 被等待的代码接住了取消，照常返回了结果。`guard` 丢掉这个结果，把取消抛出。真要吸收取消的代码会用 `uncancel` 把请求收回，`asyncio.timeout` 就是这样做的，这种代码不受影响。

任务运行期间收到的取消请求要到它下一次等待时才送达。`guard` 在取计数之前先让出一次，这样的请求在被等待的代码启动之前就送达。

### 4.6 与 Cordis 的差异

- 服务访问用带类型的键和 `use`、`get`，不用属性访问。
- 每个事件只带一个载荷对象。
- 不做文件监听式热重载。保留运行时卸载和重新挂载的能力，测试需要它。
- 卸载时严格逆序、逐个等待。Cordis 的顶层撤销函数是逆序启动、并发执行。
- 不做 `intercept` 配置叠加、mixin、Proxy 属性魔法、`!!js` 表达式。清单里只支持环境变量插值。

## 5. 会话日志

### 5.1 事件信封

```json
{"type": "tool/call", "seq": 42, "time": 1791234567890, "data": {...}}
```

`seq` 等于追加时的日志长度。可选字段 `ignorable`。模型可见的事件另带 `surface_op`，替换型的还带 `source_event_seqs`。

每种事件是一个 pydantic 数据类，类上写明事件名和是否 `ignorable`。事件类型要先在会话服务里注册，插件用 `sessions.declare(ctx, 类)` 注册自己的类型，注册随插件卸载撤销。

`append()` 在入口处依次做五件事。

1. 检查事件类型已注册。
2. 把数据写成 JSON 再读回。读回的副本与原数据不相等就拒绝。日志保存的是这份副本，调用方之后改动原对象不影响日志。
3. 校验消息面约束。
4. 写入存储。存储拒收时事件不进日志，也不通知任何人。
5. 按日志顺序同步通知观察者。观察者抛异常被隔离。观察者在通知里追加的事件排在当前事件之后通知。

事件的字段是冻结的。Python 拦不住对字段里列表和字典的修改，所以约定集合字段一律用元组，事件进日志后不再改动。

### 5.2 核心事件

| 事件 | 载荷要点 | 进入模型历史 |
|---|---|---|
| `turn/start`、`turn/end` | 回合号；`turn/end` 带 `reason`、可选的 `detail` 和可选的 `code` | 否 |
| `step/start`、`step/end` | 回合号、步号 | 否 |
| `system/message` | 渲染后的系统提示，消息面的第 0 个节点 | 是 |
| `user/message` | 人的输入、注入的上下文、压缩摘要，靠 `source` 区分 | 是 |
| `assistant/message` | 装配后的回复、用量、结束原因。结束原因为空表示回复被取消打断 | 是，空内容除外 |
| `assistant/attempt` | 失败的尝试，存已到达的内容、用量和失败原因 | 否 |
| `tool/call` | `call_id`、`name`、模型原样产出的参数字符串 | 否 |
| `tool/result` | 结果内容、可选 `error{code, reason}`、可选 `meta` | 是 |
| `request/header` | 调用配置和工具模式的完整快照，含提供方、模型、上下文窗口、采样参数 | 否 |
| `session/end-seed` | 继承或恢复的历史与本次生命周期的分界 | 否 |
| `request/aside` | 对话之外的一次模型请求，例如摘要：存用途、用量和可选的失败原因。它不带消息，只为了用量有处可记，读日志的程序可以略过 | 否 |

`turn/end.reason` 取值：`completed`、`aborted`、`blocked`、`error`、`max-tokens`、`interrupted`、`forked`。后两个只由崩溃修复和分叉合成。

`detail` 是给人看的一句话，`code` 是给程序看的代码，界面和基准按代码分类，不去匹配那句话。只有两种原因带代码。`blocked` 时代码说明是谁不让回合继续：回合预算的三个上限是 `STEP_BUDGET`、`TOKEN_BUDGET`、`TIME_BUDGET`，钩子拦下输入是 `HOOK`，没有监听者作出决定是 `NO_DECISION`。拒绝一步的回答 `Reject` 自己带着代码，别的插件拒绝时给它自己的。`error` 时，请求最终失败的回合带着那次失败的代码，程序自己出错是 `EXCEPTION`。旧日志里没有这个字段，读出来是空。

插件用自己的命名空间追加事件：`agent/inbox/spliced`、`approval/asked`、`approval/decided`、`sandbox/mode`、`approval/policy`、`compaction/start`、`compaction/summary`、`compaction/end`、`todo/write`、`llm/retry`、`hook/invoked`、`hook/result`、`subagent/started`、`subagent/ended`。

### 5.3 消息面

`surface_op` 只有两种：`"append"` 和 `{"op": "replace", "start_seq", "end_seq"}`。替换用一个新节点顶替一段现有节点，必须在 `source_event_seqs` 里列出全部被遮蔽的节点。

事件是否进消息面由它的数据类决定，`for_model()` 返回消息的事件才是节点。调用方写 `session.append(data, replaces=[...])` 做替换，被替换的节点必须在当前消息面上相邻，并按当前顺序列出。只有带消息的事件才能替换别的节点。

`session.messages` 是当前消息面上的消息，`session.surface` 是对应事件的 `seq`。两者随追加和替换增量维护，也可以按顺序重放全部事件重建，性质测试检查两种算法结果一致。压缩和工具结果裁剪都只做替换，原始事件永远留在日志里。

### 5.4 持久化

- 路径：`<COLUMBINA_HOME>/sessions/<规范化的工作目录>/<会话 id>/session.v1.jsonl`。
- 首行是头：`type: "session"`、`version`、`id`、`created_at`、`cwd`、可选 `parent_session`。之后一事件一行。
- 每条事件追加后写入并刷新缓冲。模型请求前、工具体执行前、回合结束时各做一次落盘屏障，即 `await session.flush()`。
- 新会话在写入第一条事件之前不落盘。
- 同一会话只允许一个写者，靠操作系统对会话目录里 `lock` 文件的锁保证。进程退出时锁自动释放。
- 写入或落盘失败一次后，这个文件不再接受写入。有洞的日志比中断的日志更糟。
- 读到不认识且未标 `ignorable` 的事件，拒绝加载。读到别的格式版本，拒绝加载。不认识但标了 `ignorable` 的事件原样保留，复制日志时原样写回。
- 行格式有误、`seq` 不连续、消息面对不上，都拒绝加载，错误信息给出文件和行号。
- 最后一行没有换行符，说明写到一半进程就死了。这一行不读，续写时把它截掉。

只有一个格式版本，不做迁移链。

### 5.5 恢复与分叉

恢复时如果日志停在回合中途，追加修复事件：给每个没有结果的工具调用补一条错误结果，再补 `step/end` 和 `turn/end{interrupted}`。

修复区分两种状态。有 `tool/call` 记录但没有结果，标 `TOOL_OUTCOME_UNKNOWN`。连调用记录都没有，标 `TOOL_NOT_STARTED`。结果文本告诉模型只有只读或幂等操作才可重试。

调用和结果按出现的次序逐个配对，不只看 `call_id`，因为模型可能在后面的回复里重用同一个 id。顶替别的事件的事件不参与配对。它只是把日志里已有的内容重说一遍，既不发起调用，也不回答调用。

分叉复制到指定 `seq` 为止的前缀，追加 `session/end-seed{inherited: true}`，再用同一个修复函数以 `forked` 为原因关闭未闭合的尾部。新会话的头里 `parent_session` 记着来源。Agent 服务有同名的 `fork`，在副本上创建 Agent，与 `create`、`resume` 并列。

分叉有两个入口。`/fork` 在 Agent 空闲时执行，它复制整个日志，对话转到副本上，原会话保持原样。Agent 空闲时日志停在两个回合之间，最后一个 `turn/end` 之后只有回合之间发生的事，例如用户要求的压缩，它们属于会话当前的状态。`columbina sessions fork ID` 把一个存着的会话复制到最后一个 `turn/end` 为止。被复制的会话可以正开在别的对话里，副本里没有需要关闭的回合。一个回合都没有结束的会话不复制。

### 5.6 状态投影

`Projection(name, initial, apply)` 是一个纯同步的折叠单元。`apply(state, event)` 返回新状态，不改传入的状态，不关心该事件时返回同一引用。`projection.of(session)` 给出该会话当前的状态。状态在被读取时才计算，每条事件对每个会话只折叠一次，恢复出来的会话从第一条事件折起。

会话包自带两个投影：`TURN` 给出回合号、步号和是否在回合中，`USAGE` 给出累计调用次数和 token 用量。inbox、待办、重试计数用同一种办法各自定义。

面向前端的投影注册表放到第 10 阶段，和第一个需要它的前端一起做。

## 6. 模型接入

### 6.1 词汇

- 消息角色：`system`、`user`、`assistant`、`tool`。
- 内容块：`text`、`reasoning`、`tool-call`。`reasoning` 块可带适配器私有的 `replay_state`，下次请求原样带回，只交还给产生它的适配器。
- 流式分片：`block-start`、`text-delta`、`reasoning-delta`、`tool-call-delta`、`block-end`、`usage`、`finish`。
- 结束原因：`stop`、`tool-calls`、`max-tokens`、`error`。结束分片带 `failure` 当且仅当原因是 `error`。
- 用量字段互不重叠：`input_tokens` 只含未命中缓存的输入，`cache_read_tokens`、`cache_write_tokens`、`output_tokens` 单列。

适配器只需实现 `stream(request)`，返回一个产出分片的异步迭代器。取消不用信号对象。读取方的任务被取消或提前离开时，运行时关闭这个迭代器，这次调用没有结束分片。共享的装配器把分片折回内容块。结束原因为 `max-tokens` 时丢弃全部工具调用，因为被截断的调用不安全。工具参数全程保持原始字符串。

### 6.2 失败与重试

所有失败归一成 `LlmFailure{message, code, status?, retry_after_ms?, request_id?}`。适配器可以抛 `LlmError`，也可以发错误结束分片，运行时对外统一成结束分片。无论适配器做了什么，一次调用的分片流都以恰好一个结束分片收尾，适配器的流在这个分片送达之前已经关闭。

读取方的取消不会被吞掉。关闭适配器的流时出错只记日志。取消恰好落在关闭过程中时，关闭被打断，`call.aclose()` 会再关一次。运行时不把关闭放到别的任务里做保护，因为跨任务关闭生成器会弄坏在生成器里持有任务级状态的适配器。清理不能被打断的适配器要自己做保护。

运行时还让结束分片与实际到达的内容一致。原因为 `tool-calls` 时回复里一定有工具调用，原因为 `stop` 时一定没有，不管提供方报的是哪一个。

错误码：`AUTH`、`QUOTA`、`RATE_LIMIT`、`CONTEXT_WINDOW_EXCEEDED`、`INVALID_REQUEST`、`SERVER`、`HTTP_<状态码>`、`TRANSPORT`、`TIMEOUT`、`STREAM_CLOSED`、`MALFORMED_RESPONSE`、`EMPTY_RESPONSE`、`INTERNAL`。

- 结束原因不是 `error` 但没有内容块，算 `EMPTY_RESPONSE`。
- 适配器抛出 `LlmError` 以外的异常，算 `INTERNAL`。流没有结束分片就断了，算 `STREAM_CLOSED`。分片顺序违反协议，算 `MALFORMED_RESPONSE`。
- 流空闲看门狗默认 300 秒，只在等待下一个分片时计时。
- 适配器内部不重试。重试是独立插件，挂在"请求出错"拦截点上。
- 默认策略：最多 5 次，只重试 `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`、`STREAM_CLOSED`，指数退避 0.5 到 10 秒，抖动 10%，提供方给出的等待时间在上限内优先。
- 每次重试先写 `llm/retry` 事件再等待，等待可取消。重试在同一个打开的步内重跑，不重复追加用户消息。

### 6.3 适配器

| 适配器 | 线格式 | 用途 |
|---|---|---|
| `openai_chat` | Chat Completions，SSE | DeepSeek、Ollama 的 `/v1`、vLLM 及其他兼容服务 |
| `ollama` | Ollama 原生 `/api/chat` | 本地模型。能在每次请求里显式写出 `num_ctx`、`seed`、`repeat_penalty` 等采样参数 |
| `scripted` | 无 | 测试。构造时给一个脚本数组，每次调用消费下一项，记录收到的每个请求 |
| `replay` | 无 | 测试。从录制的会话日志里取出每次调用的回复，重新拆成分片当脚本。顶替别的事件的消息不是模型的回复，不回放 |

`anthropic_messages` 放在第 6 阶段之后。DeepSeek Harness 的官方适配器走这个格式，Columbina 先做 Chat 格式是因为本地模型都用它。

`openai_chat` 另有五条规则。

- 密钥在发请求时从环境变量读取，不进配置。适配器给出的每一个失败都走同一个出口，先从来自外部的文本里剔除密钥，再截短。这样的文本有两处：失败信息截到 500 个字符，请求 id 截到 200 个字符。先剔除后截短，截断处就不会留下密钥的前半段。被捕获的原始异常不随失败向外传，连 `__context__` 也不保留，因为它的文本没有清理过。
- 有一件事不归适配器管。HTTP 库有自己的日志器 `httpx`，它在 INFO 级别照原样写出每个响应的状态行。Columbina 不启用这个日志器。
- 工具调用的名字和 id 可能一次给全，可能分片到达，也可能每个事件都重复一遍。适配器等两者齐全才开始这个内容块。同一调用来了一个不带名字和 id 的片段，或者回复结束，才算齐全。别的调用的片段和文本可能夹在中间，它们说明不了名字已经完整。在这之前到达的参数先存着。
- 一次回复带多个 `choices` 时，只读 `index` 为 0 的那个。
- `Retry-After` 既认秒数，也认 HTTP 日期。

DeepSeek 的注意事项，来自官方文档：

- 思考模式默认开启。开启时 `temperature` 等采样参数不生效。
- 带工具调用时，之前每一轮的 `reasoning_content` 必须原样回传，否则返回 400。适配器把它存进 `replay_state`。
- 缓存命中的输入单价是未命中的五十分之一。上下文必须只追加，不改前缀。

### 6.4 采样参数显式化

每次请求明确写出温度、种子、重复惩罚、上下文长度，并记进 `request/header`。不依赖任何服务端默认值。

### 6.5 token 估算

`ctx.token_meter` 回放日志得出估算，不调模型。文本按字符的类别计价，比率是对 DeepSeek 的真实接口实测之后选出来的。

| 字符 | 每字符 token |
|---|---|
| ASCII 的空白 | 0.15 |
| ASCII 的数字 | 0.50 |
| ASCII 的字母 | 0.24 |
| 连续 24 个以上字母数字里的字母，例如哈希和 base64 | 0.85 |
| 其余的 ASCII 字符，也就是符号 | 0.70 |
| 东亚的宽字符 | 0.62 |
| 其他字符 | 0.50，没有实测 |

每条消息另加 3 个 token，声明了工具时另加 210 个，工具声明的 JSON 按同一张表计价。这张表在 28 段实测文本上的平均偏差是 7.1%，最大 19.2%。最初的设想是 ASCII 四个字符一个 token、中日韩文字每字一个，它在实测文本上的偏差从少估 41% 到多估 60%。

剩下的偏差用会话自己的实测比例来补。最近一次成功的请求报告了用量，并且它的提供方和模型与当前相同时，取报告的输入 token 数与当时估算值之比作为这个会话的比例，估算值乘上它。比例落在 0.5 到 2 之外时不采信。压缩顶替一段历史之后，这个算法不需要特殊处理。

## 7. Agent 与循环

### 7.1 Agent 接口

| 方法 | 语义 |
|---|---|
| `followup(content)` | 排一个新回合 |
| `steer(content)` | 运行中在最近的步边界被消费，空闲时开新回合 |
| `inject(content)` | 只附带上下文，等别的输入唤醒 |
| `cancel(cause, keep_inbox=False)` | 中止当前活动。`cause` 取 `user`、`parent`、`hook`、`budget`、`disposed`，写进 `turn/end` |
| `wake()` | 告诉 Agent 可能有输入在等。没有输入时什么也不做 |
| `when_idle()` | 等到空闲 |
| `close()` | 结束 Agent：停下当前活动，关闭会话 |
| `run_maintenance(task)` | 在真正空闲时跑非回合任务，手动压缩用它。第 5 阶段加入 |

`cancel` 默认丢弃排队的输入。`keep_inbox=True` 时输入保留，但 Agent 在下一次被唤醒之前不开新回合。新的输入和 `wake()` 都会唤醒它。

inbox 分 `next-turn` 和 `next-step` 两个队列。回合边界认领全部 `next-step` 加一条 `next-turn`，步之间只认领 `next-step`。每次 inbox 变更落成一条 `agent/inbox/spliced` 事件，排队的输入是日志投影出的状态。

正在被取消的回合不再从 inbox 取任何东西。这时还在等的输入，要么是特意保留的，要么是取消之后才给的，都留给后面的回合。认领和清空各分两步，每一步写出的事件都会通知监听器，监听器可能在这时取消 Agent，也可能给出新的输入。所以循环在认领的每一步之前都看一眼有没有取消请求，清空时只丢弃开始清空时就在等的输入。

`agents.create(ctx, spec, session_id=...)` 新建，`agents.resume(ctx, spec, session_id)` 恢复。`spec` 给出工作目录、调用配置、系统提示和用哪一个循环。扩展插件只依赖 `columbina.agent`，不依赖 `columbina.agent_loop`，所以循环可以替换。

### 7.2 回合与步

步是一次模型请求加它触发的工具调用。回合是零个或多个步。

```
turn/start
  第一步之前：对账 system/message → 问上下文消息的来源，追加 user/message
  每一步之前：认领输入，追加 user/message
          → waterfall agent/pre-step ⇒ Reject | Enter
     Reject，或者没有明确的决定 ⇒ turn/end{blocked}
  step/start
     waterfall agent/request（可替换调用配置）
     调用配置或工具模式有变化时写 request/header
     由日志派生请求
     读流，逐分片发 agent/assistant-stream
     成功 ⇒ assistant/message；失败 ⇒ assistant/attempt
            → waterfall agent/request-error ⇒ Retry 才重试，否则保留原错误
     有工具调用 ⇒ 按 8.3 节调度执行
  step/end
  本步给出结束原因且 next-step 队列为空 ⇒ serial agent/turn-stopping
turn/end{reason}
```

没有输入在等时，唤醒 Agent 不开回合。回合的第一步之前，循环核对一次系统提示，再向上下文消息的来源各问一次，写下的消息排在这一回合的输入之前（见第 10 节）。这两件事出错时，输入照常认领，回合以 `error` 结束，不向模型发请求。

`turn/*`、`step/*`、`*/message`、`assistant/attempt`、`tool/*` 是持久事件。`agent/*` 是进程内的实时接口。需要可回放数据的前端消费会话事件，`agent/*` 只管队列、状态、拦截和流式帧。

### 7.3 停止条件

| 条件 | 结果 |
|---|---|
| 回复里没有工具调用 | `completed` |
| 回复被输出上限截断 | 循环让模型接着写，一个回合里至多三次。次数用完，或者这项功能被关掉，回合以 `max-tokens` 结束 |
| 工具结果带 `concludes_turn` | 提交完本批结果后以 `completed` 结束，`next-step` 队列里的输入留给下一回合 |
| `agent/pre-step` 返回 `reject` | `blocked`，不开步 |
| 取消 | `aborted` |
| 异常 | `error` |

回复被输出上限截断时，已经到达的文字留在日志里，回复里的工具调用一个也不执行。循环随后写一条来源为 `context/cut-off` 的消息再走一步。消息告诉模型上一次回复被截断，要它从断处接着写、不要重复；截断时正在写工具调用的，指出哪几个调用没有写完、没有执行，要它重新发起并且小到一次回复装得下。截断发生在第一个字之前时没有可留的消息，这次请求记成一条 `assistant/attempt`，失败代码是 `CUT_OFF`，用量照记，然后同样接着写。用户恰好在这时说了话，就不写这条消息，模型接下来回答用户，也不占接着写的次数。次数是循环的配置 `continuations`，缺省 3，写 0 就不接。接着写的每一步照常受回合预算管。回合以什么原因结束只看最后一次回复：截断之后接上并正常收尾的回合是 `completed`，每条助手消息自己的 `finish_reason` 仍然记着它是怎么结束的。被截断又接上的几条助手消息是同一段话，要取“模型最后说的话”的地方用 `columbina.agent.replies` 把它们接起来，无界面运行的输出和子代理交回的结果都是这样取的。

除了工具要求结束这一种情况，回合关闭还要求 `next-step` 队列为空。`agent/turn-stopping` 的监听器想阻止结束时，调用 `agent.steer()` 塞一条消息，循环就再跑一步。

`agent/pre-step` 和 `agent/request-error` 的监听器必须给出明确的决定。前者只有 `Enter` 才进入下一步，后者只有 `Retry` 才重试，别的返回值一律按拒绝处理。

循环本体不设步数上限。上限由回合预算插件 `columbina.guard.budget` 提供，它在 `base` 清单里。它监听 `agent/pre-step`，检查三项：这个回合已经走了几步，这个回合的请求一共用了多少 token（用量的四项相加），从这个回合第一步被问到起过了多少秒。对应的配置是 `max_steps`、`max_tokens`、`max_seconds`，缺省都是不限。哪一项到限就返回 `reject`，`turn/end` 写成 `blocked`，`detail` 里写明是哪一项和具体的数，`code` 是这一项的代码。回合不会在一步的中间被切断：正在进行的那一步连同它的调用会做完，不再开始的是下一步。

Agent 的规格可以自带 `max_steps`，它优先于清单里的数。子代理就是这样拿到比主对话少的步数的，见 11.3。

`Stop` 钩子挂在 `agent/turn-stopping` 上。钩子给出理由时，钩子桥调用 `agent.steer()`，模型再走一步。一个回合里这样续至多三次，见 11.2。

### 7.4 取消与失败

- 流中途被取消时，已到达的内容落成结束原因为空的 `assistant/message`。一点内容都没到达时，这条消息不进消息面。
- 未派发的工具调用各补一对 `tool/call` 和"未执行"的结果，错误码 `ABORTED_BEFORE_DISPATCH`。被打断的回复里的工具调用也这样处理。
- 正在执行的工具被停下，结果的错误码是 `TOOL_CANCELLED`，文本提醒模型调用可能已经部分生效。
- 步失败时，给每个没有结果的工具调用补错误结果。调用与结果在任何情况下都成对。
- 四个拦截点的监听器抛异常时，回合以 `error` 结束。监听器自己抛出的取消同样算它出错，回合不会被记成 `aborted`。

## 8. 工具

### 8.1 定义

```python
Tool(
    name="read",
    description="...",
    parameters=ReadArgs,            # pydantic 模型，生成给模型看的 JSON Schema
    execute=read_file,              # async (args, run) -> 值
    render=render_read,             # (args, value) -> 模型读到的文本，缺省用 str(value)
    timeout_seconds=None,           # 缺省用工具服务的时限
    concurrency_safe=True,          # 布尔值，或 (args) -> bool
    effect="read",                  # 这次调用对外界做什么：none、read、write、run
    target=where_it_reads,          # (args, run) -> 规则可以匹配的文本
)
```

`effect` 和 `target` 是工具对自己的说明，权限规则靠它们判断。规则的写法是 `工具名(匹配串)`，匹配串对的是什么，只有工具自己知道。文件工具的 `target` 返回定位之后的路径，命令工具返回命令本身。

发给模型的模式只含名字、描述和参数的 JSON Schema，宿主字段不泄漏。pydantic 自动加的 `title` 会被去掉，它对模型没用，却每次请求都占 token。

模型给的参数是一段 JSON 文本。`tool.parse()` 把它读成参数模型。不是合法 JSON、不是对象、字段对不上，都抛 `ToolFailure(code="INVALID_ARGS")`，消息逐字段说明问题，模型据此改正。工具体自己也抛 `ToolFailure` 来报告调用没成功。

`run` 句柄提供 `call_id`、`cwd`、`session`、`target` 和 `conclude_turn()`。前四项在调用开始时定下，监听器改不了。`target` 是检查时所说的对象。文件工具运行时再定位一次路径，落点不同就不读也不写。取消靠任务取消，不传信号对象。`defer_context`、`agent`、`finalize_content` 在用到它们的阶段再加。

`tools.add(ctx, 工具)` 注册，注册是 effect。按 Agent 作用域过滤工具放到第 6 阶段，和子代理一起做。

### 8.2 执行管线

| 阶段 | 形态 | 能做什么 |
|---|---|---|
| 记录 `tool/call` | 循环在派发前追加 | 审计和界面先看到调用 |
| 查工具、读参数 | `tools.begin()` | 工具不存在或参数对不上时，调用当场得到错误结果 |
| `tools/pre-execute` | waterfall | 返回 `Allow` 或 `Deny` |
| 守卫 | 登记的函数 | 只能返回拒绝，没有"允许"这个返回值。按登记顺序问到第一个拒绝为止。权限规则和审批在这里 |
| `tools/execute` | 环绕式 waterfall | 度量、包装。时限由管线自带，包住整条环绕链 |
| 工具体 | `execute` | 产出值，再由 `render` 变成模型读到的文本 |
| `tools/post-execute` | waterfall | `Accept`（可替换文本）或 `Block`（变成错误结果） |
| `tools/result` | emit | 每次调用恰好通知一次最终结果 |
| 记录 `tool/result` | 循环按模型顺序追加 | |

一次调用在管线里是一个 `PendingCall`，分两步走。`authorize()` 问前置检查，`execute()` 跑工具并检查结果。循环按模型顺序对每个调用先走第一步，可并行的调用再让第二步重叠。没走第一步就走第二步时，管线自己先补上检查。

守卫不在 waterfall 上。waterfall 的监听器可以不调用 `next` 就返回放行，外层的监听器因此能跳过内层，而守卫谁也跳不过。检查紧挨着执行：循环先等到这次调用可以运行，再问检查，问完立刻执行。执行的必须是检查过的那一次调用。管线在调用开始时留下参数的取值，问守卫之前和执行之前各比对一次。`tools/execute` 的监听器换了别的调用往下传，或者就地改了参数，工具都不运行，结果是 `CHECK_FAILED`。调用开始之后工具被卸载的，这次调用不再执行。

三条不变式：

- 参数一旦记录就不能被改写。历史、审计、界面和执行必须一致。
- 一切失败都变成结构化的错误结果返回给模型，回合不中断。检查本身出错时调用不执行，结果检查出错时结果不放行。检查没有给出明确答复时也一样，只有 `Allow` 和 `Accept` 算放行。
- 只有调用方自己被取消才会向外抛。这时工具被停下，调用没有结果，由循环补一条。工具清理时出错不会吞掉取消，工具内部自己触发的取消算工具出错。读参数和判断能否并行时不等待任何东西，这两处出现的取消同样算工具出错。

错误码：`UNKNOWN_TOOL`、`INVALID_ARGS`、`TOOL_ERROR`、`TOOL_TIMEOUT`、`DENIED`、`CHECK_FAILED`、`RESULT_BLOCKED`、`ABORTED_BEFORE_DISPATCH`、`TOOL_CANCELLED`。权限守卫另有 `APPROVAL_REJECTED`、`APPROVAL_UNAVAILABLE`、`APPROVAL_CANCELLED`、`RULES_UNREADABLE`、`RULES_NOT_READ`。工具可以用 `ToolFailure` 带上自己的错误码，文件系统接缝的错误码见第 9.2 节。

### 8.3 并行

工具用 `is_concurrency_safe(args)` 自报，默认独占。独占调用是顺序屏障。连续的可并行调用进一个滚动池，上限 `max_parallel_tool_calls`，默认 10。前置策略按模型顺序串行，只有工具体重叠执行。结果按模型顺序提交。

### 8.4 内置工具

| 工具 | 说明 | 上限 |
|---|---|---|
| `read` | 带行号读文本，支持 `offset` 和 `limit` | 2000 行，每行 2000 字符，50 KiB，只看文件的前 64 MiB。一页的 token 数另受单个结果的上限约束，见第 8.5 节 |
| `write` | 整文件创建或覆盖，缺少的上级目录一并创建。内容按原样写入 | |
| `edit` | 精确字面替换。必须唯一匹配，否则报错并要求扩大上下文。`replace_all` 可选。文件原来的换行方式保持不变 | 16 MiB |
| `glob` | 文件名匹配，支持 `**`、`*`、`?` 和字符集，结果按修改时间从新到旧 | 100 条，扫描 20000 个条目 |
| `grep` | 内容搜索，纯 Python 实现，正则在另一个进程里匹配。ripgrep 后端以后作为优化加入 | 250 条，每行 200 个字符，每个文件 16 MiB，一次搜索 64 MiB、20 秒 |
| `powershell` / `bash` | 每次在全新进程里执行一条命令。Windows 上叫 `powershell`，用系统自带的 Windows PowerShell 5.1；其他平台叫 `bash` | 默认超时 120 秒，上限 600 秒，输出保留 64000 字节 |
| `todo_write` | 整体替换本会话的任务清单。条目有 `content` 和三态 `status` | |
| `skill` | 按名字加载一个技能的完整说明 | |
| `subagent` | 委派给全新上下文的子代理 | 深度 1 |
| `ask_user_question` | 向用户提问并等待回答，只在交互式前端可用 | |

`read` 的上限管的是它做的事，不只是它返回的东西。文件按 64 KiB 一块读入。要返回的行边读边解码，只留前 2000 个字符，其余的只计数，所以提示里的字符数与整行解码的结果一致。没被要求的行只计数，不解码。超出 64 MiB 的部分不看，提示写成"至少 N 行"。调用方被取消时，读文件的线程在下一块处停下。

写和改已有的文件之前必须先读过它。读后文件变了就拒绝并提示重读。这条规则在文件系统接缝替换文件的那一刻比对，不写在工具里，见第 9.2 节。读到的内容后来被压缩裁短或者被摘要取代的，也算没有读过：模型眼前已经没有那些内容，凭印象整体改写会丢东西，所以要重读。接缝按调用编号记下每个文件是哪一次调用给模型看的，压缩把被它拿走的调用告诉接缝，拒绝时的说法写明这个文件读过、只是读到的内容已经不在对话里。

`grep` 的遍历、权限判断和读文件都在主进程里做，文件内容经管道交给一个只做匹配的子进程。Python 的 `re` 在匹配时不放开 GIL，一条回溯很久的正则会让整个事件循环停住，时限和取消都生效不了。时限到了或调用被取消，就杀掉那个子进程。匹配程序的源码在模块加载时读入，运行的是加载时的内容。`glob` 和 `grep` 不跟随链接，跳过 `.git`，并在结果里说明有多少文件没看。

命令工具把一条命令交给平台的 shell。工具名就是 shell 的名字，模型据此决定写哪种语法。Windows 上命令行里只放一行固定的引导代码，命令本身经标准输入传入，这样不受命令行长度的限制，也不落临时文件。PowerShell 用 `%SystemRoot%` 下的完整路径启动。结果的最后一行写明退出码，或者写明命令在多少秒后被停下。一条命令启动的进程不比它活得久：命令正常结束、超时、调用方被取消，三种情况下它留下的进程都被停下。调用方在命令还在启动时被取消的，等它建出来、被结束掉、被事件循环看到退出，再把取消交回去，至多等几秒。Windows 上进程一创建就在一个作业对象里，POSIX 上在新的会话和进程组里。Windows 上有一类程序不在作业里：命令里的名字解析到应用执行别名时，比如从 Microsoft Store 装的 `python`，系统把启动出来的程序放在请求者的作业之外。停下命令时因此多做一步：先看一遍每个进程是谁创建的，从作业里的进程出发找出作业之外的后代，再把它们和作业一起结束。进程号会被重新分配，所以只认比创建者晚出现的进程，查不到创建时间的不动。这一步找不到创建者已经先结束的进程；本程序自己被强行结束时，作业里的进程由系统结束，作业之外的不会。命令工具依赖沙箱服务和权限服务，少了任何一个它就不加载。

可选插件：`apply_patch`（Codex 的补丁格式，带四级模糊定位）、`web_fetch`。

### 8.5 输出上限

| 层 | 机制 | 默认值 |
|---|---|---|
| 子进程流 | 内存里保留头尾各一半，丢弃中段并说明丢弃的字节数。输出超过这个数时，完整的输出边到边写进溢出文件，结果末尾写明它在哪里。溢出文件最多比 64 MiB 少 64 KiB，存下的文件因此总在 `read` 够得着的范围之内 | 64000 字节 |
| 结果级 | `tools/post-execute` 监听器。超预算的结果换成头尾预览，加全文的定位符和读取提示。保存失败时仍然截短，并如实说明全文没有保住。预算跟着模型走：会话最近一次请求的配置里写着窗口时，取固定值和窗口四分之一中较小的，没写时只用固定值。窗口的四分之一不到 256 token 时按 256 算，免得写错的窗口让预算小到装不下说明省略的那两行。声明自己分页的工具不受这一层限制，`read` 是这样，但它的一页按同一个数收短：超出时在整行处提前结束，页尾照常写明从哪里接着读。这个数由这一层作为服务提供，`read` 去问，问不到时一页只按行数和字节数算 | 12500 token，窗口的四分之一 |
| 压力期 | 只在压缩触发后，把超大的旧工具结果换成头 4096 加尾 1024 字符。换了之后不省 token 的结果不动。裁之前先把整份存到放过大结果的地方，省略行的下一行写明整份在哪、怎么读，存不了就只裁。本来就是两端加一行去向的结果不再存。模型还没读过的结果，也就是它最后一次回复引出的那几个，只在裁读过的还不够时才动：它们加起来超过窗口的四成时，其中大的让出地方。这一步按 token 算，不看字符数，因为中文一类的文本字符不多而 token 多，按字符数还算不上长的结果就能占掉小窗口的大半。先算出一个公共的上限，使它们合起来刚好不超过四成；小于上限的原样留下，没用完的份额归大的，超过上限的各裁到两端加起来等于上限。裁掉不到 512 个字符的不裁，被裁过的不再裁。这样够了就不写摘要，免得为了几个只需要首尾的结果丢掉此前的对话。窗口未知时这一步不做 | 阈值 8192 字符；窗口的四成，按 token |

子进程结果把正交的事实分开上报：`exit_code`、`timed_out`、`output`、`omitted_bytes` 各自成字段。被信号结束的程序，退出码是信号编号的负数。

## 9. 安全与权限

### 9.1 两个旋钮

| 旋钮 | 取值 | 存储 |
|---|---|---|
| 沙箱模式 | `read-only`、`workspace-write`、`danger-full-access` | 会话事件 `sandbox/mode`，回放即恢复 |
| 审批策略 | `ask`、`never` | 会话事件 `approval/policy` |

三个预设把两个旋钮打包：`read-only`（只读加询问）、`workspace-write`（工作区可写加询问，默认）、`full-access`（完全访问加从不）。预设由权限插件在会话的第一个回合开始时写进日志，日志里已经有的不重写。沙箱模式的状态在 `columbina.sandbox`，审批策略的状态在 `columbina.approval`，预设和规则在 `columbina.permissions`。

### 9.2 文件系统接缝与文件工具

文件工具不直接碰文件，都经过文件系统接缝 `ctx.fs`。一次访问先定位，再判断，通过后接缝发一张许可，文件只能经许可打开或替换。

- **定位。** 路径先解析符号链接和目录联接，再看它在不在工作目录之内。Windows 上会被读成别的文件的写法在定位时拒绝：指向另一台机器的路径、带冒号的名字、以点或空格结尾的名字、设备名。途中的链接逐个查看，指向另一台机器的不跟随。
- **判断。** 接缝自己的规则只有一条：读工作目录之内的文件可以。写任何地方、读工作目录之外，都要有一条登记的放宽说可以。除了放宽还有登记的限制。限制只能拒绝，接缝按登记顺序逐条问，问到第一条拒绝为止，放宽压不过限制。
- **沙箱模式是放宽。** `read-only` 不放宽任何东西。`workspace-write` 放宽工作目录之内的写，`.git` 和 `.columbina` 除外。`danger-full-access` 全部放宽。没有沙箱插件时什么也写不了，少装一个插件只会更严。
- **许可与读写绑在一起。** 文件打开之后按句柄取它的最终位置，与判断时的不是同一个位置就拒绝。替换经上级目录的句柄完成：POSIX 上用 `dir_fd`，Windows 上在操作期间持有不允许删除共享的目录句柄。新内容先写到旁边的临时文件再改名，读的人看到的要么是旧内容，要么是新内容。
- **先读后写。** 读的结果送到模型手里之后，接缝记下文件的指纹，即大小和修改时间。替换时比对两次，一次在准备新内容之前，一次在改名之前。已有的文件没给模型看过就拒绝，看过之后变了也拒绝并提示重读。新建文件不需要先读，用不覆盖的改名。记录按会话存在内存里，恢复会话后要重读。
- **工作目录不能中途换掉。** 接缝记住会话第一次访问文件时工作目录的落点，之后落点变了就拒绝一切访问。
- **容器里的路径名。** 命令在容器里运行时，工作目录在那里可能另有一个名字，Windows 上是 `/workspace`，模型会在命令的输出里读到它。提供者说出这个名字，接缝把以它开头的路径先换成工作目录里的相对路径，再走上面的定位和判断，规则一条不少。

错误码：`INVALID_PATH`、`OUTSIDE_WORKING_DIRECTORY`、`READ_ONLY`、`PROTECTED`、`NOT_WRITABLE`、`NOT_READ`、`CHANGED_SINCE_READ`、`MOVED`、`NOT_A_FILE`、`WORKING_DIRECTORY_MOVED`。

`workspace-write` 模式下文件工具不写系统临时目录。容器里的命令用容器自己的临时目录，它随容器一起消失。接缝把路径解析到文件上，硬链接分辨不出来。

### 9.3 Shell 命令

命令由沙箱的提供者执行。沙箱接缝 `ctx.sandbox` 把命令交给配置点名的提供者，提供者把命令运行到结束，并说明它把一个会话的命令约束到什么程度，取 `none`、`partial`、`full`。

| 提供者 | 强度 | 说明 |
|---|---|---|
| `none` | `none` | 命令原样在本机上运行，是缺省的提供者。第 3 阶段 |
| `docker` | `full`。容器有网络、工作目录里找到套接字、受保护的名字在磁盘上还有别的名字、工作目录不在本机磁盘上、容器答不出自己拿到的是哪个目录时是 `partial` | 一个会话一个容器，只挂载工作目录，默认断网。第 7 阶段 |

设计之初还列了 `bwrap`，没有做。选哪个提供者有三个办法：环境变量 `COLUMBINA_SANDBOX`，命令行的 `--sandbox`，或者改动文件里沙箱那一项的 `provider`。

**强度为 `none` 时**，shell 命令无法被约束。因此除了 `danger-full-access` 模式，shell 调用一律要审批或命中允许规则。审批策略为 `never` 时直接拒绝。无界面模式没有人可问，需要审批的命令在那里不执行。

**强度为 `full` 时**，命令不再询问，因为它能做的事不会超出沙箱模式允许的范围。拒绝规则和询问规则仍然排在它前面。这样的放行绑定到实际的执行上：守卫为这次调用记下一个期望，提供者拿到容器之后核对，实际的强度不够时命令不运行，结果告诉模型再调用一次就会被问到。

**容器的一生。** 会话的第一条命令到来时创建容器，这个会话的命令在其中依次运行。看守进程以 root 身份在容器里读着本程序握着的一根管道，管道一断容器就结束，所以本程序无论怎样退出都不会留下容器。命令以另一个用户运行，没有任何能力，也不能提权。每条命令之后，这个用户的全部进程被杀掉。超时和取消时先在容器里收尾，再等客户端退出；等不到，或者收尾没有回音，就放掉整个容器，并在结果里说明。会话结束、长时间没有命令、程序退出时容器被放掉。放掉是一件只做一次的事，谁来都等同一个结果；只有查得到引擎并且查不到这个容器时才算它没了，否则警告用户。命令运行期间容器被放掉而没能确认它没了，结果里说它可能还在运行，并给出删除它的命令。容器没说出第一句话就结束时，只有 `docker` 程序自己说没连上引擎、或者引擎没有这个镜像，才当作从未建成；其余情况是否建成并不知道，要等查过引擎才算数。关闭提供者的人被取消时，正在建的和正在放掉的容器照样做完。容器按会话本身记账，不按会话的名字，因为名字只在一个工作目录里唯一。

**容器看得到什么。** 只有工作目录。`read-only` 模式下它是只读的。`workspace-write` 模式下，顶层的 `.git` 和 `.columbina` 再以只读挂上一次；它们是链接时，挂的是工作目录下通往目标的第一级目录，因为挂载点挪不动，而只把终点挂成只读时命令可以把途中的目录换掉。`danger-full-access` 模式下整个目录可写。引擎会跟随作为挂载来源的链接，所以每个来源都先在本机解析，指向工作目录之外的不挂。链接指向的地方在不在工作目录之内，按它是哪个目录来判断，也就是比设备号和 inode，不只看路径怎么写：不区分大小写的磁盘上，同一个目录有许多种写法。挂载点用磁盘列出的那个名字。容器启动后以命令的用户看一眼工作目录，能读能写的情况必须和模式一致。

**一个名字盖不住的地方。** 只读挂载盖住的是一个名字。不区分大小写的磁盘上，容器经共享拿到的目录同样不区分大小写，`.GIT` 找到的就是 `.git`；Windows 的磁盘还可能留着 `GIT~1` 这样的短文件名。命令用另一个名字就能写进受保护的目录，也能把它改名。这在 Windows 的 Docker Desktop 上实测如此，而且拿挂载没有办法：可写的根目录只要挂进容器，名字就由本机那一侧去认。所以有东西以只读挂在某个名字上时，本机先看这个名字是不是还有别的写法或者短文件名，有的话强度降为 `partial`，命令照常要问人。`read-only` 模式下整个目录只读，不受影响。

**留着的门。** 本机和容器共用一个内核时，工作目录里的套接字从容器里够得到，哪怕没有网络、挂载只读。所以每条命令之前把工作目录查一遍，直到查到什么为止；查到之后这个容器的强度就是 `partial`，不再重查。查的过程中被别人删掉的目录当作里面没有东西。命令运行期间才出现的套接字看不到。容器放掉之后，会话记着它最后查到的情况，下一个容器建好之前按这个回答强度，否则下一条命令会先被放行、再被退回。

**容器拿到的是哪个目录。** 引擎按名字取工作目录，而能写上一级目录的人可以把名字换掉。所以会话记住目录名第一次的指向，之后指向别处就不再运行命令；容器连同目录的设备号和 inode 一起保存，每条命令之前核对；从看目录到挂载之间，Windows 上本程序持有工作目录和每个只读挂载来源的句柄，全部持有之后再看一遍，和第一遍不同就不建容器；其他系统上让容器报出它那里工作目录和每个只读挂载的编号来比对。比对只在容器看到的编号就是本机编号时才作数：随令牌一起挂进去的两个目录，本机知道它们的编号，容器报的对不上，就说明文件是经过共享换了编号才到容器里的，这时什么也核对不了，强度降为 `partial`。Windows 上的句柄只在本机磁盘上管用，工作目录在共享上或者在 WSL 发行版里时，强度同样降为 `partial`。

**`docker` 程序。** 提供者自己在搜索路径里找，只认绝对路径的条目，从名字到文件的整条路不得经过工作目录和本程序的启动目录。找到之后，在提供者的一生里不再换。被选中的提供者是 `docker` 而找不到程序时，启动时就给出警告；引擎在不在，要到第一条命令才问。

**不可用时不回退。** 引擎没有应答、镜像不在本机或者里面没有 bash、引擎会把容器里的用户对应到别的用户、配置点名的提供者不存在，命令工具的结果都是 `SANDBOX_UNAVAILABLE`，并写明原因。命令不会改在本机上不加约束地运行。程序不替用户下载镜像。

命令工具按命令所在位置的 shell 来写：在容器里是 bash，在 Windows 本机上是 PowerShell。交给容器的命令经固定的一行从标准输入读入，不经过本机的命令行。当前的强度，和提供者关于命令在哪里运行的说明，作为运行时上下文告诉模型，强度也显示在界面上。

子进程环境做清洗：变量名里含 `KEY`、`PASSWORD`、`SECRET`、`TOKEN` 的不传给子进程。容器里的命令只拿到镜像自己的变量和配置里写明的变量。

已知的限制见指南 `docs/guide.zh-CN.md` 的"在容器里执行命令"一节，和第 7 阶段计划里"实施中的发现"的最后一条。

### 9.4 规则

规则语法取自 Claude Code：`工具名` 或 `工具名(匹配串)`，例如 `powershell(git status*)`、`write(src/**)`、`read(./.env)`、`mcp__github__*`。

- **名字。** `read`、`write`、`run` 三个名字指所有这样做的工具。`write(docs/**)` 也管 `edit`，`read(.env)` 也管 `grep` 和 `glob`。其余的名字按工具名匹配，可以带 `*`。只按工具名的话，拒绝 `read(.env)` 之后还能用 `grep` 读到内容。
- **来源。** 用户目录的 `<COLUMBINA_HOME>/permissions.yml` 可以写 `deny`、`ask`、`allow`。项目的 `.columbina/permissions.yml` 只认 `deny` 和 `ask`，里面的 `allow` 被忽略并记一条警告，因为克隆下来的仓库不应该能替用户批准命令。命令行的 `--allow` 是本次运行的允许规则。人在审批提问里给出的"本会话内不再问"不是规则，它只对那一次调用原样有效，见 9.5 节。
- **求值顺序**固定为 `deny`、本会话的允许、`ask`、`allow`，首个命中生效。没有规则命中时，执行命令的调用要审批，会话处于 `danger-full-access` 时除外。其余调用放行，对文件能做什么由接缝把关。
- **文件模式**由 `/` 隔开的名字组成。`*` 代表一个名字里的任意一段，单独的 `**` 代表任意层目录。模式管它点名的东西和下面的一切。单独一个名字在任何深度上找，带斜杠的从工作目录算起，以 `/`、盘符或 `~` 开头的按完整路径匹配。`..` 只和 `..` 匹配，星号不会走出工作目录。Windows 和 macOS 上不分大小写。
- **命令**先拆开再判断。拆分器只认一种简单的形状：若干条简单命令，用 `&&`、`||`、`;`、`|` 或换行连接，每条由普通的词和不含展开的引号串组成。变量、命令替换、圆括号、重定向、转义符这类写法，拆分器看不懂，带匹配串的允许规则对这样的命令不生效。看得懂的命令逐段判断，每一段都被允许才放行。拒绝规则和询问规则对整条文本和每一段都匹配。bash 和 PowerShell 各有一个拆分器。
- **两处求值。** 规则实现为工具管线的守卫，判断调用点名的对象。针对文件的规则还登记成接缝上的限制，对工具实际碰到的每一个文件再判断一次：命中 `deny` 的拒绝，搜索途中命中 `ask` 的跳过。`grep` 的调用只点名一个起点目录，守卫看不到它一路读了哪些文件。
- 规则读不了时，这个会话不碰任何文件，也不运行任何工具。规则不清楚就没法遵守。

文档写明：命令规则按文本匹配，不是安全边界。隔离靠容器。

### 9.5 审批

`ctx.approval` 的结果是封闭集合：`allowed-once`、`rejected`、`cancelled`、`unavailable`。只有 `allowed-once` 放行，并且只对这一次调用有效。审批策略为 `never` 时不问任何人，结果是 `rejected`。没有应答者、应答者抛错或返回非法值，一律归为 `unavailable`。

每次询问写一对事件 `approval/asked`、`approval/decided`，不进模型上下文。询问带着调用所动的东西的全文，向人提问的界面应当展示全文，只看开头没法对一条命令说"可以"。

询问还带着一句话，说明一个管到会话结束的"可以"会管到哪里。不能给这样的"可以"时，这句话为空。给不给由权限插件判断，依据是调用本身。

终端里的应答者把问题印在输入行上面，依次是工具名、调用所动的东西的全文、询问的原因和每个键的含义。`y` 是允许这一次，`n` 是拒绝，Esc、Ctrl+C 和 Ctrl+D 也算拒绝。询问带着上面那句话时多一个键 `a`，表示本会话内不再问。应答者这时把这次调用原样登记到权限插件里，交回审批接缝的结果仍然是 `allowed-once`。接缝因此只认一次性的授权。

只有 `y` 和 `a` 算同意。输入行只把提问给出的那几个字母当作回答，一次一个字母。有些键到达程序时不带任何字符，这样的键不是回答。应答者拿回的东西只要不是这两个键，一律按拒绝处理。

提问可能在用户打字的时候出现，一个词打到一半的人没有读过这个提问。所以 `y`、`a`、`n` 要等提问印到屏幕上、键盘又安静了 0.6 秒才算数。选项从这一刻起才显示在输入行上，在这之前输入行显示三个点，按下的字母被丢弃，并且重新开始计时。看到选项再按键的人，回答的一定是这个提问。Esc、Ctrl+C 和 Ctrl+D 表示拒绝，不需要等。

本会话的允许只对同一个工具、同一个对象有效。命令要求逐字相同，并且只限拆分器看得懂的命令，因为带变量的命令下一次做的可能是另一件事。运行别人的东西、又不给出命令的工具，例如 MCP 服务器的工具，没有可以把两次调用分开的对象，对它的允许管这个工具的每一次调用，和一条写明工具名的规则一样。给命令用的工具没给出命令时不算这一类。它排在拒绝规则之后、询问规则之前，拒绝规则因此不会被一次回答绕过。它只留在内存里，程序结束就没有了，续接的会话重新询问。

### 9.6 来自别处的文字

前端显示的文字不全是本程序写的。回复来自模型，命令的输出来自命令读到的东西，报错可能来自服务商或某个文件。终端会执行它收到的控制字符：移动光标，改写已经显示的内容，改窗口标题，写剪贴板。还有一些字符会改变文字的方向，屏幕上的顺序于是和实际的顺序不同。不处理的话，一个被命令打印出来的文件就能改写屏幕上的审批提问。

`columbina.apps.terminal_text` 有三个函数，各管一种用途。

| 函数 | 用在哪里 | 做什么 |
|---|---|---|
| `harmless` | 要显示的来自别处的文字 | 控制字符、不是换行符的断行字符、落单的半个代理对、改变文字方向的字符，各换成一个 `U+FFFD`。长度不变，制表符和换行符保留 |
| `spelled_out` | 审批提问里调用所动的东西 | 看不见的字符、冒充空格的字符、改变方向的字符，都写成编号，例如 `<U+200B>`。拆分器正是因为这些字符拒绝给一条命令规则 |
| `escaped` | 打印出去的 JSON | 同样的字符写成 JSON 自己的转义，也就是字符的编号。JSON 的含义不变，其他语言的文字保持可读 |

哪些字符算看不见，由 `columbina.unseen` 一处回答，审批提问和命令拆分器用的是同一个判断。它包括控制字符、只管排版和方向的字符、各种空格和断行符、落单的半个代理对、私用区的字符和还没有分配含义的字符。还有一类字符被 Unicode 归在字母、标记和符号里，却什么也不画出来，只看类别认不出它们：把两边的字符连在一起的 `U+034F`、谚文的填充符、高棉文里两个不写出来的元音、选择字形的变体选择符、没有点的盲文图案。文件名里带着这样一个字符，就是另一个文件。字母上的重音看得见，保持原样。

终端 CLI 里，印到屏幕上的每一行、输入行上方没写完的那一行和输入行下面的状态行，都先经过 `harmless`。这些文字里因此没有任何内容会作为转义序列到达终端，到达终端的序列只有程序自己选的颜色和绘制输入行用的那些。来自别处的文字在组成一行的时候就经过 `harmless`，早于交给 `rich`。`rich` 会把响铃、退格、回车等五个控制字符直接删掉，不留痕迹，中间夹着退格的两个词在屏幕上会连成一个词。别处组成的行在印出之前还会再过一遍。

`columbina run` 的回答在输出是终端时经过 `harmless`，输出是文件或管道时保持原样，脚本读到的是模型写的原文。写到标准错误的说明和日志一律经过 `harmless`，命令行解析器复述一个它不认识的参数时也一样。`--json` 的每一行经过 `escaped`。

## 10. 上下文管理

模型需要知道的事情里，有一些既不是用户说的话，也不属于系统提示：它在哪个目录里工作，项目有什么约定，上一回合被打断过。这些都作为用户角色的上下文消息，在回合开始时写进日志。来源登记在 Agent 服务上。每个来源给出一段文本，并声明自己属于哪一种。

| 种类 | 什么时候写 | 用它的来源 |
|---|---|---|
| `replace` | 文本与这个来源上一次的不同时写，顶替旧消息 | 指令文件、待办清单 |
| `append` | 文本与上一次的不同时写，追加在对话后面 | 运行时上下文 |
| `note` | 来源每给一次就写一次 | 打断说明 |

循环在每个回合的第一步之前按 `order` 逐个问来源，全部问完再写，写下的消息排在这一回合的输入之前。文本包在 `<context source="名字">` 和 `</context>` 之间。文本里出现的结束标签被拆开，所以文件内容不能提前结束这一段。来源出错时一条也不写，输入照常认领，回合以 `error` 结束，不向模型发请求。输入如果不认领就会留在 inbox 里，循环会立刻再开一个同样出错的回合。

上一回合以 `aborted` 或 `interrupted` 结束时，打断说明这个来源给出一条说明。被打断的回复后面原本直接跟着新的用户消息，模型看不出中间发生过什么。

压缩把一段对话换成摘要之后，站在那一段里的上下文消息就不在模型看到的内容里了。会话记下消息面被顶替的次数，循环在发每个请求之前比较这个次数，变了就把来源重新问一遍，`note` 类的除外。一个来源上一次给出的消息已经不在消息面上时，文字没有变也重写。这样被遮蔽的上下文在同一个请求之前就补上了，不必等到下一个回合。

### 10.1 系统提示

`ctx.system_prompt` 是段落注册表加一条 `system-prompt/assemble` waterfall。文本是 `AgentSpec.system_prompt` 加上各段落，段落按 `order` 升序、再按名字排序，之间空一行。变量（`{{name}}`）和工具模式提供者在用到它们的阶段再加。

循环在每个回合开始时要一次文本，结果作为 `system/message` 进日志。文本没变就不写新事件，变了就顶替旧的。没有这个服务时循环直接用 `AgentSpec.system_prompt`。

### 10.2 运行时上下文

沙箱模式、审批策略、工作目录这类会变的事实不进系统提示。它们合成一条上下文消息，只在内容变化时追加新的一条。被压缩遮蔽时重发，在第 5 阶段和压缩一起做。目的是保住前缀缓存。

事实由知道它的插件给出。`columbina.context.runtime` 自己只知道工作目录。它发一个 `agent/runtime-facts` 事件，沙箱加上模式、约束强度和提供者关于命令在哪里运行的说明，审批加上策略，命令工具加上它用的是哪种 shell。没装的插件不加，卸载的插件带走它的那一行。各行按名字排序，文本不随插件的加载顺序变。

日期默认不注入。

### 10.3 指令文件

- 候选文件名默认是 `AGENTS.md`、`CLAUDE.md`，同一个目录里两个都有时都读。项目根是从工作目录往上最近的含 `.git` 的目录，找不到时只看工作目录。
- 文本由宽到窄：先是用户级的 `<COLUMBINA_HOME>/AGENTS.md`，再是从项目根到工作目录的链。每个文件前面有一行写明它的路径。内容相同的文件只出现一次。
- 字节预算 65536。超预算时先丢更宽的文件，最后才截断最具体的文件，并在文本里说明。
- 指令文件由 Harness 替用户读，不经过沙箱，所以读得谨慎。只读就在那个位置上的普通文件，链接一律不跟随，并告诉模型哪个文件没读。仓库里的链接可以指向用户的密钥，也可以指向项目里被规则挡住的文件。指向另一个指令文件位置的链接直接跳过，那个位置上的文件照常读。
- 文件变了，下一回合发一条顶替的消息。文件没了，发一条说明。文件在而读不了时，回合以 `error` 结束。

### 10.4 溢出存盘

溢出存盘是一个接缝，有两个方法。`save_text` 存一段文字。`open` 给出一个可以边到边写的文件，命令的完整输出用它。

本地提供者写到 `<COLUMBINA_HOME>/spill/<工作目录的键>/<会话 id>/`。文件名是八位随机的十六进制数加上调用方给的名字，独占创建。POSIX 上三层目录和文件都只有属主可以访问，目录逐层创建，因为一次建到底时只有最末一层得到指定的权限。超过 2000 个字符的行在存盘时被折开，否则 `read` 读不到一行的后半段。分段到来的文字无论怎样切分，折行的位置都相同。

提供者在文件系统接缝上登记一条授权：模型可以读这个工作目录的溢出文件，不能往里写，也不能读别的工作目录的。启动时清掉超过三十天的文件，不跟随链接。

### 10.5 压缩

压缩是可选能力，接缝为 `ctx.compaction`，提供者 `compaction_basic`，手动入口是 `/compact` 命令。

| 项 | 内容 |
|---|---|
| 主动触发 | 在 `agent/pre-step` 上，估算 token 超过 `floor(min(W×0.8, W−O−B))`。`W` 是上下文窗口，`O` 是输出上限，`B` 是余量 |
| 余量 | `B = min(65536, W×0.25)`。原版固定 65536，窗口小的本地模型会永远触发不了 |
| 被动触发 | `agent/request-error` 收到 `CONTEXT_WINDOW_EXCEEDED`。每一步最多一次，只有消息面确实前进才授权重试。报错里有窗口大小和请求大小时读出来：要去掉的量是超出的数量加上余量，服务说的窗口优先于配置 |
| 裁剪与摘要 | 先算出裁剪超大的旧工具结果能省多少。够回到阈值以下就只裁剪，不调模型。不够时再算上模型还没读过的结果：它们加起来超过窗口的四成时，其中大的裁到一个公共的上限，使它们合起来不超过，两项合起来够了也只裁剪。还不够才对原样的选区做摘要：这样摘要请求的开头与上一次请求相同，缓存能命中，模型写摘要时看到的也是完整的结果。摘要之后仍然超出，或者没有得到摘要，再裁剪前两步找到的结果 |
| 选区 | 从系统消息和紧随其后的上下文消息之后开始的最老区间。边界保持工具调用与结果成对。最后一条由人写的消息留在保留的尾部里，除非从它开始的尾部超过窗口的一半：当前的任务是用户的原话，不应该只剩转述 |
| 保留 | 最新的约 `(W−O)×16%` 原样保留 |
| 摘要调用 | 一次额外的模型请求。原样回放系统提示、工具声明和被压缩区的消息，最后追加压缩指令。指令要求写一份给接手者的交接说明：进展与决定、约束与偏好、剩余步骤、关键数据。请求不设 `tool_choice`，因为服务会因此拿掉工具声明，缓存随之失效。指令里写明不要调用工具。指令还要求分清谁说的：文件、网页和工具结果里的话记成读到的东西，不记成用户的要求或同意，用户设下的限制照原话记。回复带着工具调用或者什么都没有时不算摘要，不带工具声明再问一次。被输出上限截断的回复和不比原文短的摘要都作废。被压缩区超出模型能接受的长度时只给它看较新的一半，这时顶替的那条消息写明摘要没有覆盖最早的部分，要用到时照实说没有，不要猜 |
| 落盘顺序 | `compaction/start`，每次摘要请求一条 `request/aside`，`compaction/summary`，一条替换型的 `user/message`，最后 `compaction/end`。裁剪留下的是替换型的 `tool/result` |
| 崩溃语义 | 顶替的那条消息写下去，压缩才算发生。中途崩溃留下可检测的孤儿 `compaction/start`，续接之后不算数 |
| 失败 | 摘要失败时这次压缩作废，`compaction/end` 带上原因，回合照常继续。主动压缩连续失败两次之后暂停，直到有一次成功。被用户取消的和用户要求的不计入失败 |
| 模型与窗口 | 取下一次请求实际会用的调用配置。`agent/request` 的监听器把请求改送别的模型时，窗口和写摘要的模型都跟着换 |

压缩之后，被遮蔽的上下文在同一个请求之前补上，见本章开头。手动压缩走 `Agent.run_maintenance`：它只在 Agent 空闲时接受一件事，由驱动任务执行，执行期间到来的输入排在它后面，`cancel()` 能停下它。

窗口很小时主动压缩可能无从下手。系统提示和工具声明合计约两千个 token，窗口只有这个数的三四倍时，对话可以已经越过阈值，而最后一条由人写的消息之后的内容还不到窗口的一半。这时选区是空的，主动压缩失败，等模型拒绝请求时由被动压缩接手。DeepSeek Flash 的窗口远大于此。第 8 阶段用本地模型时再考虑让选区可以从人写的消息之后开始。

### 10.6 待办

`todo_write` 每次整体替换清单，状态存为 `todo/write` 事件。每项有内容和状态，状态是 `pending`、`in_progress`、`completed` 之一，同一时刻最多一项在进行。清单最多 100 项，每项是一行，最多 500 个字符。不合规的清单被拒绝，旧清单不变。清单跨回合保留，只影响模型看到的内容和界面显示。

模型在写下清单的那次调用里看得到它。那次调用被压缩遮蔽之后，清单作为上下文重新告诉模型，模型还看得到那次调用时不重复。终端在清单写下时把它印出来，一项一行，`/todos` 随时可以看。

## 11. 扩展机制

四项各是一个插件，互不依赖，都在 `base` 清单里。MCP 的服务器不在清单里：有哪些服务器是用户的事，每个服务器是用户自己的清单里的一项。逐条的设计决定和理由见[第 6 阶段的实施计划](2026-10-10-columbina-stage6-extensions.md)。

### 11.1 技能

- 一个技能是一个目录，路径是 `<根>/<名字>/SKILL.md`，只看一层。frontmatter 必填 `name` 和 `description`，`name` 必须与目录名相同。可选 `disable-model-invocation` 和 `user-invocable`。别的键忽略，但这两个键的近似拼写不忽略，带着它们的技能判为无效。
- 根按先后是 `<项目>/.columbina/skills`、`<项目>/.agents/skills`、`<COLUMBINA_HOME>/skills`，再是配置里的 `user` 和 `extra`。同名的技能取先找到的那个，落选的和无效的都记下原因。随包的清单只配了 `<COLUMBINA_HOME>/skills`，`~/.agents/skills` 要在配置里写明才会去找。
- 项目里的根不跟随链接，用户自己的根跟随。仓库里的东西是别人写的，一个链接可以指到仓库之外。
- 渐进披露三层。模型先在一条上下文消息里读到目录，每个技能一行，写名称和至多 500 个字符的简介，整条消息至多 12000 个字符。模型调用 `skill` 工具时才读正文。正文提到的文件由模型自己去读。
- 每个回合开始时重新找一遍，目录的文字没变就不重写。某个根这一次读不出来时沿用上一次的结果。
- 用户目录下的技能在工作目录之外。技能插件向文件接缝登记一条只读的许可：这个会话被告知的各个技能目录之内的文件可以读。许可按文件的真实位置判断。
- 人用 `/skills` 看有哪些技能，用 `/skill 名字 [任务]` 直接把一个技能交给模型。技能名不当作斜杠命令，免得一个新技能盖住一条命令。

### 11.2 钩子

原生的钩子就是内核事件。另有一个兼容桥 `columbina.hooks`，读 Claude Code 格式的 `hooks.json`，只支持命令型。

| 钩子事件 | 挂在哪里 | 能做什么 |
|---|---|---|
| `SessionStart` | 上下文来源，Agent 的第一个回合开始时 | 输出作为上下文交给模型 |
| `UserPromptSubmit` | `agent/pre-step`，每条人写的输入一次 | 拦下这条输入，或者附加上下文 |
| `PreToolUse` | `tools/pre-execute` | 拒绝这次调用，或者要求先问人 |
| `PostToolUse` | `tools/post-execute`，只在工具成功之后 | 把结果换成理由，或者在结果后面附加上下文 |
| `Stop` | `agent/turn-stopping` | 给出理由，让模型再走一步，一个回合至多三次 |

- 配置有两处：`<COLUMBINA_HOME>/hooks.json` 和 `<项目>/.columbina/hooks.json`。项目的那一处要先由用户用 `columbina hooks trust` 信任才生效。记录的是文件的位置和内容的 SHA-256，文件一变就要重新信任。两个文件在每个回合开始时重读。
- 匹配只对两个与工具有关的事件起作用。没写、空串或 `*` 表示全部，别的写法是正则，要求与工具名整体匹配。一个工具有两个名字可以对上：它自己的名字，和 Claude Code 里同类工具的名字。
- 命令用 shell 工具的那个 shell 运行，一行 JSON 从标准输入交给它。退出码 2 表示拦截，理由取标准错误。退出码 0 时标准输出里的 JSON 可以给出决定和上下文。别的退出码和超时记为失败，不拦截。
- 钩子只能收紧。钩子的“允许”只表示它没有异议，权限规则和沙箱照常判定。几个钩子的结果取最严的一档。
- 被 `UserPromptSubmit` 拦下的输入从模型看得到的对话里撤下，回合以 `blocked` 结束。
- 子代理只运行两个工具事件的钩子。另外三个事件说的是人和人的会话，对子代理不运行。
- 每次运行写一对 `hook/invoked`、`hook/result` 事件。桥里的任何失败都只记日志，不向循环抛异常。

`SessionStart` 没有像最初设计的那样映射到 `agent/created`。钩子的输出要等命令跑完才有，通知式的事件等不了它。上下文来源在回合开始时被问到并被等待，输出一定赶得上第一个请求。

### 11.3 子代理

- 接缝是 `columbina.subagents`，提供者 `spawn` 在进程内创建子代理。模型用 `subagent` 工具交出任务，参数是 `description`、`prompt` 和可选的 `type`。调用等到子代理的回合结束才返回，同一条回复里的几个调用同时执行。
- 每个子代理是父 Agent 之下的一个 Agent，从空白的上下文开始，有自己的作用域和自己的会话。会话头里记 `parent_session` 和 `delegation_depth`，会话列表和 `--continue` 只看深度为 0 的会话。
- 子代理与父 Agent 同目录，缺省用同样的模型、系统提示和工具，步数上限 50。工具里总是去掉 `subagent`。审批策略固定为从不询问，沙箱模式取父会话此刻的。
- 结果是子代理最后一条非空回复。回合不是以 `completed` 结束，或者结束了却没有文字，都是一条工具错误，写明是怎么结束的。已经写出的文字附在错误里并注明不完整，不把部分输出当成功。
- 类型用 Markdown 加 frontmatter 定义，放在 `<项目>/.columbina/agents/` 或 `<COLUMBINA_HOME>/agents/`，项目里的优先。可以写 `tools`、`max_steps`、`model`。类型只能把工具和步数收窄。项目里的类型不能选模型：模型花的是用户的钱，而项目是别人写的。
- 上限：委派深度 1，同时运行 4 个，多出的排队。
- 父会话里记 `subagent/started` 和 `subagent/ended` 两种事件。后者带着子代理那个回合结束的原因、说明和代码，读父会话的日志就能给子代理的结束方式分类。子代理的用量以一条 `request/aside` 记进父会话，状态行和合计里有它。

### 11.4 MCP 客户端

- 插件 `columbina.mcp` 在 `base` 清单里，它不导入 SDK。每个服务器是用户清单里的一项，插件是 `columbina.mcp.server`。官方 `mcp` SDK 是可选的依赖，由 `columbina[mcp]` 装上。
- 传输是 stdio 或 streamable HTTP。被启动的服务器进程只拿到 `PATH` 一类的少数变量和配置里 `env` 写明的变量，程序自己的环境不传给它。它写到标准错误的内容进文件 `<COLUMBINA_HOME>/logs/mcp-<服务器>.log`。
- 服务器在后台连接，不挡住程序启动。回合在拼系统提示之前和每一步之前等所有服务器连上或者失败，至多等到启动时限。连不上的服务器记一条日志，别的照常。
- 工具名是 `mcp__<服务器名>__<原名>`，服务器名取本地配置的。原名里不合规的字符换成下划线，换过或者过长的名字截断并加一段哈希。
- 工具的描述和参数说明是服务器写的。参数说明原样交给模型。它的根不是对象、`properties` 不是对象，或者它超过 16 KiB 时，这个工具不提供，原因记日志：服务会因为一个写错的参数说明拒绝整个请求。
- MCP 工具走和原生工具相同的管线。服务器标注只读的工具算读，别的一律算运行，要过审批。审批时可以只同意这一次，也可以对这个工具同意到会话结束，见 9.5。
- 结果转成文字：文本原样，图片和音频换成一句占位的话，没有文本而有结构化内容时给它的 JSON。服务器标明出错的结果是一条工具错误，它的文字至多一万个字符，超出的略去中间一段。
- 一次调用的时限缺省 60 秒，管的是整个调用，包括把它写给服务器的那一段。
- 每个服务器有一个保持连接的任务。连接断开时，正在进行的调用回答一条错误，不重发。保持者记一行日志并重连，连接是带着错误断开的就写上原因，等待从 0.5 秒起加倍到 30 秒，连续 10 次失败后放弃并撤下工具。连上之后稳定满 30 秒，次数才清零。重连期间工具仍然在，这时来的调用等连接恢复；断线一经得知，旧的连接就不再交给新来的调用，哪怕保持者还没有来得及放开它。
- 用 HTTP 对话、说 2026 年之前协议的服务器给每个连接一个会话，并且可以随时结束它：隔了一阵没有调用，或者服务器重启过。此后带着这个会话号的请求一律得到 404，SDK 把它当成普通的错误交回来，连接看上去还在，每次调用都失败。所以 HTTP 这一层看每个回答的状态：带会话号的工具调用得到 404，就是被拒了。别的状态不算，不带会话号的请求不算，调用之外的请求（例如 SDK 在调用之后为核对结果列的工具）也不算。
- 哪一次调用被拒，靠调用方上下文里的一个标记认出来。SDK 在调用方上下文的副本里发出请求，副本里是同一个标记对象，看回答的钩子在它上面记一笔，调用方就看得到。同时在途的几次调用各有各的标记。
- 有调用被拒，保持者先让还在途的调用听到各自的回答，至多 2 秒，再放开旧连接并重连：会话结束之后发出的调用很快也会被拒，太早放开会把它们切断，变成“不知道走到哪一步”。按协议，被拒的调用服务器没有执行。服务器可能不守协议，所以只有服务器标注只读的工具才在新连接上自动重发一次，再被拒就回答错误；别的调用回答一条错误，说明连接正在重建、请重新调用，由模型和审批来定。重发的那一次重新计时，整个调用仍受工具管线的总时限约束。会话结束不算服务器出故障，不计入放弃前的连续失败次数，等待也不加倍。
- 放开旧连接时 SDK 想结束那个已经不在的会话，会记一条“Session termination failed: 404”。这不是故障，谁也做不了什么，所以连着地址上的服务器期间，这一条不进日志。
- 调用带着它被放行时服务器对这个工具的说法。它等到连接之后，服务器列出的同名工具如果已经不一样，例如不再标注只读，这次调用不执行，模型被告知按现在的工具重新调用。
- 服务器用订阅告知“工具变了”。订阅正常结束或者中途断掉而连接还在时，SDK 不会自己再订阅，保持者等一会儿重新订阅，订阅上之后再列一次工具，这中间的变化就不会漏掉。等待的规则与重连相同。订阅之后很快又结束，连续超过 10 次，这次连接里就不再订阅，记一条警告。
- 关闭连接时比放开连接的时限多等半秒，所以放开得慢但守时限的连接在关闭返回时已经放开。到时仍不放开的连接记一条警告，再关一次就再等一次，不会第二次打断它。
- 地址里问号之后的部分、主机名之前的用户名和密码，还有请求头的值，都不进日志。连接自己写的失败原因里没有它们。SDK 和 HTTP 库自己写日志，请求失败时会复述地址，所以服务器在用期间，进程里每一条日志记录在生成时都去掉这些文字，连同它带着的回溯，见 `columbina.withheld`。地址的路径不在其中，令牌不要放进路径。不足 6 个字符的文字不算令牌，不处理。
- 服务器的说明作为带归属的系统提示段，缺省上限 4096 字节。
- `/mcp` 列出每个服务器的状态、工具的个数和最近一次失败的原因。

### 11.5 命令与插件

人用的斜杠命令走 `ctx.commands`，由程序直接执行，不产生模型消息。命令登记在一个注册表里。谁拥有一份状态，谁登记显示或修改它的命令，前端不需要认识这些命令。登记命令的插件卸载时，命令跟着消失。

第 4 阶段有七条命令。`/help` 来自命令插件自己。`/tools`、`/sessions`、`/permissions` 各是一个插件，等它要显示的服务就绪才加载，所以没有权限插件的程序也没有 `/permissions`。`/exit`、`/model`、`/new` 由终端前端登记。

第 5 阶段加了三条，各是一个插件。`/compact` 请压缩服务在两个回合之间压缩一次，并说明结果。`/todos` 显示待办清单。`/fork` 让对话转到当前会话的一份副本上。换会话要靠拿着对话的前端来做，能做的前端提供服务 `SWITCH`：给它一个创建 Agent 的函数，它先让新的 Agent 建好。新的一到，对话就接到它上面，旧的随后才关掉，所以旧的收尾期间新的做了什么都不会漏掉。新的建不出来时对话留在原处。`/new` 走同一条路。没有前端提供 `SWITCH` 时，`/fork` 说明原因，什么也不复制。

第 6 阶段加了三条。`/skills` 列出技能，`/skill` 把一个技能交给模型，两条来自同一个插件。`/mcp` 列出 MCP 服务器的状态。

命令名取到第一个空格为止，不分大小写。没有这个命令、命令执行出错，或者命令做到一半被停下，都回答一句话，程序照常运行。回合进行中不执行命令。

树外插件是普通的 Python 模块，在清单里用导入路径引用。

## 12. 前端

### 12.1 启动器

- `columbina`：进入终端 CLI。
- `columbina run "任务"`：无界面，跑一个任务。
- `columbina bench ...`：跑基准。
- `columbina sessions list|show|fork`：管理会话。
- `columbina doctor`：自检密钥、模型可达性、shell、ripgrep、容器。
- 通用参数：`--profile`、`--patch`、`--model`、`--permission`、`--sandbox`、`--dump-config`。

第 2 阶段有 `columbina run`，参数是 `--profile`、`--patch`、`--model`、`--cwd`、`--session-id`、`--json`、`--no-json`、`--dump-config`。第 3 阶段加了 `--permission` 和 `--allow`：前者给名为 `permissions` 的条目点名预设，后者给它追加一条允许规则，可以给多次。清单里没有这个条目或者它被禁用时，用这两个参数会报错，退出码为 2。

第 4 阶段加了 `columbina chat`，进入终端里的对话。不写子命令时就是它，命令行以选项开头时也是它，所以 `columbina --continue` 等于 `columbina chat --continue`。`--help` 和 `--version` 除外。`chat` 加载 `cli` 清单，`run` 加载 `headless` 清单。除 `--json` 之外，`run` 的参数 `chat` 都有。`--continue` 只属于 `chat`，续接这个工作目录最近用过的会话，和 `--session-id` 同时给出时报错。清单里写了会话的名字时，`--continue` 优先，清单里的名字不用。`--cwd` 指向的不是目录时报错，什么都不加载。其余命令随各自的阶段加入。

两个子命令都把日志写到标准错误，写之前经过 `harmless`。对话期间日志显示在输入行上面，由前端接管。输入行出现之前和消失之后，日志仍然走标准错误：插件在这两段时间里加载和卸载，加载失败的记录带着完整的报错和文件名。

第 5 阶段加了 `columbina sessions`。`list` 列出工作目录下存着的会话，`show ID` 逐回合印出一个会话的输入、回答的末尾和回合没有正常结束时的原因，`fork ID` 把一个会话复制到最后一个完整的回合，印出副本的 id。三个子命令接受 `--cwd`、`--profile` 和 `--patch`，`fork` 另有 `--session-id`。它们叠出与对话相同的各层，但只加载其中名为 `session` 和 `agent` 的两项：前者管日志，后者声明了读日志的程序不能略过的收件箱事件。所以它们不需要模型，清单里的模型加载不了也不妨碍。会话读不出来、id 不合法或者没有可复制的回合时退出码为 2。

程序由几层叠出来，依次是清单、`<COLUMBINA_HOME>/config.yml`、各个 `--patch`、命令行自己的参数。名为 `frontend` 的条目提供要运行的前端。命令行只改它点名的设置。没给 `--cwd`、`--json`、`--session-id` 时，前面各层的值保持不变。工作目录只有在哪一层都没指定时才取当前目录。

### 12.2 无界面

最终回答写到标准输出。`--json` 输出逐行事件：`session`、`status`、`text`、`thinking`、`tool_call`、`tool_result`、`final`。`final` 带结束原因、代码和用量。`--session-id` 续接已有会话，没有这个会话就用这个 id 新建。

回答是模型写的。输出是终端时，回答里会被终端执行的字符先换掉。输出是文件或管道时回答保持原样。见 9.6 节。

退出码有四个。回合以 `completed` 结束为 0。回合以别的原因结束，或者 Agent 中途停下，为 1。命令行、清单或插件加载有问题，为 2，这时不发任何模型请求。被 Ctrl+C 打断为 130，打断前先把当前回合正常收尾。

### 12.3 终端 CLI

终端里始终有一个输入行，对话印在它上面。输入行由 `prompt_toolkit` 绘制，只有它移动光标。`rich` 只把一行文字渲染成带颜色的字符串。

**输入。** 提交的一行交给 Agent。Agent 空闲时，这一行是新任务。回合进行中，它是 `steer`，模型在下一步开始时读到。以斜杠开头的是命令，等 Agent 空闲才执行。行首行尾的空格不算。

**显示。** 显示的内容来自会话日志，续接的会话因此和原来看到的一样。只有正在生成的回复取自流式分片，别的来源不够快。写完的行印到输入行上面，之后不再改动。没写完的那一行画在输入的上方，随回复增长重画，每秒最多二十次。提交一行时，这半行不留在屏幕上，否则它会出现两次。

| 发生的事 | 屏幕上的样子 |
|---|---|
| 模型的回复 | 原文，逐行 |
| 工具调用 | 一行，写明工具名和它所动的东西。`edit` 另有改前改后的开头各六行，`write` 写明行数 |
| 工具结果 | 一行，写明成功或错误码，以及用时。命令的输出给出末尾五行，报错和退出码都在末尾。错误给出开头三行。等人回答的时间不算在用时里 |
| 回合中途说的话 | 模型读到它的时候印一行，前面有标记 |
| 回合没有正常结束 | 一行说明原因 |
| 请求重试 | 一行说明错误码和等待时间 |

每个回合结束后空一行。上下文消息和记账用的事件不显示。

**按键。** Esc 停止正在进行的回合，Ctrl+C 也可以。命令让 Agent 做的事同样可以这样停下，例如 `/compact` 请模型写的摘要。命令执行期间提交的行，等命令结束后再处理。终端用 Esc 开头表示 Alt 组合键，单独的 Esc 因此要等十分之一秒才算数。空闲时 Ctrl+C 清空输入，输入为空时再按一次退出。Ctrl+D 在输入为空时退出。

**审批。** 提问印在输入行上面。提问上屏、键盘安静 0.6 秒之后，输入行的提示符换成 `[y/n]` 或 `[y/a/n]`，在这之前是三个点。提问期间，正在输入的文字先收起来，回答之后放回。已经提交的一行不会被放回。写字的键不起作用，回车不算回答。见 9.5 节。

**状态行。** 输入行下面有一行，写着模型、沙箱模式与强度、对话现在折合多少 token 和它占上下文窗口的比例、缓存命中率。token 数是估算值，前面有一个 `~`，压缩之后立刻降下来。程序没有估算服务时，这里是上一次请求发出的 token 数，不带这个记号。回合进行中和命令执行期间，这一行提示 Esc 可以停止。数字取自会话日志。预设要到第一个回合开始时才写进日志，在那之前状态行和 `/permissions` 显示的是预设将要给出的模式和策略。

**续接。** 用 `--continue` 或 `--session-id` 续接会话时，先印出上一个回合的输入和回答的末尾。

**终端。** 前端不自己找控制台，它拿到一个终端对象。真实的终端由 `real()` 给出，标准输入或输出不是终端时没有。测试经服务 `terminal` 提供自己的。屏幕显示不了的符号换成 ASCII 写法，Windows 的旧控制台一律用 ASCII 写法。环境变量 `NO_COLOR` 不为空时不用颜色。

退出码有三个。用户离开为 0。会话打不开，或者 Agent 因为会话写不下去而停下，为 1。没有终端为 2，这时提示改用 `columbina run`。Agent 停下这件事不论发生在哪里都会被发现：回合可以不是从键盘发起的，停下也可以发生在用户离开的那一刻，那时正在进行的回合要收尾，收尾的内容要写进日志。

待办清单在模型写下它的时候印出来，一项一行，正在做的一项加粗，做完的变淡。写清单的那次调用只印工具名。

压缩开始时印一行原因：对话接近模型的上限，或者模型因为太长拒绝了请求。结束时印一行结果。压缩进行期间，输入行上方写着正在压缩，位置与模型思考时的提示相同。用户用 `/compact` 要求的那一次由命令自己回答，终端不重复。

### 12.4 之后

第 10 阶段加 JSON-RPC 2.0 的 stdio 服务和桌面应用。应用由三部分组成：Electron 写的壳，网页技术写的界面，以及这个服务。界面与服务之间的消息已经先行规定，见 [`docs/protocol/README.md`](../protocol/README.md)，界面可以在服务实现之前对着样例数据开发。选 Electron 是因为它自带浏览器内核，界面在各个平台上的表现一致。界面的视觉设计届时单独做。

## 13. 质量保障

### 13.1 测试分层

| 层 | 做法 |
|---|---|
| 单元 | 内核、日志折叠、路径隔离、编辑工具、截断、权限规则、分片装配等 |
| 循环 | 用脚本化适配器驱动真实的工具管线和 JSONL 持久化。只替换模型、网络和时钟 |
| 性质 | 用 hypothesis 随机生成输入与取消的时序，取消也可以从监听器和工具内部发起。不变量见表后 |
| 回放 | 录制的真实会话既是输入也是期望输出，不需要密钥。`replay` 适配器按顺序给出会话里记下的每次回复，工具在工作目录的副本里真的再跑一遍，重跑得到的日志必须与录制的逐事件相同。每个录制写明当时加载的清单，测试按它装配。调用了命令工具的录制只在录制时的平台上重放 |
| 请求快照 | 把每次请求写成文本存成快照。每条消息一行序号和角色，每个内容块一行。只在上一次请求之后追加内容的请求，只写它追加的部分 |
| 变异 | 往代码里逐个放入小错误，看测试能否发现。第 4 阶段结束时有 25 组，共 654 个变异体，覆盖循环、工具管线、文件系统接缝、沙箱、各个工具、权限、审批、上下文消息、指令文件、启动器、清单，以及终端前端的各个部件。带随机样例的测试在变异检查里用固定的样例，同一份代码的结果因此可以重现。`tests/mutation/mutate.py` 手工运行，不进闸门。闸门里只有一条测试，检查变异清单仍然对得上代码 |
| 屏幕 | 终端前端的测试跑在一个模拟的终端上。`tests/support/vt.py` 执行 `prompt_toolkit` 发给 VT100 类终端的序列，留下屏幕的每一行、滚出窗口的行和光标的位置。不认识的序列一律报错，测试因此不会去看一块靠猜拼出来的屏幕。测试断言屏幕上实际显示的内容，被覆盖和被擦掉的部分也算在内。整场对话结束时的屏幕另存一份快照 |
| 卸载 | 每个注册表一条测试：销毁贡献它的插件实例，断言清理干净 |
| 适配器恢复 | 本地模拟 SSE 服务器，编排断流、挂起、畸形 JSON、429、5xx |
| 真实接口 | 有密钥时对真实模型跑，没有就跳过 |

性质测试检查这些不变量。

- 每条输入恰好在一处：已经进了模型的历史，还在 inbox 里等，或者在一次要求丢弃的取消发生时正在等。
- 回合号严格递增，步号连续，回合和步都正常闭合。
- 工具调用与结果始终成对，结果按模型给出的顺序写入。
- 后一次请求以前一次请求的全部消息开头，历史只增不改。
- 回合被取消之后不再向模型发请求。工具要求结束回合之后不再开新的步。
- 被取消的回合不再取走输入。取消提出时还在等的输入，以及之后才给的输入，都不会进入这个回合。
- 独占的工具不与别的调用重叠，并行的调用不超过上限。
- 整个过程不产生错误级别的日志。

两条纪律。断言要重新读文件或重跑命令来验证结果，不信 Agent 的自述。产品可见的插件必须有一条经真实清单加载的测试。

### 13.2 闸门

- `ruff` 检查和格式化。
- `pyright` 严格模式。
- `src/columbina/kernel`、`session`、`llm`、`agent`、`agent_loop`、`tools` 的行覆盖率不低于 90%。
- GitHub Actions 矩阵：Windows、Ubuntu、macOS，Python 3.11 和 3.12。

## 14. 基准

### 14.1 验收基准

四类任务，每类都能自动判分。每个任务在全新的临时工作区里运行。

| 类别 | 内容 | 判分 | 规模 |
|---|---|---|---|
| 代码修改 | 小型 Python 仓库，给出问题描述和可见的失败测试 | 运行隐藏测试 | 约 15 个 |
| 文件与命令行操作 | 整理目录、改配置、合并文件等 | 检查最终的文件树和内容 | 约 12 个 |
| SQL 数据查询 | 带种子生成的 SQLite 库和自然语言问题。工具有查表结构、只读查询、提交答案 | 比对结果集；另在一份扰动过的库上复核，防止硬编码 | 约 15 个 |
| 多步工具计算 | 由 ReliQuant 的程序生成。题面中的数值藏在查询工具后面，必须调用工具才能得到 | 核对最终答案和必需的查询调用 | 可大样本 |

每个任务带参考解。校验命令检查两件事：初始状态判为失败，应用参考解后判为通过。

每次发布前在 DeepSeek Flash 上跑，成功率不得低于上一版。

### 14.2 部件开关表

对每个可选部件，比较开与关时的成功率和 token 成本，一张表。部件包括压缩、待办、工具调用修复、重复调用提醒、溢出预览。用途是决定默认开哪些。

### 14.3 本地模型支持矩阵

Qwen2.5 和 Llama 的各量化档在验收基准上的成功率，标出哪些档位可用。用独立的 Ollama 实例，模型目录指向 `D:\ollama-models`，不改动现有的 Ollama 设置。

### 14.4 性能与成本

- 性能：冷启动时间、一千步合成长会话的恢复与折叠耗时、内存占用。输入全部由常量合成。设预算并放进持续集成。
- 成本：每个任务的 token 数和缓存命中率。

## 16. 风险与未决事项

| 事项 | 处理 |
|---|---|
| Windows 上 shell 没有操作系统级约束 | 第 7 阶段前靠审批和规则。界面如实显示强度为"无" |
| 现有的 Ollama 读的是 C 盘空目录 | 基准阶段单独起一个指向 D 盘的实例 |
| DeepSeek 思考模式下采样参数不生效 | 基准中记录每次请求的完整配置；是否关闭思考在基准阶段决定 |
| 真实终端里的显示没有人工之外的验证办法 | 界面的测试跑在模拟的终端上，逻辑和画面都有断言。真实终端由作者按第 4 阶段计划末尾的清单检查。Windows 的旧控制台走的是另一条绘制路径，模拟不到 |
| 服务把一个代理对拆在两个流式事件里 | 这条回复以 `MALFORMED_RESPONSE` 失败。适配器的 JSON 解析器不接受落单的半个代理对。合并拆开的代理对留到确有服务这样做时再加 |
| 规模约一万行，周期数周 | 每个阶段结束都能运行和演示 |
| PyPI 上的包名在发布之前可能被别人占用 | 2026-10-09 查询时 `columbina` 没有被占用，发行包名和导入名都用它。发布前再确认一次 |
| 本地小模型在手工任务上可能几乎全错 | 任务分难度档；先在 Qwen2.5-7B 上试跑，把难度调到可区分的范围 |
