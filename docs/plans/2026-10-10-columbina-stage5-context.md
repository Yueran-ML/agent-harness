# Columbina 第 5 阶段实施计划：上下文管理、恢复与分叉

**Goal:** 一个会话可以一直用下去。上下文快满时自动压缩，过大的工具结果存到盘上，模型有一份自己的待办清单。进程被杀之后，同一个会话可以接着用，也可以从它分出一个新的会话。

**Architecture:** 压缩是一个可选的接缝，默认提供者挂在循环已有的两个拦截点上：每一步开始之前按估算主动压缩，请求因上下文过长失败时被动压缩。压缩只做一件事，用一条摘要消息顶替消息面上最老的一段，原始事件留在日志里。估算、溢出存盘、结果上限、待办各是一个小插件，经已有的服务相连。

**Tech Stack:** 不增加运行依赖。

设计依据是 `docs/plans/2026-10-09-columbina-design.md` 的第 5.5、6.5、8.5、10、12.1、12.3 节。本计划与这些章节不一致的地方列在"与设计文档的差异"一节，阶段结束时把设计文档改成一致。

---

## 结束标志

设计文档 15.2 给本阶段的结束标志是两句话：长会话能自动压缩，进程被杀后能恢复。落到测试上是四条。

1. **脚本化的长会话。** 测试经 `columbina run` 的命令行运行，清单把上下文窗口设成一个很小的值。脚本化的模型连续调用工具，估算越过阈值，压缩在回合中途发生。之后的每个请求都只含系统提示、摘要、保留的尾部和重新追加的上下文。回合照常完成，结束原因是 `completed`。日志里有成对的 `compaction/start` 和 `compaction/end`。
2. **被动压缩。** 脚本化的模型对一次请求回答"上下文过长"。压缩之后同一步重发，第二次成功。消息面没有前进时不重发，回合以 `error` 结束。
3. **真实服务。** 同一段流程对 DeepSeek Flash 运行，窗口同样设小。摘要由真实模型写。压缩之后问模型一个只出现在被压缩段落里的事实，它答得出来。没有密钥时这条测试跳过。
4. **杀掉进程再续接。** 测试启动一个真实的 `columbina run` 子进程，等它运行到一条长命令的中途，用系统的手段杀掉它。再用同一个会话 id 启动一次。日志被修复：没有结果的调用补上 `TOOL_OUTCOME_UNKNOWN`，回合以 `interrupted` 结束。下一个回合里模型读到打断说明，任务完成。

## 范围

本阶段做的：token 估算，溢出存盘和它的本地提供者，工具结果的上限，命令完整输出的存盘，压缩的接缝和默认提供者（裁剪、摘要、主动触发、被动触发、手动触发），压缩之后上下文的重新追加，`Agent.run_maintenance`，待办工具，命令 `/compact`、`/todos`、`/fork`，子命令 `columbina sessions list|show|fork`，清单里的接线和 DeepSeek Flash 的窗口大小，状态行显示估算值，文档与记录。

本阶段不做的：图片的卸载，常驻的待办面板，子代理的分叉，会话的删除和改名，跨工作目录列出会话，溢出文件按容量清理。子代理的分叉随第 6 阶段的子代理加入。

## 先做的试验

写计划之前做了六个试验。第一、二、三、六个的对象是 DeepSeek 的真实接口，模型是 `deepseek-flash`，第四、五个只在本机运行。脚本留在草稿目录里。

**试验一：各类文本每个字符折合多少 token。** 每段文本单独作为一条用户消息发出，读取用量里的输入 token 数，再减去一条单字母消息的 31 个。

| 文本 | 字符数 | 每字符 token | 每 token 字符 |
|---|---|---|---|
| 英文说明文（README） | 17032 | 0.267 | 3.74 |
| Python 代码 | 20000 | 0.229 | 4.37 |
| 中文设计文档（ASCII 占 54%） | 20000 | 0.507 | 1.97 |
| 只有汉字和全角符号 | 10000 | 0.625 | 1.60 |
| 带转义的 JSON | 8842 | 0.268 | 3.72 |
| 文件路径，一行一个 | 5090 | 0.371 | 2.70 |
| 十六进制哈希与标题 | 12000 | 0.422 | 2.37 |
| pytest 的输出 | 20000 | 0.280 | 3.57 |

另外两个数：每多一条消息多 3 个 token，其中 2 个是消息本身的开销。声明工具有大约 210 个 token 的固定开销，之后每个字符的 JSON 约 0.27 个 token。

结论有三条。设计文档写的"ASCII 四个字符一个 token，中日韩文字每字一个 token"在这八段文本上的偏差从少估 41% 到多估 60%。ASCII 文本内部的差别很大，哈希和路径的密度是代码的近两倍，只用一个比率不够。汉字的实测值是每字 0.625 个 token，不是 1 个。

**试验二：上下文超长时服务怎么回答。** 发出一条 500 万字符的消息。

| 问题 | 结论 |
|---|---|
| 状态码和错误码 | HTTP 400，`type` 和 `code` 都是 `invalid_request_error`，不是 `context_length_exceeded` |
| 报错文字 | `This model's maximum context length is 1048576 tokens. However, you requested 1089775 tokens (1089774 in the messages, 1 in the completion).` |
| 适配器认不认得 | 认得。它按文字里的 `context length` 归为 `CONTEXT_WINDOW_EXCEEDED` |
| 窗口有多大 | 1048576 个 token，服务自己在报错里说的 |
| 窗口管的是什么 | 输入加上请求里的 `max_tokens`。请求不带 `max_tokens` 时，报错里写的是"0 in the completion"，服务不为回复预留位置 |
| 拒绝要多久 | 3.4 秒，主要是上传 |
| 贴近窗口的请求 | 一条 102 万 token 的请求被接受，22.8 秒后返回。这一次请求花了约 0.15 美元，不再重复 |

报错里同时给出窗口大小和这次请求要了多少。被动压缩可以把这两个数读出来，知道至少要减掉多少。

**试验三：估算怎样计价。** 把试验一扩到 21 段文本，加上了测试代码、带长文档串的代码、数字表、不带空格的数字 JSON、锁文件、YAML、`git log` 和 `git diff` 的输出、base64、缩进很深的 YAML。四种计价办法在这 21 段上的偏差如下。

| 办法 | 平均偏差 | 最大偏差 |
|---|---|---|
| ASCII 四个字符一个 token，宽字符每字一个 | 23.2% | 64.3%，base64 |
| ASCII 一个比率，宽字符一个比率，最小二乘拟合 | 21.0% | 54.3% |
| 字母、数字、空白、符号、宽字符各一个比率，最小二乘拟合 | 10.1% | 36.3% |
| 空白、数字、长串里的字母、其余 ASCII、宽字符各一个比率，在网格上搜 | 6.2% | 15.4% |

第三种办法不稳：符号和数字在多数文本里一起出现，拟合出的比率互相抵消，留出一段文本再拟合时，那一段的估算最多偏到 97%。第四种办法在这 21 段上最好，写计划时选的就是它。

任务 1 执行时拿另外八段文本验证了这张表，它们没有参与选表：一段英文叙事，一段代码，一段中文，中文夹代码，逐行的 JSON，哈希，一张对齐的数字表，一组路径。结果是平均偏差 15.5%，最大 29.3%。英文叙事估高了 27%，JSON 估低了 29%，数字表估低了 27%。原因是符号比字母贵得多，而这张表给两者同一个比率。

于是把符号和字母分开，在全部 28 段文本上重新搜了一遍。有一段文本取自后来改过的文件，没有再用。

| 字符 | 每字符 token |
|---|---|
| ASCII 的空白 | 0.15 |
| ASCII 的数字 | 0.50 |
| ASCII 的字母 | 0.24 |
| 连续 24 个以上字母数字里的字母，例如哈希和 base64 | 0.85 |
| 其余的 ASCII 字符，也就是符号 | 0.70 |
| 东亚的宽字符 | 0.62 |
| 其他字符 | 0.50，没有实测 |

这张表在 28 段文本上的平均偏差是 7.1%，最大 19.2%。每段文本改用不含它自己时选出的比率来估，平均偏差是 9.6%，最大 30.0%。后一组数更接近它对没见过的文本的表现。剩下的偏差由设计决定第 1 条里的实测比例来补。

**试验四：模型能不能读到存在工作目录之外的文件。** 溢出文件放在程序的数据目录里，不在工作目录里。试验加载了会话、工具、文件系统接缝、沙箱、审批、权限和四个文件工具，不调模型。

| 做法 | 结果 |
|---|---|
| 不加授权，`read` 或 `grep` 这个文件 | 拒绝，`OUTSIDE_WORKING_DIRECTORY` |
| 在接缝上登记一条授权：读这个工作目录的溢出目录 | `read` 可以读，带 `offset` 和 `limit` 也可以。`grep` 和 `glob` 对文件和目录都可以 |
| 有授权之后往里写 | 拒绝 |
| 有授权之后读另一个工作目录的溢出文件 | 拒绝 |

规则和沙箱都不拦这条读。一条授权就够，不需要改工具。

**试验五：杀掉正在运行命令的进程，再续接。** 模型是脚本化的。第一次运行让它执行一条会睡两分钟的命令，命令启动之后用系统的接口强行结束 `columbina run`。再用同一个会话 id 给一个新任务。试验在 Windows 上做。

| 问题 | 结果 |
|---|---|
| 命令是否随程序结束 | 是，半秒之内就不在了。Windows 上命令在作业对象里，程序一死作业就关闭 |
| 会话的锁是否释放 | 是。`lock` 文件还在，系统的锁随进程释放，第二次运行可以打开会话 |
| 日志是否完整 | 是，最后一行有换行符。这一次没有碰上写到一半的行 |
| 第二次运行写下了什么 | `session/end-seed`，一条 `TOOL_OUTCOME_UNKNOWN` 的工具结果，`step/end`，`turn/end` 原因是 `interrupted`，新回合里有打断说明，回合以 `completed` 结束 |
| 第二次运行的退出码 | 0 |

第 2 到第 4 阶段的代码已经让这条路走得通，本阶段要做的是把它固定成一条测试。POSIX 上命令在自己的进程组里，程序被强行结束时命令不会跟着结束，测试在那里只断言续接，并自己清理留下的命令。

**试验六：摘要请求怎样发才能用上缓存。** 先把一段带五个工具声明的对话发两次，让它的前缀进入服务的缓存。再在这段对话后面加一条要求写交接说明的指令，用三种办法发出。对话的最后一句是让模型去读一个文件，这是有意留下的诱因。

| 发法 | 输入 token | 其中来自缓存 | 回复 |
|---|---|---|---|
| 对话本身，第二次 | 3879 | 3712 | |
| 带工具声明，加 `tool_choice: none` | 3405 | 0 | 文字，没有工具调用 |
| 带工具声明，不加别的 | 3922 | 3712 | 文字，没有工具调用 |
| 不带工具声明 | 3405 | 3200，来自上面第二种发法刚建的缓存 | 文字 |

结论有三条。加上 `tool_choice: none` 时，服务把工具声明从提示里整个拿掉：输入 token 数与不带工具声明时相同，对话的前缀也就对不上，缓存一个 token 也没有命中。带着工具声明、只在指令里写明不要调用工具时，前缀照常命中，模型在这一次试验里也确实只回了文字。不带工具声明的两种发法里，回复都以"我读不了这个文件"开头，带着工具声明的那一次直接从交接说明写起。

所以摘要请求带着与上一次请求相同的工具声明，不设 `tool_choice`。一次试验不能保证模型永远不调工具，回复里没有文字时不带工具声明再发一次。

试验到此做完，执行阶段没有留下要先回答的问题。

## 设计决定

**1. token 估算按字符的类别计价，再用会话自己的实测比例校正。** 估算不调模型。文本按试验三的那张表计价：空白、数字、字母、长串字母数字里的字母、符号、东亚的宽字符、其他字符，各一个比率。每条消息另加 3 个 token。声明了工具时另加 210 个，工具声明的 JSON 按同一张表计价。最近一次成功的请求报告了用量，并且它用的提供方和模型与当前相同时，取"报告的输入 token 数除以当时的估算值"作为这个会话的比例，当前的估算值乘上它。比例落在 0.5 到 2 之外时不采信。理由：静态的比率免不了偏差，同一个会话里文本的构成相对稳定，实测比例正好补上这一段。压缩替换了一段历史之后，这个算法不需要特殊处理。参考实现用"基线加增量"，压缩之后基线失效。

**2. 主动压缩的阈值是 `floor(min(W×0.8, W−O−B))`。** `W` 是调用配置里的上下文窗口。`O` 是调用配置里的输出上限，没有配置时取 0，依据是试验二：服务只在请求给出 `max_tokens` 时才为回复留位置。`B = min(65536, W×0.25)`，同时也是摘要请求的输出上限。`W` 没有配置时不做主动压缩，日志里说明一次。

**3. 清单给 DeepSeek Flash 写明窗口是 1048576。** 这个数取自服务的报错，不取自第三方的介绍。用户换模型时用 `--patch` 或环境变量改它。

**4. 压缩只在两个地方发生。** 一是每一步开始之前，这时上一步的结果已经全部写进日志，调用和结果是配平的。二是 Agent 空闲时的手动压缩。回合中途别的时刻不压缩。理由：压缩要读写消息面，这两个时刻之外消息面可能正在变。

**5. 先裁剪，后摘要。** 阈值越过之后，先把消息面上超过 8192 个字符的旧工具结果换成开头 4096 加结尾 1024 个字符，中间写明省略了多少。裁完重新估算，回到阈值以下就不调模型。模型还没读过的结果不裁，也就是消息面上最后一条助手消息之后的工具结果。参考实现没有这条豁免，刚拿到的结果会在模型读到之前被裁掉。

**6. 被压缩的是最老的一段，保留的是最新的一段。** 选区从第一个非系统节点开始。保留的尾部从最新的节点往回数，凑够 `(W−O)×16%` 个 token，边界再往回挪到调用与结果配平的位置。最后一条由人写的消息（来源是 `user` 或 `steer`）总在保留的尾部里，除非从它开始的尾部超过窗口的一半。理由：当前的任务是用户的原话，不应该只剩转述。参考实现在被动和手动两条路上只保留最后一个节点。

**7. 摘要请求原样回放被压缩的一段。** 请求由系统提示、选区里的消息、一条压缩指令组成，工具声明与上一次请求相同。这样请求的前缀与上一次对话请求逐字节相同，服务的前缀缓存可以命中，试验六里命中了 3922 个输入 token 中的 3712 个。请求不设 `tool_choice`：试验六表明服务会因此拿掉工具声明，缓存随之失效。指令里写明不要调用工具。回复里没有文字时，不带工具声明再试一次。输出上限是 `B`。

**8. 压缩指令要一份交接说明。** 四个部分：进展与决定，约束与偏好，剩余的步骤，关键数据。要求有五条：路径、命令、报错原文、数字和标识符照抄；用户纠正过的地方如实写下；用对话所用的语言写；不提压缩这件事，不调用工具；选区里已有一份早先的摘要时，把它并进来，不整段照抄。

**9. 模型看到的是一条用户角色的消息。** 它的来源是 `compaction`。开头一句话说明这是早先对话的摘要，供参考，不需要回应。摘要放在 `<summary>` 和 `</summary>` 之间，文字里出现的结束标签被拆开，办法与上下文消息相同。

**10. 日志里的顺序是 `compaction/start`、`compaction/summary`、顶替的 `user/message`、`compaction/end`。** 只裁剪时没有中间两条。顶替的那条消息是唯一改动消息面的事件，它写下去压缩才算发生。进程死在它之前，消息面没有变，日志里留下一条没有结尾的 `compaction/start`。续接时写下的 `session/end-seed` 之前的孤儿一律不算数。压缩是否正在进行记在内存里，不靠扫描日志。

**11. 失败不拖累回合。** 摘要请求失败、被取消，或者摘要不比原文短，这次压缩作废，写 `compaction/end` 并带上原因。主动压缩失败时回合照常继续。连续失败两次之后，这个会话不再尝试主动压缩，直到有一次请求成功。被动压缩失败时原来的错误照常上报。摘要请求遇到可重试的错误时重试一次。摘要请求自己超出窗口时，丢掉选区里最老的一半再试，丢掉的部分只留在日志里。参考实现在这三处都没有处理。

**12. 被动压缩只在消息面前进时授权重发。** 监听 `agent/request-error`，只认 `CONTEXT_WINDOW_EXCEEDED`。每一步最多一次。报错文字里有窗口大小和请求大小时读出来，据此决定至少裁掉多少。

**13. 压缩之后，被遮蔽的上下文在同一个请求之前补上。** 会话记下消息面被顶替的次数。循环在发每个请求之前比较这个次数，变了就把登记的上下文来源重新问一遍，`note` 类的除外。一个来源上一次给出的消息已经不在消息面上时，即使文字没有变也重写一遍。这条规则同时覆盖主动和被动两条路。参考实现要等到下一步。

**14. 手动压缩走 `Agent.run_maintenance`。** 它只在 Agent 空闲时接受一件事，由驱动任务执行，执行期间到来的输入排在它后面。Agent 在忙时它立刻拒绝，不排队。`cancel()` 能停下它。`/compact` 就是经它调用压缩。

**15. 溢出存盘是一个接缝，两个方法。** `save_text` 存一段文字，`open` 给出一个可以边到边写的文件。本地提供者写到 `<COLUMBINA_HOME>/spill/<工作目录的键>/<会话 id>/`，文件名是八位随机的十六进制数加上调用方给的名字，独占创建，POSIX 上目录和文件只有属主可以访问。提供者在文件系统接缝上登记一条授权：读这个工作目录的溢出目录是允许的。启动时清一次超过三十天的文件，不跟随链接。`save_text` 把超过 2000 个字符的行折开，否则 `read` 读不到一行的后半段。

**16. 工具结果有一个上限，12500 个 token。** 一个 `tools/post-execute` 监听器按第 1 条的估算量结果的文字。超出时把全文存盘，交给模型的是开头、一行省略说明、结尾和一句结尾的话。那句话写明全文有多少字节、存在哪里、怎样读。工具可以声明自己的结果是分页的，`read` 是这样，上限不管它。存盘失败时仍然截短，并如实说明全文没有保住。

**17. 命令的完整输出边到边写进溢出文件。** 输出超过内存里保留的 64000 字节时才打开文件，先写下已经到的部分，之后每到一段写一段，最多 64 MiB。命令工具的返回值带着这个文件的位置，结果上限用它，不再另存一份。屏幕上和模型读到的仍然是开头和结尾。

**18. 待办清单是模型自己的记事。** 工具 `todo_write` 每次整体替换清单，每项有内容和状态，状态是 `pending`、`in_progress`、`completed` 之一，同一时刻最多一项在进行。清单存成 `todo/write` 事件，读日志的程序可以略过它。工具的结果是三种状态各有几项。清单跨回合保留。写下清单的那次调用被压缩遮蔽之后，待办插件作为上下文来源把清单重新告诉模型。终端里清单变化时印出来，`/todos` 随时可以看。

**19. 分叉从最后一个完整的回合切。** `/fork` 在 Agent 空闲时执行：复制当前会话到最后一个 `turn/end` 为止，开一个新会话，前端换到新会话上，原会话保持原样。`columbina sessions fork ID` 做同样的事，不进入对话，印出新会话的 id。`sessions list` 列出这个工作目录的会话，`sessions show ID` 印出一个会话每个回合的输入和回答的末尾。这三个子命令只加载会话插件，不需要模型。

**20. 状态行显示估算值。** 有估算服务时，状态行写的是当前消息面的估算和它占窗口的比例，不再是上一次请求的输入 token 数。压缩刚发生之后这个数会降下来，用户看得到。

## 与设计文档的差异

1. 估算的比率不是"ASCII 四个字符一个 token，中日韩文字每字一个 token"，而是按字符类别拟合的一张表，见设计决定第 1 条和试验一。
2. 用量锚点的用法不是"基线加增量"，而是会话的实测比例。
3. 结果上限在存盘失败时仍然截短。设计文档 8.5 节写的是保留原文。
4. 溢出目录按工作目录和会话 id 分层，不用会话 id 的哈希。
5. 溢出存盘有第二个方法 `open`，用来写命令的完整输出。
6. 保留的尾部总含最后一条由人写的消息。
7. 待办清单跨回合保留，同一时刻最多一项在进行。
8. `sessions show` 和 `sessions fork` 的具体行为，设计文档没有写。

### `columbina.token_meter`（新建，插件 `token-meter`）

```python
def estimate(text: str) -> int                      # 一段文字折合多少 token
def estimate_message(message: Message) -> int        # 一条消息，含块和角色的开销
def estimate_tools(tools: Sequence[ToolSchema]) -> int

@dataclass(frozen=True)
class Measure:
    tokens: int            # 估算值，已按实测比例校正
    estimated: int         # 校正之前的估算值
    ratio: float | None    # 采信的实测比例，没有时为 None

class TokenMeter:
    def measure(self, session: Session) -> Measure   # 当前消息面加上工具声明

TOKEN_METER = ServiceKey[TokenMeter]("token-meter")
```

每个会话有一本账，随事件增量维护：消息面上每个节点的估算值，它们的和，最近一次可用的用量和当时的估算值。账按 `seq` 记，事件不可变，所以只算一次。
