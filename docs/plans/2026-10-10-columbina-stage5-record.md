## 状态

本阶段的代码已经完成。设计文档给本阶段的结束标志是两句话：长会话能自动压缩，进程被杀后能恢复。计划把它落成四条测试，四条都已通过。前三条和第四条的续接部分经 `columbina run` 的命令行和随包发布的清单运行。

**1. 脚本化的长会话。** `tests/apps/test_a_long_session.py` 把模型的窗口设成 15000 个 token。脚本化的模型先写下待办清单，再一个接一个地读文件。读完第五个文件，对话的估算值越过了可用的 11250 个 token。下一步开始之前，最老的一段被摘要顶替：用户的任务、待办清单和前三个文件，共九条消息。最后读的两个文件原样保留。之后的请求只含系统提示、运行时上下文、摘要、保留的两次调用和重新告诉模型的待办清单。模型接着读完第六个文件，回合以 `completed` 结束。

**2. 被动压缩。** 同一个文件里的第二条测试不给模型配置窗口。模型对一次请求回答"上下文过长"，报错里写着窗口是 5000、请求是 5600。压缩按这两个数去掉任务和第一个文件，同一步重发，第二次成功。第三条测试里对话只有一条任务，没有可以去掉的内容，请求不重发，回合以 `error` 结束，退出码为 1。

**3. 真实服务。** `tests/live/test_deepseek_compaction.py` 把窗口设成 15000，分八个回合各给 DeepSeek Flash 一段约 1700 个 token 的笔记，每段笔记的第一行有一个人名。2026-10-10 的一次运行里，对话在第五个回合越过了可用的部分，最早的九条消息被模型自己写的摘要顶替，估算值从 11827 降到 6711，摘要有 2849 个字符。第八个回合又压缩了一次，估算值从 12488 降到 7002。整次运行发了 12 个请求，其中 2 个是摘要请求，合计输入 22147 个 token、输出 2055 个，另有 67328 个取自服务的缓存。 之后问第一段笔记里的人名，这时那段笔记已经不在发给模型的消息里。模型没有调用工具，答出了那个名字。同一个文件里的另一条测试用 65536 的输出上限发了一次请求，服务照常回答，这是窗口为 1048576 时摘要请求会用的上限。

**4. 杀掉进程再续接。** `tests/apps/test_a_killed_run_is_taken_up.py` 启动一个真实的 `columbina run` 子进程。脚本化的模型让它执行一条会睡两分钟的命令。命令开始之后，测试用系统的手段杀掉这个进程。日志停在一条没有结果的 `tool/call` 上。第二次运行用同一个会话 id：日志先被修复，那次调用得到一条 `TOOL_OUTCOME_UNKNOWN` 的结果，步和回合被关闭，回合的结束原因是 `interrupted`。新回合里模型先读到打断说明，再读到新任务，回合以 `completed` 结束，退出码为 0。在 Windows 上测试还断言那条命令随程序一起结束。

## 做出来的东西

**估算。** `columbina.token_meter` 不调模型就给出一个会话现在折合多少 token。比率来自对真实接口的 28 段实测文本。每个会话有一本账，随事件增量维护。

**溢出存盘与结果上限。** `columbina.spill` 是接缝，`columbina.spill.local` 把文字和字节流写到程序的数据目录里，`columbina.spill.policy` 把超过 12500 个 token 的工具结果换成头尾预览，并写明全文在哪里。命令工具的输出超过内存里保留的 64000 字节时，完整的输出边到边写进溢出文件。

**压缩。** `columbina.compaction` 是接缝，`columbina.compaction.basic` 是默认的提供者。它在每一步开始之前检查对话的大小，在模型拒绝请求之后被动地压缩一次，也接受用户的要求。它先裁剪模型读过的超长结果，不够时请模型写一份交接说明，用它顶替最老的一段。日志里的事件一条也不删，变的只是发给模型的那一面。

**上下文的补写。** 压缩把一段对话换成摘要之后，站在那一段里的上下文消息不再被模型看到。循环在发每个请求之前检查这一点，把被遮蔽的来源重新问一遍。

**回合之间的工作。** `Agent.run_maintenance` 让一件要读写对话的事在两个回合之间执行，执行期间到来的输入排在它后面，`cancel()` 能停下它。手动压缩走这条路。

**待办清单。** 工具 `todo_write` 每次整体替换清单。清单存在日志里，跨回合保留，在终端里随写随显示。写下它的那次调用被摘要顶替之后，清单作为上下文重新告诉模型。

**分叉与会话子命令。** `/fork` 让对话转到当前会话的一份副本上。`columbina sessions list|show|fork` 不进对话就能列出、查看和复制存着的会话，不需要模型。

**清单与界面。** 随包发布的 `base` 清单加载上面这些插件，两个前端写明模型的窗口。状态行显示估算值，终端在压缩开始和结束时各印一行。

## 与计划的出入

出入都在实施时写回了计划，这里只列条目。

1. 裁剪和摘要的先后。计划是一律先裁剪后摘要。实现是先算裁剪能省多少，够用就只裁剪，不够时对原样的选区做摘要，之后需要再裁剪。原因是这样摘要请求的开头与上一次请求相同，服务的缓存能命中。
2. 连续失败之后何时恢复。计划是下一次对话请求成功就恢复主动压缩。那样每走一步都会再失败两次，实现改成等到有一次压缩成功。
3. `/fork` 复制整个日志，不切在最后一个 `turn/end`。原因见计划的设计决定第 19 条。
4. 核心事件多了一种，`request/aside`，记对话之外的请求的用量。此前摘要的花费不在任何合计里。
5. 命令输出的存盘上限从 64 MiB 减了 64 KiB，给存盘时折行多出的换行符留位置。
6. 换会话的能力是一个服务 `SWITCH`，不是命令服务上的一个属性。
7. 会话子命令加载清单里的 `session` 和 `agent` 两项，不只是会话插件。收件箱事件由后者声明，读日志的程序不能略过它。
8. 状态行的估算值前面有一个 `~`。终端在压缩开始和结束时各印一行，计划里没有写这一条。
9. 计划之外做了桌面应用的协议文档，是应作者的要求提前做的。

## 实施中找到的问题

**持续集成找到的。** 溢出目录应当只有属主可以访问。`Path.mkdir(mode, parents=True)` 只把权限给最末一层目录，上面两层用的是默认权限。这条断言只在 POSIX 上运行，本机是 Windows，它在第一次推送之后才在 Linux 和 macOS 上失败。修复是三层目录逐层创建。同时补了一条在每个平台都运行的测试，它记录程序向系统请求的权限。此后凡是只在 POSIX 上成立的行为，都配一条不依赖平台的测试。

**闸门自己的问题。** 会话重启之后，密钥出现在运行闸门的环境里，闸门因此调用了真实服务，花费估计不到 0.02 美元。闸门改成运行测试时去掉这个环境变量，真实接口测试要显式要求才运行。

**变异检查找到的。** Codex 的意见修完之后，对压缩那一组做了完整的变异检查，有两个变异体没有被发现。一个指出裁剪代码里有一个条件被说了两遍，删掉了。另一个指出一条保护没有测试能看见，补了测试。Agent 服务里"副本建好之后循环建不出来"的清理原本也没有测试看得见，同样补上了。

**覆盖率报告找到的。** 回合之间的工作有两种结束方式没有测试走到：工作进行中驱动任务被停下，以及发起者不再等待之后工作抛出异常。各补了一条测试和一个变异体。

**端到端测试找到的。** 窗口很小时主动压缩可能无从下手，见计划的"实施中的发现"第 3 条和"已知的限制"。`columbina sessions show` 在会话没有任何回合时会崩溃，发现于它的第一轮测试，已修。

## 已知的限制

1. **窗口很小时主动压缩可能无从下手。** 系统提示和工具声明合计约两千个 token。窗口只有这个数的三四倍时，对话可以已经越过阈值，而按规则没有可以去掉的内容。这时主动压缩失败，等模型拒绝请求时由被动压缩接手。DeepSeek Flash 的窗口是 1048576，不受影响。第 8 阶段用本地模型时要回头处理。
2. **`--model` 和 `/model` 只换模型的名字。** 窗口照清单里的不变。换成窗口更小的模型时要用 `COLUMBINA_CONTEXT_WINDOW` 给出它的窗口，否则第一次超长的请求会先被服务拒绝一次。
3. **建到一半的副本会留下来。** 分叉先写副本再创建 Agent。Agent 创建失败时副本已经在磁盘上，它是一份完整的会话，可以照常续接。
4. **会话子命令只认识两个插件的事件。** 别的插件将来如果声明了不可略过的事件，`sessions show` 和 `sessions fork` 读不了含有这种事件的会话。
5. **无界面的 JSON 输出不报告压缩和待办清单。** 这两样只在会话日志里。
6. **溢出文件只按存放时间清理。** 没有按容量清理。
7. **桌面应用的服务进程还没有实现。** 协议文档描述的事件是已经实现的，请求和通知要等第 10 阶段。

## 桌面应用的协议

本阶段进行中，作者决定终端之后的前端是桌面应用，不是网页，并要求先把协议写出来，让界面可以提前开发。技术栈按"哪个能做得更好看"选了 Electron，界面用网页技术写，Columbina 作为子进程运行，三者之间走标准输入输出上的 JSON-RPC。

`docs/protocol/` 里有三样东西。`README.md` 规定消息和界面必须遵守的规则。`events.schema.json` 是全部事件的 JSON Schema，由代码导出。`samples/tour.jsonl` 是一份样例会话，由真实的 Agent 循环跑出来，每种事件至少出现一次。三样都有测试看着：代码里新增一种事件，文档的表、Schema 和样例没有跟上，测试就失败。本阶段后来加的 `todo/write` 就是这样被要求补进去的。

服务进程本身属于第 10 阶段。

**留给作者的检查。** 下面这些要在真实的终端里做，测试替代不了。

1. 开一段对话，让 Agent 连续读几个大文件。看状态行的 token 数随着增长，前面带着 `~`。
2. 把窗口设小再试一次，例如 `COLUMBINA_CONTEXT_WINDOW=20000`。看到一行"对话接近模型的上限"，压缩结束后看到一行结果，状态行的数字降下来，对话照常继续。
3. 在对话里用一次 `/compact`。压缩期间输入行上方有提示，状态行写着 Esc 可以停止，结束后命令回答压缩前后的 token 数。再用一次，这次在压缩期间按 Esc，命令回答它被停下了，对话没有变化。
4. 让 Agent 做一件分几步的事。看它写下的待办清单显示在对话里，用 `/todos` 再看一次。
5. 用一次 `/fork`。屏幕上先出现副本里最后一个回合的摘要，再出现两个会话的 id。退出后用 `columbina sessions list` 看到两个会话，用 `--session-id` 能分别接上。
6. 用 `columbina sessions show ID` 看一个会话，用 `columbina sessions fork ID` 复制一个。
7. 让 Agent 运行一条耗时很长的命令，在任务管理器里结束 `columbina` 进程。再用 `columbina --continue` 接上，看到上一个回合的摘要，问它刚才发生了什么。
8. 让 Agent 运行一条输出很长的命令，例如列出一个大目录。结果的末尾写着完整输出存在哪个文件里，让它去读那个文件的某一段。
