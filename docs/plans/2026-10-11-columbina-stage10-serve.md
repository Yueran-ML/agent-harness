# Columbina 第 10 阶段实施计划（上）：服务进程

**Goal:** 别的程序可以经标准输入输出驱动 Columbina。`columbina serve` 按 [`docs/protocol/README.md`](../protocol/README.md) 的协议版本 1 说话：界面发请求，服务进程回答，并把会话里发生的事作为通知送出去。桌面应用接上它之后，显示的就是真实的 Agent。

**Architecture:** 服务进程是又一个前端，与终端界面和一次性运行并列，装在同一套插件上。它分三层，每层可以单独测试。最里面是一行文字与一条 JSON-RPC 消息之间的转换，是纯函数。中间是 `Server`，持有一段对话的状态，处理请求，发出通知和提问，它对外只认两样东西：收到的行，和发出一行的办法。最外面是真实进程的标准输入输出，由两个线程读写，不挡住事件循环。

**Tech Stack:** 不增加依赖。JSON 用标准库，参数检查用 pydantic。

设计依据是协议文档的第 2 到 6 节，以及设计文档第 15.2 节的第 10 阶段。这个阶段原本排在最后，2026-10-11 作者要求把交互的工作提前，并且先打通服务进程。本计划只管服务进程。桌面应用的界面是另一份计划。本计划与协议文档不一致的地方列在"与协议文档的差异"一节，实现时把协议文档改成一致。

## 先做的试验

**试验：一个进程能不能把自己的标准输入输出收归己用。** 协议要求标准输出上只有协议消息。插件是别人写的，其中任何一处 `print`，或者任何一个继承了标准输出的子进程，都会在协议的行中间插进别的字。反过来，一个继承了标准输入的子进程会把本该给服务进程的请求读走。

试验的做法是：进程启动时复制出标准输入和标准输出的两个私有描述符，然后把标准错误放到标准输出的位置上，把空设备放到标准输入的位置上。之后协议只走那两个私有描述符。试验在本机的 Windows 上运行，子进程是一个 Python 程序。

| 情形 | 结果 |
|---|---|
| `print`、直接写 1 号描述符、启动一个继承标准输出的程序 | 三者的输出都到了标准错误，标准输出上没有多出一个字 |
| 启动一个读标准输入的程序 | 它立刻读到结束，用时 0.06 秒，没有读走给服务进程的内容 |
| 读入一行 3 MB，写出一行 2 MB | 完整到达 |
| 读的线程用 `os.read`，写的线程用 `os.write` | 正常 |
| 读的线程还在等输入时进程退出 | 退出码 0，没有报错 |
| 对方关闭它那一端 | 读的线程立刻读到结束，进程退出，退出码 0 |

结论：这个做法在 Windows 上可行。POSIX 上 `dup2` 的语义是标准的，由 CI 上的测试覆盖。读的线程不用带缓冲的文件对象：解释器退出时，一个被别的线程占着的缓冲读对象会让解释器报致命错误，这在标准输入上是已知的问题。

## 设计决定

### 进程与传输

**1. 一个进程，一个工作目录，同一时刻一个打开的会话。** 这是协议第 1 节定下的。工作目录来自命令行的 `--cwd`，缺省是进程的当前目录。

**2. 标准输入输出归协议所有。** 做法见上面的试验。标准输出被换成标准错误之后，`sys.stdout` 也指向标准错误。标准错误不能用时，1 号描述符换成空设备。这一步只在真实的进程里做。测试里的 `Server` 用内存里的队列，不碰描述符。

**3. 读和写各用一个线程。** 读的线程用 `os.read` 取字节，自己按换行切成行，经 `call_soon_threadsafe` 交给事件循环。写的线程从一个队列里取行写出去。这样对方读得慢的时候，事件循环不会卡在写上，`session/cancel` 仍然来得及处理。两个线程都是守护线程。进程退出时，写的线程最多等 5 秒把队列写完。写失败说明对方已经不在了，按关闭标准输入处理。

**4. 行的规则。** 每条消息一行，UTF-8，以 `\n` 结束，行尾的 `\r` 去掉。只有空白的行跳过，不回答。一行超过 16 MiB 时，这一行被丢弃，回答一条 `id` 为 `null` 的错误 -32600。不是合法 UTF-8 或不是合法 JSON 的行，回答 -32700。

**5. 发出的 JSON。** 事件的那一段直接用会话文件里的那一行，不重新编码，所以界面收到的事件与文件里的逐字节相同。其余的用标准库编码，不转义非 ASCII 字符。一行编不成 UTF-8 时（文字里有落单的代理字符），改用全部转义的写法再编一次，不丢消息。

**6. 请求按到达的顺序办，慢的请求不挡路。** 读到一行就地办完再读下一行，所以连着发来的 `session/prompt` 和 `session/steer` 不会颠倒。`session/command` 和 `session/list` 可能要花时间，各起一个任务去办。这样 `/compact` 进行中，`session/cancel` 和审批的回答照样被处理。协议允许回答的顺序与请求的顺序不同。

**7. 握手。** `initialize` 之前，除了 `shutdown`，任何请求都回答 1000。第二次 `initialize` 也回答 1000。结果里的协议版本是 1 与界面给的版本中较小的那个，界面给的版本小于 1 时回答 -32602。`client` 只写进日志。

**8. 参数的检查。** 每个方法的参数是一个 pydantic 模型。不认识的字段忽略，因为协议只增不改，新的界面可能多带字段。缺字段或类型不对时回答 -32602，`message` 说明是哪一个字段。`params` 可以省略，给出时必须是对象。请求的 `id` 接受字符串和整数。界面发来的通知（没有 `id` 的消息）现在没有定义，一律忽略。

**9. 内部出错。** 处理一个请求时出了没有料到的错，回答 -32603，`message` 是一句不带内部细节的话，完整的错误写进日志。进程继续运行。

### 会话

**10. `session/open` 先打开新的，再结束当前的。** 新会话打不开时，当前的会话保持打开，界面只需要显示一句话。先检查 id 是否合法，不合法回答 -32602。读不出来或者被别的进程占着，回答 1002。重新打开当前正开着的那个会话是例外：它只能先结束再打开。

**11. `session/open` 的回答先于新会话的任何通知。** 结果里的 `events` 是那一刻日志的长度 N，编号不小于 N 的事件都作为通知送出，不重不漏。做法是：Agent 建好之后，记下 N，挂上监听，立刻把回答写出去，这几步之间不让出事件循环。然后发一条 `session.status`，最后才去结束旧的 Agent。旧会话在结束过程中写下的事件不再送出。

**12. `session/events` 的一页有大小的上限。** 除了 `limit`，一页里事件的总长度超过 4 MiB 就不再往里放，至少放一条。`from` 超过日志的长度时，结果是空的，`next` 为 `null`。`limit` 大于 500 时按 500 算，小于 1 时回答 -32602。

**13. `session/list` 不需要有会话打开。** 它列的是工作目录下存着的会话，子代理的会话不在其中。

### 回合

**14. 状态只有一个来源。** `session.status` 的内容由一个函数从当前的状态算出来，每当可能变了就算一次，与上次发出的不同才发。可能变的时刻有：打开会话之后，交了任务或转向之后，每条事件之后，换了模型之后，Agent 回到空闲时，Agent 停止时。状态说的是 Agent 处在什么状态，一条命令是否正在执行不在其中，理由见"实施中的发现"。

**15. `idle` 以 Agent 自己说的为准。** 一个回合结束不等于空闲，后面可能还排着任务。所以 `turn/end` 不直接把状态变成 `idle`。服务进程在每次状态变成 `running` 时确保有一个任务在等 `agent.when_idle()`，它回来了才是 `idle`。它抛出异常说明 Agent 已经停止，状态变成 `stopped`，`detail` 是原因，此后的 `session/prompt`、`session/steer`、`session/command` 回答 1004。

**16. `session/cancel` 立刻返回。** 它停下回合，也停下正在进行的命令所占用的 Agent 的工作。等待中的输入一并丢弃。没有东西在运行时什么也不做。

**17. 模型可以换。** 服务进程像终端界面一样登记 `/model` 命令，并在每次请求模型之前换上用户最后指定的模型。换了之后 `session.status` 里的 `model` 随之变化。`/exit`、`/new` 和 `/fork` 不提供：退出用 `shutdown`，新会话用 `session/open`，分叉时怎样通知界面协议还没有定。

### 审批

**18. 提问是服务进程发出的请求。** `id` 从 1 起编号。回答的 `outcome` 是 `allowed-once` 才放行。回答是错误、形状不对、或者是别的值，都按 `rejected` 处理。`remember` 为真，而且这次提问的 `standing` 不为 `null`，就把这个调用记为本次运行期间不再询问，做法与终端界面按 `a` 键相同。没有权限插件时 `standing` 一律为 `null`。

**19. 提问被撤回时，服务进程不再等。** 回合被停下，等待中的提问随之作废，日志里出现 `approval/decided`，结果是 `cancelled`。这之后才到的回答对不上任何提问，被忽略，不算错误。

### 结束

**20. `shutdown` 和关闭标准输入做同一件事。** 停下正在进行的命令和回合，结束 Agent，把收尾写进日志。`shutdown` 在这之后回答，再退出。退出码是 0。收尾写不进日志时退出码是 1，原因写在标准错误里。

## 实施中的发现

**Agent 多了一个属性 `at_rest`。** 状态里的 `idle` 和 `running` 需要随时知道 Agent 是不是空闲，而此前只有 `when_idle()` 可以等。从发给 Agent 的东西和它写下的事件去推算会有空档：一个刚交了任务还没有开回合的 Agent 已经不空闲了。所以 `Agent` 的接口加了只读属性 `at_rest`，循环里就是那个空闲事件有没有被置位。已经停止的 Agent 也算 `at_rest`，它停止了这件事只有 `when_idle()` 会说。

**会话多了一个属性 `created_at`。** 协议里 `session/open` 的回答有这一项，此前这个时刻只在会话文件的头里。现在 `Session` 自己带着：新建时是创建的时刻，接着旧会话时是文件头里的时刻，分叉出来的副本是做副本的时刻。直接构造 `Session` 而不给这一项时，取系统的时钟，不动传进来的那个时钟。测试里的时钟是数着事件走的，多问它一次，事件的时间就全错开了。

**状态说的是 Agent，不是这个程序在忙什么。** 计划第 14 条原想在命令开始和结束时各看一次状态。实现时发现这样做，`/help` 这样立刻执行完的命令也会让状态从 `idle` 跳到 `running` 再跳回来，界面上的停止按钮会跟着闪一下。现在状态只看 `Agent.at_rest`：让 Agent 做事的命令（`/compact`）在 Agent 写下第一条事件时变成 `running`，立刻执行完的命令不引起任何通知。同一时刻只执行一条命令这件事仍然成立，第二条被拒绝，错误码 1003。有一个已知的空档：一条命令让 Agent 做事，却一条事件都不写，状态要到下一条事件才更新。现有的命令没有这样的。

**只转发打开的那个会话自己的东西。** 内核的规则是：在一个作用域里登记的监听器，除了听到本作用域里的事件，还听到所有作用域之外发出的事件。所以挂在 Agent 作用域上的监听器会听到别的会话的事件，只要那个会话建在根上。服务进程因此在转发处按会话核对：事件要是这个 Agent 的会话的，流式片段要是这个 Agent 的，审批的提问要是关于这个会话的。对话换到别的会话之后，原来那个 Agent 在结束过程中写下的东西也不再转发。

**标准输入输出要在加载插件之前收走。** 计划第 2 条只说了进程启动时收走。实现时先是放在前端开始运行的时候，那已经晚了：插件是在这之前加载的，一个在加载时打印的插件会把字写在第一条回答的位置上。现在启动器在加载任何插件之前就调用 `taken()`，再把得到的线路作为服务提供给前端。前端自己取线路的那条路还留着，给不经过启动器的用法。

**描述符的编号会被系统复用。** 复制描述符时系统给的是最小的空闲编号。进程启动时如果没有标准错误，2 号是空的，复制出来的私有描述符就会落在 2 号上，接着被当成标准错误用。`keep()` 因此先看三个描述符是否都开着：标准输入或标准输出没开就报错，标准错误没开就先在那个位置放上空设备。把空设备放到一个空位置上时，系统给出的编号可能正是那个位置本身，这时不能再把它关掉。这两处都是测试先发现的。

**Windows 上关闭一个正被别的线程读写的描述符会一直等。** C 运行库给每个描述符一把锁，读和写的时候拿着。所以线路关闭时，只有写线程已经结束才关闭写的那个描述符，否则留给进程退出去收。读的那个描述符从不主动关闭。

**审批的回答可能来两次。** 界面连着发来两条针对同一个提问的回答时，第二条到的时候那个提问还登记着，但已经有了结果。这种回答与迟到的回答一样被忽略。此前它会让读循环抛出异常。

**回合开始时读的输入改成按到达的先后排。** 循环在第一步先取"下一步要读的输入"，再取任务，两者此前按这个顺序写进对话。`/skill 名字 任务` 靠的就是这个顺序：技能的正文要在任务之前。但对转向来说这不对：界面紧接着 `session/prompt` 发来的 `session/steer`，如果回合还没有开始取输入，会在对话里排到任务前面。回合开始之前的那一段不总是很短，会话开始时的钩子和 MCP 服务器的连接都在这之前。终端界面有同样的问题。这是服务进程的一条测试发现的。现在收件箱另记着每条等待中的输入是什么时候到的，第一步取出来之后按到达的先后排：任务之前到的排在任务前面，任务之后到的排在后面。技能正文仍在任务之前，因为它先到。这一处改在循环里，单独一个提交。

**第 12 节的顺序与真实的进程逐条一致。** 写测试时预计要改文档，结果一条都不用改：文档里那一段是当初照着真实运行的记录写的。

**一条与本计划无关的测试被顺带修了。** 适配器的五条真实套接字测试共用了只有 50 毫秒的静默上限，机器忙的时候会超时。已经单独提交。

### 提交前的复查

提交之前请 Codex 只读地看了两遍。第一遍提了 11 条，10 条成立，1 条在实际的用法下不成立。第二遍看的是为第一遍所做的修改，又提了 3 条和一处测试的漏洞，都成立。每一条都先写出会失败的测试再动代码。

**被接受的命令会被后面的请求抢先。** 这是最要紧的一条。命令被接受的那一刻它的工作还没有开始，要过事件循环的几轮才开始。紧跟着的 `session/prompt` 在这之前就被办理了，回合先开始，命令随后因为 Agent 在忙而失败。`/permissions read-only` 后面跟着一件任务时，这个回合会带着原来更宽的权限开始。现在的规则只有一句：命令执行期间发来的输入由服务进程留着，命令一结束就按原来的先后交给 Agent。第一版的规则更细：Agent 正在为命令工作时让输入直接进它的等待队列，这样界面看得见它在等。第二遍复查指出这不够：一条命令可以让 Agent 工作不止一次，输入会在两次之间开出回合。于是改成一律留着。有输入留着的时候状态是 `running`，Agent 这时也许闲着，但有回合即将开始，界面不会看到状态在命令和回合之间闪回 `idle`。

**停止的要求会错过还没开始的命令。** 同一个空档的另一面：`/compact` 之后立刻 `session/cancel`，这时没有东西在运行，要求落空，压缩随后照常开始。现在命令是一个单独的任务。停止的要求到来时 Agent 如果空闲，就取消这个任务，命令不会开始，回答是 `The command /NAME was stopped.`。Agent 正在为命令工作时仍然只让 Agent 停下，命令自己说明它是怎么结束的。

**一个任务在迈出第一步之前被取消，它里面的代码一行都不会执行。** 上一条的第一版把"被取消了就回答一句话"写在命令任务的 `try` 里，结果正好在最需要的情形下不起作用：取消在第一步之前到达时，协程根本没有进入 `try`。所以等待命令的是另一个任务，它一定已经在运行，由它来接住取消并回答。

**每个请求都要有回答，退出时也一样。** 退出时还在后台办理的请求先等一秒，然后被取消。此前被取消的请求没有回答。现在命令回答一句话，`session/list` 回答新的错误 1005。

**退出码要看每一个会话。** 换会话时原来的会话在后台结束，结束得怎样此前没有人看。现在每一次结束都会被看一眼，失败就记进日志，进程退出时退出码为 1。此前有一条测试认为"已经停下并且被离开的会话"不影响退出码，它现在也期望 1。规则只有一句：这次运行里有会话的收尾没写进日志，退出码就是 1。

**不回答一条回答。** 缺少 `"jsonrpc": "2.0"` 的审批回答此前被当成不合法的请求，服务进程回了一条带着同一个 `id` 的错误，提问则一直等下去。那个 `id` 在界面那边是界面自己的请求编号，这条错误会被对到不相干的请求上。现在带着 `id` 而没有 `method` 的一行一律当作回答，外壳不对就是一次失败的回答，按不同意处理，什么也不回。

**长一点的许可按会话的 id 记。** 权限插件把这种许可记在会话对象上，重新打开同一个会话是一个新对象，许可就没有了。对用界面的人来说，许可是给一件任务的，中途看一眼别的任务不应该收回它。所以服务进程按会话的 id 另记一份，打开会话时再交给权限插件。工具已经不在了的许可交不回去，记一条警告，会话照常打开。

**没写出去的消息有上限。** 写线程等着一个不读的界面时，队列此前可以无限增长。现在最多留 64 MiB，超过就把界面当作已经不在，按标准输入被关闭处理。关闭线路时等写线程结束，也不再借线程池里的线程去等：线程池可能被卡在文件系统上的线程占满。

**读不了的 JSON 有自己的说法。** 嵌套十万层的数组会让解析器抛出 `RecursionError`，它不是 `ValueError`，此前一路传出去让进程退出。五千位的整数被 Python 拒绝，此前的回答是"不是 JSON"并且带着 Python 自己的提示。现在两种情形都回答 -32700 和一句说明原因的话。

**不成立的一条。** Python 的文档说在 Windows 上复制标准描述符得到的副本可以被继承。实测是只有控制台才这样，管道的副本不能被继承，3.11 和 3.13 都是如此。服务进程的标准输入输出总是管道，所以代码没有改。真实子进程的那条测试现在多问一句：除了三个标准位置，还有哪些描述符可以被继承，答案必须是没有。

**没有做的一条。** 线程池里有线程卡在文件系统上时，解释器结束不了，进程也就退不出去。这是整个程序的性质，不只是服务进程的。协议第 11 节要求壳等几秒之后强行结束进程，这一条靠它兜底。

**停不下来的会话也要收尾。** 第二遍复查指出的最要紧的一条。停下回合要把丢弃的输入记进日志，日志写不进去时这一步会抛出异常。此前这个异常让收尾半途而废：Agent 没有结束，退出码是 0。现在结束 Agent 的那段代码不让任何一步的失败挡住后面的步骤，最先出的错被记下来并算进退出码。

**没有 `id` 的回答也是回答。** 对方读不懂一行时回的错误，`id` 是 `null`。此前这样的一行被当成不合法的消息，又回了一条 `id` 为 `null` 的错误。两个这样做的程序会一直互相回下去。现在没有 `method` 而带着 `result` 或 `error` 的一行一律算回答，对不上提问就忽略。

**管道的容量各个系统不一样。** 排队上限的测试第一版用 60 KB 的行，在 Windows 上通过，因为那里的管道只有 4 KB。Linux 的管道有 64 KB，整行会直接写进去，计数随即减掉，测试就会失败。现在用的行比任何系统的管道都长。测试还补了三处：写线程正在写的那一行也算在排队里，按字节而不是按字符计数，恰好等于上限不算超过。

**测试多了一条总的检查。** 服务进程的每条测试结束时都检查：没有请求被回答两次，也没有回答被回答。新行为的测试把两行连着发出去，中间不等命令开始，因为要查的正是这个空档。

## 模块与接口

### `columbina.apps.serve.rpc`（新建）

错误码的常量。`Request(id, method, params)`、`Notification(method, params)`、`Response(id, result, error)` 三个数据类，分别是界面的请求、界面的通知、界面对服务进程的请求的回答。`parsed(line: bytes)` 把一行变成三者之一，行有问题时抛出 `Malformed(code, message, id)`。`answered(id, result_json)`、`refused(id, code, message)`、`told(method, params_json)`、`asked(id, method, params_json)` 生成发出的行。`RpcError(code, message)` 是处理请求时用来回答错误的异常。

### `columbina.apps.serve.wire`（新建）

`Wire` 是一个协议（`typing.Protocol`）：`lines()` 给出收到的行的异步迭代器，对方关闭时结束；`send(line)` 发出一行，不等待；`close()` 把还没写完的写完。`taken()` 把进程的标准输入输出收归己用，返回走这两个私有描述符的 `Wire`。`WIRE` 是服务键，测试用它放进一个内存里的 `Wire`，没有人提供时前端自己调用 `taken()`。

### `columbina.apps.serve.server`（新建）

`Server(ctx, config, agents, sessions, commands, send)`。`serve(lines) -> int` 处理到来的行，直到 `shutdown` 或者行结束，返回退出码。

### `columbina.apps.serve`（新建，插件 `serve`）

`Config(model, cwd, system_prompt)`。`apply` 提供 `FRONTEND`，登记 `/model`。

### 启动器和清单（修改）

`columbina serve`，参数与 `run` 相同，但没有任务和 `--session-id`。清单 `serve.yml` 在 `base` 之上加命令服务、除 `/fork` 以外的命令和这个前端。

uv run columbina serve

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocol":1,"client":{"name":"hand","version":"0"}}}

{"jsonrpc":"2.0","id":4,"method":"shutdown"}
