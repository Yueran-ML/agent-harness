# Columbina 第 7 阶段实施计划：容器沙箱

**Goal:** Agent 运行的命令在一个容器里执行。容器里只有工作目录，默认没有网络，命令能做的事不超过会话的沙箱模式允许的范围。这样的命令不必再逐条问人。

**Architecture:** 沙箱接缝的提供者不再只是包装命令，而是自己把命令运行完。新的提供者 `docker` 为每个会话保持一个容器，容器的寿命系在本程序握着的一根管道上。守着管道的进程是 root，命令以普通用户运行，所以命令动不了它。每条命令是一次 `docker exec`，结束、超时或取消之后，这个用户在容器里的全部进程被一并杀掉，杀不干净就放掉整个容器。命令在哪里运行，shell 工具就用哪里的 shell：容器里是 bash，在 Windows 上也是。

**Tech Stack:** 只用 `docker` 命令行，不加 Python 依赖。本机是 Docker Desktop 4.94.0，引擎 29.8.2，后端是 WSL 2。

设计依据是 `docs/plans/2026-10-09-columbina-design.md` 的第 9.1、9.2、9.3 节。本计划与这些章节不一致的地方列在"与设计文档的差异"一节，阶段结束时把设计文档改成一致。

本文是第二稿。第一稿经过一次只读的复查，得到 15 条意见，其中 3 条是能让命令越出沙箱的。第二稿按这些意见和三个补做的试验重写，改动列在"复查之后改了什么"一节。

## 结束标志

设计文档 15.2 给本阶段的结束标志是：shell 工具在容器内执行，断网。落到测试上是下面五条，前四条用真实的引擎，经 `columbina run` 的命令行和脚本化的模型运行。

1. **只碰得到工作目录。** 命令在工作目录里写的文件，本机上看得到。命令写到工作目录之外的东西，本机上没有任何变化。`read-only` 模式下工作目录写不进去。`workspace-write` 模式下 `.git` 写不进去。
2. **没有网络。** 命令去连一个地址，连不上。
3. **不再逐条询问。** 没有人可问的运行里，命令照样执行，因为它被完全约束住了。有一条询问规则管着它时，它仍然要问。容器有网络时，它也仍然要问。
4. **停得干净。** 超时的命令连同它启动的进程一起被停掉，另开会话的进程也不例外。运行结束之后，没有容器留下。
5. **引擎不在时不放行。** 用测试替身模拟引擎不在、镜像不在、镜像里没有 bash、引擎不受支持四种情形：命令的结果是 `SANDBOX_UNAVAILABLE`，写明该怎么办，命令没有改在本机上运行。

另有一条对真实服务的测试：模型被告知命令在一个 Linux 容器里运行之后，用容器里的 bash 把第 3 阶段的小仓库修好。它用 `python:3.12-slim`，没有密钥、没有引擎或者没有镜像时跳过。

## 范围

本阶段做的：接缝改成由提供者运行命令。shell 工具按命令运行的地方选 shell。提供者 `docker`：找到可信的 `docker` 程序，检查引擎，容器的保持与放掉，按模式挂载，运行与收尾，失败时的说法。`process.run` 在停掉程序之前先让调用方收尾。强度按会话给出。权限里"被完全约束的命令不问"，并把这次放行绑定到实际的执行。告诉模型命令在哪里运行。Windows 上文件工具认得容器里的工作目录路径。清单、命令行选项、测试替身、真实引擎的测试、文档。

本阶段不做的：设计文档里标为可选的 `bwrap`。`columbina doctor`。按域名放行的网络。替用户下载或构建镜像。把文件工具也搬进容器。项目自带的沙箱配置：镜像是别人写的程序，由项目来指定等于运行别人的代码，要有钩子那样的信任机制，留到以后。无根模式的 Docker、用户命名空间重映射和 Podman：它们的用户编号对应关系各不相同，本机没有条件试，遇到时明确说不支持。

## 先做的试验

写计划之前在本机做了六个试验，复查之后又补了三个，脚本留在草稿目录里。两个参考实现都用各自系统的原生沙箱，没有用容器的，所以这一阶段没有可以照着做的地方。

**试验一：一条命令要多久。**

| 做法 | 用时 |
|---|---|
| `docker version` | 0.10 秒 |
| 每条命令一个新容器（`docker run --rm`） | 0.4 到 0.6 秒 |
| 启动一个留着的容器 | 0.3 秒 |
| 在留着的容器里 `docker exec` | 0.11 秒 |
| 删除容器 | 0.16 秒 |

**试验二：把 Windows 的目录挂进容器。** 目录的路径里有空格和中文，作为一个参数传给 `docker` 就能挂上。

| 情形 | 结果 |
|---|---|
| 容器里看到的文件 | 属主是 root，权限是 777。回车换行原样。中文文件名正常 |
| 容器里写的文件 | 本机上看得到 |
| 容器里建的符号链接 | 容器里是链接。本机上看得到名字，但 `exists()` 说它不存在 |
| `Case.txt` 和 `case.txt` | 是同一个文件 |
| 以另一个用户运行（`--user 1000:1000`） | 写得进挂载的目录 |
| 只读挂载 | 写不进去，"Read-only file system" |
| 可写的挂载里再把 `.git` 只读挂一层 | `.git` 里写不进去，改名和删除也都失败 |
| 速度 | 356 个文件，`find` 用 0.32 秒，`grep -r` 用 0.5 秒。本机上同样的遍历用 0.02 秒 |

**试验三：在留着的容器里运行命令。** 退出码传得出来，标准输出和标准错误是分开的，输入传得进去，不是文字的字节原样出来，几兆字节的输出没有问题。`--network none` 之下名字解析不了，地址连不上，回环地址还在。最要紧的一条：把本机的 `docker` 客户端杀掉，容器里的命令照样在跑。

**试验四：按会话号收尾。** 这是第一稿的做法：命令把自己的会话号写进容器里的一个文件，停的时候按会话号找进程。它停得掉后台的进程，停不掉自己另开会话的进程。第二稿不用它，原因见第 21 条。

**试验五：出错时 Docker 怎么说。**

| 情形 | 退出码 | 说法 |
|---|---|---|
| 引擎不在 | 1，0.06 秒 | "failed to connect to the docker API at ..." |
| 镜像不在，又不许下载 | 125 | "No such image" |
| 容器不在 | 1 | "No such container" |
| 要运行的程序不在，或者工作目录不在 | 127 | "OCI runtime exec failed"，写在标准输出上 |

所以单看退出码分不清是 Docker 出了错，还是命令自己以这个码结束。另外，`--cap-drop ALL` 之下容器里的 root 不能改属主，也不能挂载。`--pids-limit` 到限时 `fork` 失败。

**试验六：容器的寿命。** 用 `docker run --rm -i ... cat` 启动容器，本程序握着通向它标准输入的管道。关掉管道、杀掉 `docker` 客户端、把握着管道的程序整个杀掉，三种情形下容器都在 0.2 秒内消失，里面的进程一起结束，什么都没有留下。

**试验七：`docker exec` 启动的进程已经是会话的首领。** 它的进程号、进程组号和会话号是同一个数，带不带 `-i` 都一样。`setsid` 因此会另起一个子进程，原来的那个立刻退出：命令的退出码是 5 时，`docker exec` 报的是 0。不用 `setsid` 时退出码是对的。

**试验八：命令动不了的看守，和不靠记录的收尾。** 容器的主进程以 root 运行，命令以编号 1000 的用户运行。

| 情形 | 结果 |
|---|---|
| 命令向看守发停止和杀死的信号 | 两个都是 "Operation not permitted" |
| 命令留下 47 个进程，其中有另开会话的，再由同一个用户执行 `kill -KILL -1` | 全部结束，等着命令的客户端自己以 137 退出，看守还在 |
| 一个不停分叉的命令，同样收尾 | 结束 |
| `kill -0 -1` | 没有别的进程时也报成功，所以不能用它判断收干净没有 |
| 把本机临时目录里的一个随机记号只读挂进去，由容器的入口印出来 | 印出来的与写进去的相同 |
| `--mount` 的 `bind-recursive=disabled` | 引擎接受 |
| `docker info` | 给得出版本、系统名和安全选项，本机没有 `rootless` |

**试验九：复查对 Linux 主机说的几件事。** 本机是 Windows，文件要经过一层共享才到容器里，Linux 的主机上没有这一层。所以这个试验把引擎所在的那台虚拟机里的一个目录当作主机的目录：容器和它在同一个内核、同一个文件系统上，和 Linux 主机上的情形一样。

| 情形 | 结果 |
|---|---|
| `.git` 是指向目录之外的链接，把它当作挂载的来源交给引擎 | 引擎跟着链接走，把外面的那个目录挂了进来，容器里读得到其中的文件。复查的这一条属实 |
| 同一个链接，不给它单独的挂载 | 链接在容器里指向一个不存在的路径，什么都读不到 |
| `.git` 是一个文件，把它只读挂一层 | 写不进去，替换、删除、改名都是 "Device or resource busy" |
| 目录里有一个套接字，另一头是沙箱之外的进程。容器没有网络，挂载只读，命令是普通用户 | 连得上，读到了对方的回答。复查的这一条属实 |
| 命令以另一个编号的用户运行 | 写不进目录。用目录属主的编号就写得进，文件的属主是这个编号 |
| 来源下面另有挂载 | 带子挂载时看得到其中的 22 项，`bind-recursive=disabled` 时是 0 项 |
| Windows 上，目录里有一个指向目录之外的交接点 | 容器里它是一个指向不存在路径的链接，读不到也写不进外面。符号链接没有试成，本机没有建它的权限 |

## 复查之后改了什么

复查的意见里，关于 `.git` 链接和套接字的两条在试验九里复现了，关于 `docker.exe` 的一条与 shell 工具早先遇到的是同一个问题。

| 复查的意见 | 第二稿的做法 |
|---|---|
| Windows 上按名字启动 `docker`，仓库里放一个 `docker.exe` 就能让它在本机上运行 | 第 5 条：按绝对路径找，不在当前目录和工作目录里找 |
| 工作目录里的套接字在只读挂载和断网之下照样连得上 | 第 16 条：启动容器时找一遍，找到或者没找完，强度降为 `partial` |
| `.git` 是指向别处的符号链接时，把它单独挂一层等于把主机上的那个目录挂了进去 | 第 13 条：挂载的来源先解析，必须落在工作目录之内 |
| 只保护启动时已有的顶层目录，不合现有的说法 | 第 13、14 条：工作目录自己在受保护的目录里时整个只读；命令新建的顶层受保护目录在这条命令之后被发现并保护起来；嵌套的写进已知的限制 |
| 硬链接让写入落到工作目录之外 | 写进已知的限制。文件工具现在也分辨不出硬链接 |
| 只读挂载在旧内核上不递归 | 第 13 条：挂载一律不带子挂载，引擎太旧时说不支持 |
| 命令能改写用来给它收尾的记录 | 第 19 到 21 条：容器里不留任何记录，收尾按用户杀进程，退出码用引擎报的 |
| 另开会话的进程在模式收紧之后还带着旧的权限活着 | 第 9、21 条：一个会话一个容器，模式变了就放掉旧的；收尾不放过另开会话的进程 |
| 命令能让守着管道的进程停住，容器就永远删不掉 | 第 11 条：看守是 root，命令是普通用户。第 10 条：放掉容器时另用 `docker rm -f` 并确认它没了 |
| 取消发生在命令登记之前时，命令会在调用结束之后才启动 | 第 22 条：先收尾，再等客户端自己退出，等不到就放掉容器 |
| 扫描 `/proc` 再按进程号杀，有竞争 | 第 21 条：`kill -KILL -1` 由内核一次做完 |
| 放行时看的强度，和实际执行时的情形可能不是一回事 | 第 26 条：放行带着一个期望，执行时核对 |
| 引擎可能在另一台机器上，挂载的是那台机器上的同名目录 | 第 7 条：用一个随机记号确认引擎看到的是本机的文件 |
| 无根模式、用户命名空间重映射、Podman、SELinux 的用户对应关系各不相同 | 第 6 条：明确支持哪些引擎，其余的报不支持 |
| 持续集成可以在两段脚本一行都没运行的情况下通过 | 第 33 条：Ubuntu 的机器上真实引擎的测试必须运行，不许跳过 |

## 设计决定

### 接缝与 shell

**1. 提供者自己运行命令。** 原来的接缝是 `confine(argv)`，提供者交回一条包装过的命令，由 shell 工具去运行。容器做不到这样：运行之前要先有容器，运行之后要把命令留下的进程停掉，客户端被杀掉时这一步尤其不能少（试验三）。所以接缝改成异步的 `run`，提供者拿到命令、会话、模式、工作目录、输入和时限，交回运行的结果。提供者 `none` 的 `run` 就是原来 shell 工具里的那次 `process.run`。这一条已经在任务 1 里做完。

**2. 命令在哪里运行，就用哪里的 shell。** 提供者说明它运行命令的地方用什么 shell：`none` 不说，用本机的；`docker` 说 `bash`。shell 工具登记的是这个 shell 的工具，所以在 Windows 上用 `docker` 时，工具叫 `bash`，不叫 `powershell`。工具的名字仍然在程序启动时定下，一次运行里不变。为 `powershell` 写的规则管不到容器里的 bash，`run(...)` 这种不指名工具的规则照常管用。

**3. 容器里的命令经标准输入交进去。** Windows 的命令行至多 32767 个字符，命令要先经过本机的 `docker.exe`，写成参数会被这个上限卡住。所以容器这一路的 bash 用一行固定的话启动，由它从输入里读出命令再执行，命令自己的输入接到 `/dev/null`。这与 PowerShell 那一路的做法相同。命令至多 120000 字节，因为容器里它最终是 bash 的一个参数。

**4. `docker` 提供者随沙箱插件一起登记。** shell 工具加载时就要知道用哪种 shell。如果提供者由另一个插件带来，它可能还没有登记。所以 `docker` 和 `none` 一样由沙箱插件自己登记，配置写在沙箱的配置里。它被选中之前不碰 Docker。

### 引擎

**5. `docker` 程序按绝对路径找。** 在 Windows 上按名字启动程序，系统先看当前目录，而当前目录常常就是一个仓库。所以程序自己在 `PATH` 里找：只看写成绝对路径的目录，跳过当前目录，取第一个 `docker`。配置里可以直接给出绝对路径。启动容器时再查一次：找到的程序如果落在这个会话的工作目录里面，就不用它，结果是 `SANDBOX_UNAVAILABLE`。

**6. 支持哪些引擎。** 启动第一个容器之前问一次 `docker info`。支持的是 Docker Desktop，和 Linux 上以 root 运行的 Docker Engine，版本 25 或更新。安全选项里有 `rootless` 或 `userns` 的不支持，问不出这些信息的也不支持。在 Linux 上以 root 运行本程序时也不支持，原因见第 11 条。不支持时命令的结果写明是哪一种情形。macOS 上的 Docker Desktop 按 Windows 上的同样对待，但没有机器验证过，文档里写明。

**7. 引擎要看得到本机的文件。** `docker` 可能被配置成连到另一台机器，那时挂载的是那台机器上的同名目录。启动容器时在本机的临时目录里放一个随机的记号，只读挂进去，由容器的入口印出来。印出来的与写进去的不同，或者挂载失败，容器就不能用，结果里写明引擎看不到本机的文件。这个目录要让别的用户读得到：容器里的 root 没有越过权限的能力。记号只用这一次，不是秘密。

**8. 不替用户下载镜像。** `--pull never`。镜像不在时，命令的结果写明镜像的名字和 `docker pull` 的命令。一条命令背后悄悄下载一个吉字节的镜像，既慢又出乎意料。

### 容器

**9. 一个会话一个容器。** 第一稿让同一个工作目录的会话共用容器。收尾的办法改成杀掉这个用户的全部进程之后（第 21 条），一个容器里同一时间只能有一条命令。一个会话的命令本来就是一条接一条的，所以按会话分。子代理有自己的会话，也就有自己的容器，父 Agent 装在工作目录之外的东西它看不到，装在工作目录里的看得到。会话的模式或者工作目录变了，旧的容器被放掉，下一条命令启动新的。容器在第一条命令到来时才启动。

**10. 容器的寿命系在一根管道上，放掉时另行确认。** 容器的主进程是 `cat`，读本程序握着的管道（试验六）。程序被杀掉时，系统替它关掉管道，容器随即消失。程序自己放掉一个容器时，先关管道，再执行 `docker rm -f`，然后确认这个名字已经不在了。确认不了时记一条警告，写明容器的名字。会话没有"结束"这个事件可听，所以提供者每隔几秒看一遍手里的容器：会话已经关闭的放掉，子代理结束时就是这样；半小时没有命令的也放掉。

**11. 看守是 root，命令是普通用户。** 容器的主进程以 root 运行，启动时明确写 `--user 0:0`，因为镜像可以自己指定别的用户。命令以另一个用户运行：Linux 上是本机用户的编号，这样命令写得进工作目录，建出的文件属主也是对的（试验九）；Windows 和 macOS 上挂载的属主是虚拟出来的，用 1000。能力全部去掉之后，普通用户给 root 的进程发不了信号（试验八），所以命令停不住看守，也改不了容器里的 `sh` 和别的系统程序。本机用户自己就是 root 时这一条不成立：命令和看守成了同一个用户，所以不支持。命令的 `HOME` 是 `/tmp` 下的一个目录，每条命令运行之前建好。命令不能往系统目录里装东西，`pip install` 会装到 `HOME` 下面。

**12. 启动容器的参数。** `docker run --rm -i --pull never --init --user 0:0 --name columbina-<随机> --label columbina=1`，加上 `--cap-drop ALL`、`--security-opt no-new-privileges`、`--pids-limit`，配置里给了内存和处理器的上限时再加这两项。入口换成一小段 sh：查一下有没有 bash，印出一行 `ready` 加那个记号，或者 `missing`，然后变成 `cat`。程序读到对的那一行才把容器交出去用。

**13. 按模式挂载，来源都要核对。**

| 模式 | 工作目录 | 另外 |
|---|---|---|
| `read-only` | 只读 | |
| `workspace-write` | 可写 | 工作目录顶层已有的 `.git` 和 `.columbina` 各再只读挂一层 |
| `danger-full-access` | 可写 | 没有只读的那一层 |

只有工作目录被挂进去，挂的是解析掉链接之后的那个目录。所有挂载都不带子挂载（`bind-recursive=disabled`），工作目录下面如果另挂着别的文件系统，容器里看不到它。受保护的名字是一个真实的目录或文件时，把它只读挂上。它是一个符号链接时，看它指向哪里：指向工作目录之内，就把那个真实的位置只读挂上；指向工作目录之外，什么都不挂，这个链接在容器里通不到主机上的任何东西。把链接本身当来源交给 Docker，Docker 会跟着它走，把主机上的那个目录挂进来。工作目录自己就在一个受保护的目录里时，比如在 `.git` 里面启动，整个工作目录只读。挂载用 `--mount`，路径里有逗号或引号时按它的规则加引号。

**14. 命令新建或换掉的受保护名字。** 启动容器时还不存在的 `.git` 没有办法预先挂上：给不存在的路径做挂载点，Docker 会在本机的目录里把它建出来。是链接的 `.git` 自己也没有被挂住，命令可以删掉它，再建一个同名的目录。所以启动容器时记下工作目录顶层每个受保护的名字是什么：不存在、目录、文件，或者指向哪里的链接。每条命令结束之后再看一遍，和记下的不一样就放掉容器，下一个容器按新的样子挂载，这条命令的结果里写明。这样一条命令可以建出 `.git`，之后的命令改不了它。嵌套在下面的同名目录不在这个范围里，见已知的限制。

**15. 网络是另一个开关，打开之后强度降一档。** 缺省 `--network none`。配置里写 `network: bridge` 时用 Docker 缺省的网络。它不随模式变。有网络的容器管得住命令写什么，管不住命令把读到的东西发出去，所以这时强度是 `partial`，不是 `full`。第 25 条因此不适用，命令照旧要问。

**16. 工作目录里的套接字。** 套接字文件经挂载照样连得上，只读和断网都拦不住（试验九）。它的另一头如果是 Docker 自己的接口，或者是一个密钥代理，命令就拿到了主机上的能力。POSIX 的本机上，启动容器时把工作目录找一遍，至多看二十万项或者三秒。找到套接字，或者没找完，这个容器的强度就是 `partial`，原因写进给模型的那几行。Windows 上不找：那里的文件要经过一层共享才到容器所在的内核，套接字过不去。第二次复查之后，这一遍改在每条命令之前做，见“实施中的发现”第 31 条。

**17. 挂载点。** POSIX 的本机上，工作目录挂在容器里的同一个路径上，模型在命令的输出里看到的路径和文件工具用的路径是一回事。Windows 上做不到，挂在 `/workspace`。

**18. 容器里的环境。** 只有 `HOME`、`LANG=C.UTF-8`、`TERM=dumb` 和配置里写明的变量。本程序的环境不带进去，密钥到不了容器里。

### 运行一条命令

**19. 一条命令是一次 `docker exec`，容器里不留记录。** `docker exec -i --user <用户> -w <目录> <容器> /bin/sh -c <一行> <命令…>`，那一行建好 `HOME` 然后变成命令。`docker exec` 启动的进程本来就是自己会话的首领（试验七），不需要 `setsid`。一个容器同一时间只运行一条命令，提供者用一把锁保证。

**20. 退出码是引擎报的。** 客户端的退出码就是命令的退出码。命令返回时如果看守已经不在了，那是容器没了：结果是 `SANDBOX_UNAVAILABLE`，带上 Docker 说的话，下一条命令会启动一个新的容器。启动时已经确认过 bash 在，工作目录就是挂载点，所以试验五里那两种 127 不会出现。

**21. 收尾是杀掉这个用户的全部进程。** 每条命令之后再做一次 `docker exec`，以同一个用户执行 `kill -KILL -1`，然后在 `/proc` 里确认没有这个用户的别的进程了，只用 sh 自己带的功能，不另起进程。没收干净就再来，至多几轮。这一步由内核一次做完：另开会话逃不掉，不停分叉也逃不掉（试验八），也没有按进程号去杀时进程号被别人占用的问题。它不依赖容器里的任何记录，命令没有东西可以伪造。

**22. 超时和取消：先收尾，再等客户端。** 现在的 `process.run` 在超时或被取消时立刻杀掉本机的进程。对容器这样做不够：客户端没了，命令还在（试验三）；引擎甚至可能刚接下这条命令，还没有启动它。所以 `process.run` 多一个钩子，在杀掉本机的进程之前先调用，钩子拿得到"程序已经退出"这个信号。提供者的钩子反复做第 21 条的收尾，直到客户端自己退出。客户端还连着的时候，迟到的命令一启动就会在下一轮被杀掉。十秒之内等不到，就放掉整个容器。钩子不被第二次取消打断。

**23. 收尾做不成时，放掉整个容器。** 收尾的那次 `docker exec` 启动不了、没有回答，或者几轮之后仍然有剩下的进程，都按第 10 条放掉容器。一条存心捣乱的命令可以让收尾做不成，它得到的是整个容器被杀掉。这条命令的结果里写明：容器被放掉了，装在里面的东西没有了。

### 审批与告知

**24. 强度按会话给出。** 原来的强度是整个提供者的一个值。现在提供者按会话和工作目录回答：引擎可用、没有网络、没有找到套接字时是 `full`，否则是 `partial`。容器还没有启动时按配置回答，启动之后按核对过的事实回答。状态行、给模型的那几行和权限的判断都问这一个地方。

**25. 被完全约束的命令不问。** `decide` 多一个参数，说明这次调用被约束的强度。顺序是：拒绝规则，本会话内的同意，询问规则，放行规则，完全访问，然后是这一条，最后才是询问。强度只对经沙箱运行的工具有意义，shell 工具向权限插件登记自己是这样的工具。MCP 服务器的工具在本机上运行，不受容器约束，照旧要问。

**26. 这样的放行绑定到实际的执行。** 守卫因为强度是 `full` 而放行时，给这次调用记下一个期望。shell 工具把调用的编号交给沙箱，提供者拿到容器之后核对：实际的强度够不够。不够时命令不运行，结果写明原因，并告诉模型再调用一次就会被问到。放行之后、执行之前，提供者被换掉、容器启动时发现了套接字、配置变了，都落在这一条上。

**27. 告诉模型命令在哪里运行。** 运行时上下文里原有"命令由谁运行"和"命令被约束到什么程度"两行。提供者再给出几行：命令在一个 Linux 容器里运行，用的是哪个镜像；容器里只有工作目录，在哪个路径上；有没有网络；命令不是 root，装不进系统目录；装在工作目录之外的东西，程序结束就没有了。

**28. Windows 上文件工具认得容器里的路径。** 命令的输出里是 `/workspace/src/app.py`，模型多半会原样拿去读。文件接缝多一张表：某个前缀在这个会话里就是工作目录。提供者在 Windows 上登记 `/workspace`。以这个前缀开头的路径先换成工作目录里的相对路径，再走原有的定位和判断，原有的规则一条不少。

**29. 引擎不在时，在第一条命令上说。** 程序启动时不问引擎：`sessions list` 这样的命令用不着它，Docker Desktop 也可能晚一点才启动。被选中的提供者是 `docker` 时，启动时只找一次 `docker` 程序，这一步不运行任何东西，找不到就记一条警告。

### 配置与测试

**30. 配置。** 选哪个提供者有三个办法：环境变量 `COLUMBINA_SANDBOX=docker`，命令行选项 `--sandbox docker`，或者在补丁文件里写 `provider`。`docker` 的配置项如下，写在沙箱配置的 `docker` 之下。

| 键 | 含义 | 缺省 |
|---|---|---|
| `program` | `docker` 程序的绝对路径 | 在 `PATH` 里找 |
| `image` | 镜像 | `python:3.12` |
| `network` | `none` 或 `bridge` | `none` |
| `env` | 给容器里的命令的变量 | 空 |
| `pids_limit` | 进程数的上限 | 2048 |
| `memory`、`cpus` | 内存和处理器的上限 | 不设 |
| `start_timeout_seconds` | 等容器就绪的时限 | 60 |
| `idle_seconds` | 没有命令多久之后放掉容器 | 1800 |

**31. 测试替身是一个假的 `docker` 程序。** 持续集成的六台机器里只有 Ubuntu 的两台有能跑 Linux 容器的引擎，覆盖率却要每台都是 100%。所以提供者的每一行都要能在没有引擎的机器上走到。替身是一个 Python 程序，认得 `info`、`run`、`exec`、`rm` 和 `ps`：`run` 印出就绪的一行并读输入直到结束，`exec` 在本机运行给它的命令，收尾的那次 `exec` 把记下的进程杀掉。它可以按测试的要求装作引擎不在、镜像不在、镜像里没有 bash、引擎不受支持、收尾收不干净、容器删不掉。提供者的测试给它的命令是 Python 写的小程序，不依赖本机有没有 bash。

**32. 真实引擎的测试检验那几段 sh 和那些挂载。** 替身不运行入口、运行和收尾的三段 sh，也不真的挂载。这些只有真实的引擎能检验：三种模式下能写和不能写的地方，`.git` 是目录、是文件、是链接时各自的情形，没有网络，命令给看守发信号发不了，另开会话的和不停分叉的进程都被收掉，取消之后没有东西还在跑，程序被杀掉之后容器消失，放掉之后名字不在了，记号对不上时不能用，没有 bash 的镜像，带空格和中文的目录。只在 Linux 主机上成立的几条（链接的 `.git` 不把主机的目录挂进来、工作目录里的套接字被发现、文件的属主）在别处跳过。

**33. Ubuntu 的持续集成上，这些测试必须运行。** 环境变量 `COLUMBINA_REQUIRE_DOCKER=1` 之下，引擎不回答或者镜像不在是失败，不是跳过。`ci.yml` 给 Ubuntu 的两台机器设这个变量，并在测试之前取 `debian:bookworm-slim` 和 `busybox`。别的机器和没有设它的地方，没有引擎或者没有镜像时跳过，测试自己不取镜像。这一处改动要作者同意。同意之前，这些测试在本机的 Docker Desktop 上运行，只在 Linux 主机上成立的几条以试验九为据。

**34. 已知的限制，写进文档。**

- 硬链接分辨不出来。工作目录里的一个名字如果和别处的文件是同一个文件，往它里面写就是往那个文件里写。文件工具现在也是这样。包管理器会把缓存里的文件硬链接进项目。
- 嵌套在工作目录下面的 `.git` 和 `.columbina` 不受保护，只有顶层的受保护。
- 命令运行期间才出现在工作目录里的套接字发现不了。
- 不区分大小写的磁盘上，以及留着短文件名的 Windows 磁盘上，只读挂载盖不住受保护名字的另一个名字。这时强度是 `partial`，命令照常要问。见“实施中的发现”第 32 条。
- 只有工作目录被挂进去。工作目录是仓库的一个子目录，或者是一个工作树时，容器里的 git 找不到仓库。
- Windows 上经挂载访问文件比本机慢几十倍。
- 镜像里要有 bash。项目要用的工具也要在镜像里，容器里的命令不是 root，没有网络时装不了东西。
- 无根模式的 Docker、用户命名空间重映射和 Podman 不支持。在 Linux 上以 root 运行本程序时也不支持。
- 强制开启 SELinux 的主机上挂载可能被拒绝，那时记号对不上，结果里会说。
- 工作目录很大时，找套接字的那一遍会在看完之前停下，命令就照旧逐条询问。
- macOS 没有机器验证过。Windows 上指向目录之外的符号链接没有试成，交接点试过。

## 与设计文档的差异

1. 接缝是 `run`，不是 `confine`。提供者运行命令，不只是包装。原因见第 1 条。
2. 用 `docker` 时命令工具是容器里的 bash，在 Windows 上也是。设计文档没有写这一点。
3. 完全访问模式下命令仍然在容器里，模式只决定挂载。设计文档没有写。
4. 被完全约束的命令不问，并且这次放行绑定到执行。设计文档只写了强度为 `none` 时一律要问。
5. 强度按会话给出，容器有网络或者工作目录里有套接字时是 `partial`。设计文档里强度是提供者的一个值。
6. Windows 上文件工具认得 `/workspace` 这个前缀。设计文档没有写两套路径的问题。
7. 镜像不自动下载。设计文档没有写。
8. `process.run` 多一个在停掉程序之前调用的钩子。
9. `bwrap` 不做。设计文档标的是可选。

## 实施中的发现

**1. 任务 5、6、7 是合在一起做的。** 没有命令在里面运行的容器检验不出什么，而收尾和挂载又只有真实的引擎能检验，所以保持容器、运行与收尾、真实引擎的测试写成了一块，一起过闸门。

**2. 命令的输出和报错从容器里出来时不保序。** 真实引擎的测试里，一条报错出现在它后面几行输出的后面。两路输出在容器里是两根管道，谁先到没有保证。所以固定的那一行让命令把报错也写到输出上（`2>&1`），在本机上运行的命令本来就是这样。一条测试让命令向两边各写 200 行，取回来的顺序与写的顺序相同。

**3. Docker Desktop 会把不存在的挂载来源建出来。** `--mount` 的来源不存在时，Linux 上的引擎报错，Docker Desktop 却在本机上建一个空目录，然后正常启动容器。所以提供者在启动之前自己确认工作目录还在，也从不把不存在的路径交给引擎。

**4. 不去猜引擎怎样对应用户。** 计划里按平台决定命令以谁的身份运行，但各种引擎的对应办法太多。实现里多了一步：容器启动之后，以命令的用户看一眼工作目录，能读、能写的情况必须和模式说的一致。写不进而本程序写得进，或者该只读的却写得进，都算不可用，并说明原因。

**5. 启动容器不会被半路打断。** 取消发生在容器启动途中时，客户端如果被杀在"创建"和"启动"之间，引擎那里会留下一个没人知道的容器。所以启动一旦开始就做完：等它的调用被取消时照常收到取消，容器留给这个会话的下一条命令。

**6. 一条命令至多启动两个容器。** 变异检查时发现一个死循环：容器刚做好就不合用（它立刻结束了，或者工作目录里受保护的名字一直在变），程序就一遍一遍地重做。现在重做一次还不行就报错，说明原因。

**7. 事件循环比系统晚一点知道进程结束。** 看守刚被杀掉的那一瞬间，程序还以为容器在。所以被放掉的容器另有一个标记，命令返回时先看标记。别人放掉了它正在用的容器时，结果里说的是"容器在命令运行时结束了"，不是"收尾没收干净"。

**8. 留着进程的命令要多等两秒。** 命令结束之后如果还有它启动的进程握着输出，`docker exec` 要再等两秒才返回，这是引擎等剩余输出的时限。之后这些进程照常被收掉。

**9. 结果里的说明走一个新字段。** 容器被换掉时要告诉模型。运行结果多了 `notes`，命令工具把它们写在退出码后面的括号里。提供者 `none` 没有什么可说的。

**10. 测试替身不是一个可执行文件。** Windows 上没有办法不加依赖就做出一个 `docker.exe`，批处理文件又会改写参数里的引号和 `&`。所以测试把配置里那个路径的启动改成"用 Python 运行替身"，改的是事件循环启动子进程的那一处。引擎不在时不回退到本机这一条，端到端的测试用 Python 自己充当 `docker` 程序：它在第一步就失败。

**11. 本机可以在 Linux 上跑测试了。** 有了 Docker 之后，整套测试可以在一个 Linux 容器里跑，仅 POSIX 才运行的测试不必等推送之后的持续集成。变异体也能在那里并行地试，容器限制在 8 个处理器和 6 GB 内存之内。脚本在草稿目录里，不在仓库里。

**12. 看守读记号的目录要让别人读得到。** 看守是没有任何能力的 root，别的用户的私有目录它进不去。放记号的临时目录因此是 755。

**13. 强度按会话说，任务 8 和 9 合成一次提交。** 套接字要到容器启动、看过工作目录之后才知道，所以"约束到什么程度"不是提供者的一个属性，而是对某个会话的回答。守卫放行时记下的期望也按会话和调用编号存。两件事改的是同一条线上的代码，分开提交会有一个中间状态过不了测试。

**14. 实现又请 Codex 复查了一遍，十四条意见全部属实。** 两条严重，六条重要，六条次要。下面第 15 到 22 条是其中改动较大的，其余几条是对测试的修正和两条写明的限制。

**15. 通往 `docker` 程序的整条路都不能经过工作目录。** 原来只看名字最后落在哪里，然后把名字交回去。工作目录里一个指向外面的链接因此通得过，而命令能把它换掉，下一次调用运行的就是别的文件，在本机上。现在从名字到文件逐段走，链接从它所在的目录算起，任何一步落在工作目录里都不行。顺带查出四件事：程序只找一次，之后每个会话的工作目录都要对它再验一遍，因为搜索路径可能伸进某个会话的工作目录（项目里激活着的虚拟环境就是这样）；Windows 先把路径里的 `..` 消掉再看链接，别的系统相反；Windows 上有的名字既不是文件也不是链接，Python 对它们抛的不是系统错误；不分大小写的文件系统上，一个目录有两个写法，要靠设备号和 inode 认。

**16. 受保护的链接，保护的是路上的第一级目录。** `.git` 是指向 `meta/git` 的链接时，原来只把 `meta/git` 挂成只读。命令可以把 `meta` 挪开再建一个，链接指的路径没变，指到的却是命令放的东西。试验十三在引擎自己的文件系统上和经过 Windows 的共享都重现了。现在挂成只读的是工作目录下通往目标的第一级目录，挂载点挪不动。链接指向什么也进了"形状"，命令把原来不存在的目标建出来时，容器照样被换掉。

**17. 这台机器看不了的受保护名字，让整个工作目录只读。** 命令在容器里建的链接，Windows 既打不开也读不出指向（错误号 1920，pathlib 不吞这个错误）。它保护什么无从知道，所以整个目录只读。原来这种情形会让建容器这一步直接抛出系统错误。

**18. 带换行的路径不交给 Docker。** Docker 按 CSV 的规矩读挂载的各个字段，引号里的回车加换行会被当成一个换行，挂上去的就不是写的那个路径了。这样的路径不建容器，并说明原因。

**19. 容器拿到的必须是看过的那个目录。** 引擎按名字拿工作目录，而名字是能被换掉的：上一级目录是另一个会话的工作目录时，那个会话的命令就做得到。试验十四在 Linux 上用真实引擎重现了，引擎顺着链接挂上了别处的目录。现在有三道：会话记住它的目录名第一次指向哪里，之后指向别处就不再运行命令，和文件工具的做法一致；容器连同目录的设备号和 inode 一起保存，每条命令之前核对，同名的另一个目录会换来一个新容器；从看目录到挂载之间，Windows 上本程序一直开着这个目录的句柄，不许删除，这样谁也挪不动它和它上面的目录，其他系统上做不到这一点，就让容器报出它那里工作目录的编号，对不上就不用。容器答不上来时（镜像里没有 `stat`，或者引擎给的编号自成一套），约束强度降为部分，命令重新逐条询问。

**20. 没有回音的收尾，代价是这个容器。** 收尾是一轮一轮做的。原来超时的那一轮被放弃，接着做下一轮，而引擎可能已经接下了被放弃的那一轮，晚些才运行，到时杀掉的是下一条命令。现在任何一轮没有回音（超时、失败、发不出去），收尾立刻以"可能还有东西没停"结束，容器被放掉。

**21. 放掉容器是一件事，只做一次；只有查到才算没了。** 放掉的过程原来不在任何账上，关闭提供者时不等它，第二个调用者也不等。现在它是容器身上的一个任务，谁来都等同一个结果，等的人被取消也不打断它，关闭时等所有正在进行的。引擎不应答不再被当作"容器没了"：引擎可以配置成自己停了容器还在跑。只有查得到并且查不到这个容器时才算没了，否则警告用户，结果里也不再说"已删除"，而是说留下的东西可能还在运行，并给出删除的命令。

**22. 交给容器的命令保住结尾，不许有 NUL。** 固定的那一行用 `$(cat)` 读命令，结尾的换行会被去掉，而以反斜杠加换行结尾的命令靠这个换行续行。现在读的时候加一个记号，再去掉。带 NUL 的命令各个 shell 的反应都不一样，工具在交出去之前就拒绝。

**23. 真实引擎的测试能在 Linux 上跑了。** 测试在一个容器里以普通用户运行，经套接字用本机的引擎，文件放在一个 Docker 卷里，这个卷在容器里挂在引擎那台机器上的同一个路径上，于是引擎看到的路径和测试看到的一致，和 Linux 主机上一样。只有 Linux 才走的分支（文件归属、套接字、编号核对、把目录换成链接的攻击）由此在本机上实测过，不必等持续集成。真正的 Linux 主机和 macOS 仍然没有试过。

**24. Docker Desktop 空闲时会关掉引擎。** 一段时间没有容器，它就停掉引擎，状态显示为已停止，查询类的命令从缓存里回答。下一次启动容器时引擎被重新拉起，多等几秒。所以隔了一阵之后的第一条命令慢是正常的。Windows 更新升级 WSL 时也会把引擎停掉，那一次要重启 Docker Desktop。

**25. 已知的限制。** 这几条不改，写进指南：受保护的名字如果本身是挂载点，或者指向挂载点之下，它的内容会以只读出现在容器里，而工作目录下的其他挂载是被略去的；Linux 上命令只带用户的主组，靠附加组才进得去的工作目录会被拒绝，拒绝的说法里提到这个可能；工作目录在 WSL 发行版里时，Windows 的句柄管不住它；受保护的链接指进某个一级目录时，那个目录整个只读；会话的目录以它第一条命令时的指向为准。

**26. “模块与接口”一节里有几个名字和做出来的不同。** 那一节是动手之前写的，没有随实现改，以设计文档的第 9.2 和 9.3 节为准。没有单独的 `Containers` 类，容器由提供者 `Docker` 自己保持。`seen_at(cwd)` 做成了 `workdir(session)`，`strength` 和 `facts` 只按会话问，不带工作目录。文件接缝的表叫 `Fs.names`，换路径的函数是 `Fs.here`。权限里登记“经沙箱运行”的工具的表叫 `sandboxed`。`Sandbox.expect` 的参数是会话和调用编号。

**27. 阶段末的正式变异检查卡住过一次，根在事件循环的关闭。** 容器保持的那一组在 Linux 上跑到一个变异体时停了三十多分钟。那个变异体让一条测试失败，测试自己建的提供者在测试体的最后一行才关，失败时走不到。没关的提供者照常工作：会话在收尾时关了，它的巡视就去放掉容器，为此启动 `docker` 程序，事件循环恰在这个程序启动途中被关闭。Python 3.13 之前的版本从这里回不来：接管道的任务和别的任务一起被取消，而等进程结束的等待要到所有管道都关了才算完。测试一旦失败，它自己的时限就不再计时。同一个变异体重试 8 次卡了 1 次。夹具现在把测试期间建的每个提供者都关掉，各给二十秒，再等到没有程序正在启动、每个替身进程都已被循环看到结束。改完之后重试 30 次，没有再卡。

**28. 取镜像的两句话不是一回事。** 真实引擎的那一组漏了一个变异体：把“不取镜像”换成“缺了就取”，测试照样通过。引擎没有这个镜像又不许取时说的是“没有这个镜像”，`docker` 程序准备去取镜像时写的是“本地找不到，去取”。两句原先都被说成“镜像不在本机上，不会为命令取镜像”，对后一句这话不属实。现在只有前一句这样说，后一句照 Docker 的原话说成容器启动不了。程序在不许取镜像时不会写后一句，所以用户看到的没有变化，而真实引擎的测试在镜像会被取的时候会失败了。

**29. 指名工具的放行规则原来只有随机取例的测试碰得到。** 权限的那一组漏了一个：把“一条指名工具、不带模式的规则放行”标成“因为被约束才放行”。仓库的变异脚本让取例的测试每次取同样的例子，那些例子里没有这样的规则。现在有一条确定的测试。

**30. 启动途中被取消的调用方，等启动完成再走。** `process.run` 的调用方在程序还在启动时被取消，原先取消立刻交回去，启动自己继续，建出来的程序由一个回调结束掉，没有人等它。这留下一段没有人负责的时间：测试在这段时间里结束，事件循环来不及看到程序退出，Python 就警告有进程还在运行；程序在这段时间里从主协程返回，就遇上第 27 条说的那个关不掉的循环，二十行的脚本在 Python 3.11.9 和 3.12.15 上每次都能复现。现在调用方等程序建出来、被结束掉、被循环看到退出，再把取消交回去。这通常是一瞬间。启动超过五秒的不等，仍由回调结束，再次被取消的调用方立刻放行。POSIX 上结束这样的程序时，先关闭它的传输再结束进程组里其余的进程：关闭会先问系统程序是否已经结束，对一个已经结束的程序，谁先问谁被告知，事件循环后问时会记一条“退出状态已被读走”并编一个退出码 255。

**31. 实现请 Codex 复查了第二遍，十条意见逐条对着代码核实，全部属实。** 其中九条重要，一条次要，有几条的范围比复查说的窄，有一条比它说的宽。

| 复查的意见 | 核实的结果和改法 |
|---|---|
| 盖在受保护名字上的只读挂载，它的来源在建容器期间可以被换成链接 | 属实，而且不限于复查举的例子：`.git` 是普通目录时同样是一个单独的来源。Windows 上每个来源都开着句柄，全部开好之后再看一遍，和第一遍不同就不建容器；其他系统上让容器连这些来源的编号一起报出来比对 |
| 两个工作目录里同名的会话共用一个容器 | 属实。会话的名字只在一个工作目录里唯一。容器改为按会话本身记账 |
| Windows 上工作目录在 WSL 发行版里时仍然给 `full` | 属实。句柄只在本机磁盘上管用。工作目录不在本机磁盘上（共享、WSL）时强度是 `partial`，问的是 Windows 说的磁盘种类 |
| 容器的设备号自成一套时，只凭 inode 相同就算核对上了 | 属实。原来以为共享只是把每个 inode 挪一个固定的数，靠令牌目录里的两个目录来推，而它们说明不了工作目录所在的文件系统。现在只有容器报的编号正是本机的编号时才比对，否则核对不了，强度是 `partial`。Linux 和 macOS 上的 Docker Desktop 因此会逐条询问 |
| 链接指向的地方在不在工作目录里，是按路径的写法判断的 | 属实，而且不需要有人捣乱：不区分大小写的磁盘上，工作目录的名字换一种大小写写法就会这样。改为按设备号和 inode 逐级往上认，挂载点用磁盘列出的名字 |
| 容器建好之后才出现的套接字永远看不到 | 属实，原来写成了限制。强度为 `full` 时命令不再询问，这条限制比当初重。改为每条命令之前查一遍，直到查到什么为止 |
| 关闭提供者的同时，`run()` 再问一次账本，把部分约束的容器当成了完全约束 | 属实。核对的是手里这个容器，不再问账本 |
| 取消 `close()` 会把它等着的删除和启动一起取消 | 属实，是最后一处等待和等启动的那一处。两处都保护起来 |
| 容器没说话就结束，被当成从未存在 | 部分属实。引擎之后答得上来时由查询决定，这个标记不起作用。它是为引擎根本不在的情形留的，否则每次都会叫用户去删一个没有的容器。现在只有 `docker` 程序自己说没连上引擎、或者引擎没有镜像时才这样认。起初想按退出码 125 判断，实测不行：这台机器上的 `docker` 在没有引擎时以 1 结束，引擎拒绝建容器和丢了正在运行的容器时都以 125 结束 |

**32. 换一个名字就能写进受保护的目录，这是核对上面第五条时自己查出来的，比那十条都要紧。** 只读挂载盖住的是一个名字。在 Windows 的 Docker Desktop 上实测（试验二十二、二十三）：工作目录在 NTFS 上，`.git` 以只读挂着，命令写 `.git/x` 被拒绝，写 `.GIT/x` 成功，`mv .GIT moved-git` 也成功，本机上的目录真的被改了名。系统盘上 `.git` 还有短文件名 `GIT~1`，用它同样写得进去。两个名字在容器里报的设备号和 inode 完全相同，是同一个目录。原因在共享那一侧：名字是 Windows 认的，容器所在的内核给每个写法各建一个目录项，挂载只挂在其中一个上。从第 7 阶段的第一个提交起就是这样，已经发布出去的版本里都有。

想过的办法都不成立。把每种写法都挂上一层：`.columbina` 有几百种大小写写法，再加上短文件名，命令行放不下，也列举不全。把工作目录的根只读挂载、里面的各项分别可写：顶层建不了新文件，原地替换文件也会失败，太多工具因此不能用。让 Windows 一侧拒绝写入：容器经共享访问文件时用的就是用户自己的身份，拦它就是拦用户自己的 git。可写的根目录只要挂进容器，受保护的名字就由本机那一侧去认，这一点绕不开。

所以改的是说法，不是挂载：有东西以只读挂在某个名字上时，本机先看顶层受保护的名字换一种大小写是否还找得到同一个东西，再看被挂载的东西有没有短文件名，有任何一样，强度就是 `partial`，命令照常询问。`read-only` 模式下整个目录只读，不受影响。工作目录里没有 `.git` 和 `.columbina` 时也不受影响。这意味着在 Windows 上，仓库里的命令又要逐条询问了，容器仍然把命令和机器的其余部分隔开，只是放行一条命令也就放行了它去写这两个目录。指南里写明了这一点。

顺带改了一处：容器被放掉之后，会话记着它最后查到的情况，下一个容器建好之前按这个回答强度。否则每换一个容器，第一条命令都会先被放行、再被退回，而在 Windows 上这会成为常态。

## 模块与接口

### `columbina.sandbox`（修改）

基本的类型挪到 `sandbox/base.py`：`Mode`、`Strength`、`SandboxProvider`、`SandboxUnavailableError`，由 `__init__` 原样再导出。`SandboxProvider` 的成员：`shell`，这个提供者运行命令的地方用的 shell，`None` 表示本机的；`strength(session, cwd)`；`seen_at(cwd)`，命令看到的工作目录的路径，与本机相同时是 `None`；`facts(session, cwd)`，给模型的几行；异步的 `run(argv, *, session, mode, cwd, stdin, timeout_seconds, overflow, max_overflow_bytes, expected)`，交回 `process.Completed`；异步的 `close()`。`Sandbox` 相应地有 `run`、`shell()`、`strength(session, cwd)`、`seen_at(cwd)`，以及 `expect(call_id, strength)`：守卫记下期望，`run` 取走它交给提供者。配置多一项 `docker`。

### `columbina.process`（修改）

`run` 多一个参数 `before_stop`：一个异步函数，拿到"程序已经退出"的事件。程序超时或者调用被取消、而程序还没有退出时，先等它返回，再停掉程序。它自己不被取消打断，有时限。

### `columbina.builtin_tools.shell`（修改）

三种写法各是一个 `Flavour`：名字、拆分器、描述、给模型的一行、把命令变成 `argv` 和输入的函数、命令的上限。`POWERSHELL` 只在 Windows 上有，`BASH` 和 `BASH_ELSEWHERE` 在每个平台上都有。`NAME` 仍然是本机那一种的名字。`apply` 按 `sandbox.shell()` 选写法，选了别处的 shell 时不要求本机装着 shell。工具向权限插件登记拆分器，并登记自己经沙箱运行。

### `columbina.sandbox.docker`（新建）

纯函数：`found(path, cwd)` 在 `PATH` 里找程序；`supported(info)` 读 `docker info` 的回答；`kept(...)` 给出启动容器的 `argv`；`mounts(mode, cwd, target)` 给出挂载，来源都核对过；`quoted(path)` 按 `--mount` 的规则加引号；`called(...)` 和 `ended(...)` 给出运行和收尾的 `argv`；`sockets(cwd, limit, seconds)` 找套接字；`unavailable(code, said)` 把 Docker 的失败变成给人看的一句话。三段 sh 是模块里的常量。

`Containers` 保持容器：`async held(session, mode, cwd)` 交回这个会话可用的容器，没有就启动，模式或目录变了就换；`async retire(container, why)` 放掉并确认；`async close()` 放掉全部。`Docker` 是提供者。

### `columbina.permissions`（修改）

`decide` 多一个参数 `held`。`Permissions.confined` 是经沙箱运行的工具名的注册表。守卫为登记过的工具取沙箱按会话给的强度，因为它而放行时调用 `sandbox.expect`。

### `columbina.fs`（修改）

`Fs.seen` 是一张注册表，登记的函数拿到工作目录，交回它在命令那边的路径或 `None`。`Fs.locate` 在定位之前把以这个路径开头的写法换成工作目录里的相对路径。

### 清单、启动器与持续集成（修改）

`base.yml`：`sandbox` 的 `provider` 取 `${COLUMBINA_SANDBOX:-none}`。启动器给 `run`、对话和 `serve` 加选项 `--sandbox NAME`。作者同意之后，`ci.yml` 给 Ubuntu 的机器设 `COLUMBINA_REQUIRE_DOCKER=1`，并在测试之前取两个小镜像。

### 测试

`tests/support/fake_docker.py` 是替身。`tests/sandbox/test_docker.py` 用替身，`tests/sandbox/test_docker_real.py` 用真实的引擎，`tests/apps/test_sandbox_run.py` 是结束标志的五条，`tests/live/test_deepseek_sandbox.py` 是真实服务的那一条。
