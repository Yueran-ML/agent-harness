# Columbina 第 7 阶段实施计划：容器沙箱

**Goal:** Agent 运行的命令在一个容器里执行。容器里只有工作目录，默认没有网络，命令能做的事不超过会话的沙箱模式允许的范围。这样的命令不必再逐条问人。

**Architecture:** 沙箱接缝的提供者不再只是包装命令，而是自己把命令运行完。新的提供者 `docker` 为每个工作目录和模式保持一个容器，容器的寿命系在本程序握着的一根管道上。每条命令是一次 `docker exec`，在容器里有自己的会话，结束、超时或取消之后，它留下的进程被一并停掉。命令在哪里运行，shell 工具就用哪里的 shell：容器里是 bash，在 Windows 上也是。

**Tech Stack:** 只用 `docker` 命令行，不加 Python 依赖。本机是 Docker Desktop 4.94.0，引擎 29.8.2，后端是 WSL 2。

设计依据是 `docs/plans/2026-10-09-columbina-design.md` 的第 9.1、9.2、9.3 节。本计划与这些章节不一致的地方列在"与设计文档的差异"一节，阶段结束时把设计文档改成一致。

## 结束标志

设计文档 15.2 给本阶段的结束标志是：shell 工具在容器内执行，断网。落到测试上是下面五条，前四条用真实的引擎，经 `columbina run` 的命令行和脚本化的模型运行，没有引擎的机器上跳过。

1. **只碰得到工作目录。** 命令在工作目录里写的文件，本机上看得到。命令写到工作目录之外的东西，本机上没有任何变化。`read-only` 模式下工作目录写不进去。`workspace-write` 模式下 `.git` 写不进去。
2. **没有网络。** 命令去连一个地址，连不上。
3. **不再逐条询问。** 没有人可问的运行里，命令照样执行，因为它被完全约束住了。有一条询问规则管着它时，它仍然要问。容器有网络时，它也仍然要问。
4. **停得干净。** 超时的命令连同它启动的进程一起被停掉。运行结束之后，没有容器留下。
5. **引擎不在时不放行。** 用测试替身模拟引擎不在、镜像不在、镜像里没有 bash 三种情形：命令的结果是 `SANDBOX_UNAVAILABLE`，写明该怎么办，命令没有改在本机上运行。

另有一条对真实服务的测试：模型被告知命令在一个 Linux 容器里运行之后，用容器里的 bash 把第 3 阶段的小仓库修好。没有密钥、没有引擎或者没有镜像时跳过。

## 需要作者决定的三件事

下面三件事有合理的缺省，计划按建议写。作者不同意时改一个常量或一处判断即可。

| 事情 | 建议 | 理由 |
|---|---|---|
| 缺省的镜像 | `python:3.12` | 它有 git、编译器和 curl。`-slim` 的版本没有 git，模型看不了改动。镜像约 1 GB，程序不替用户下载，缺少时报错并写明 `docker pull` 的命令 |

| 缺省是否断网 | 断网 | 设计文档如此。要装依赖时在配置里写 `network: bridge`，这时命令重新变成逐条询问 |

## 范围

本阶段做的：接缝改成由提供者运行命令。shell 工具按命令运行的地方选 shell。提供者 `docker`：容器的保持、按模式挂载、运行与停止、失败时的说法。权限里"被完全约束的命令不问"。告诉模型命令在哪里运行。Windows 上文件工具认得容器里的工作目录路径。清单、命令行选项、测试替身、真实引擎的测试、文档。

本阶段不做的：设计文档里标为可选的 `bwrap`。`columbina doctor`。按域名放行的网络。替用户下载或构建镜像。把文件工具也搬进容器。项目自带的沙箱配置：镜像是别人写的程序，由项目来指定等于运行别人的代码，要有钩子那样的信任机制，留到以后。

## 先做的试验

写计划之前在本机做了六个试验，脚本留在草稿目录里。两个参考实现都用各自系统的原生沙箱，没有用容器的，所以这一阶段没有可以照着做的地方。

**试验一：一条命令要多久。**

| 做法 | 用时 |
|---|---|
| `docker version` | 0.10 秒 |
| 每条命令一个新容器（`docker run --rm`） | 0.4 到 0.6 秒 |
| 启动一个留着的容器 | 0.3 秒 |
| 在留着的容器里 `docker exec` | 0.11 秒 |
| 删除容器 | 0.16 秒 |

**试验二：把 Windows 的目录挂进容器。** 目录的路径里有空格和中文，作为一个参数传给 `docker` 就能挂上。

| 情形 | 结果 |
|---|---|
| 容器里看到的文件 | 属主是 root，权限是 777。回车换行原样。中文文件名正常 |
| 容器里写的文件 | 本机上看得到 |
| 容器里建的符号链接 | 容器里是链接。本机上看得到名字，但 `exists()` 说它不存在 |
| `Case.txt` 和 `case.txt` | 是同一个文件 |
| 以另一个用户运行（`--user 1000:1000`） | 写得进挂载的目录。它的 `HOME` 是 `/`，写不进去 |
| 只读挂载 | 写不进去，"Read-only file system" |
| 可写的挂载里再把 `.git` 只读挂一层 | `.git` 里写不进去，改名和删除也都失败 |
| 速度 | 356 个文件，`find` 用 0.32 秒，`grep -r` 用 0.5 秒。本机上同样的遍历用 0.02 秒 |

**试验三：在留着的容器里运行命令。** 退出码传得出来，标准输出和标准错误是分开的，输入传得进去，不是文字的字节原样出来，几兆字节的输出没有问题。`--network none` 之下名字解析不了，地址连不上，回环地址还在。最要紧的一条：把本机的 `docker` 客户端杀掉，容器里的命令照样在跑。`python:3.12-slim` 里没有 `ps`，有 `kill`、`setsid`、`timeout` 和 `grep`。

**试验四：把一条命令留下的东西停干净。** 命令用 `setsid` 启动，把自己的会话号写下来。停的时候在 `/proc/*/stat` 里找会话号相同的进程，逐个杀掉，用时 0.10 秒。命令自己结束之后留在后台的进程也能这样停掉。一个自己另开会话的进程逃得掉，它活到容器消失为止。

**试验五：出错时 Docker 怎么说。**

| 情形 | 退出码 | 说法 |
|---|---|---|
| 引擎不在 | 1，0.06 秒 | "failed to connect to the docker API at ..." |
| 镜像不在，又不许下载 | 125 | "No such image" |
| 容器不在 | 1 | "No such container" |
| 要运行的程序不在，或者工作目录不在 | 127 | "OCI runtime exec failed"，写在标准输出上 |

所以单看退出码分不清是 Docker 出了错，还是命令自己以这个码结束。另外，`--cap-drop ALL` 之下容器里的 root 不能改属主，也不能挂载。`--pids-limit` 到限时 `fork` 失败，bash 会重试 30 秒。

**试验六：容器的寿命。** 用 `docker run --rm -i ... cat` 启动容器，本程序握着通向它标准输入的管道。关掉管道、杀掉 `docker` 客户端、把握着管道的程序整个杀掉，三种情形下容器都在 0.2 秒内消失，里面的进程一起结束，什么都没有留下。

## 设计决定

### 接缝与 shell

**1. 提供者自己运行命令。** 现在的接缝是 `confine(argv)`，提供者交回一条包装过的命令，由 shell 工具去运行。容器做不到这样：运行之前要先有容器，运行之后要把命令留下的进程停掉，客户端被杀掉时这一步尤其不能少（试验三）。所以接缝改成异步的 `run`，提供者拿到命令、会话、模式、工作目录、输入和时限，交回运行的结果。提供者 `none` 的 `run` 就是原来 shell 工具里的那次 `process.run`。

**2. 命令在哪里运行，就用哪里的 shell。** 提供者说明它运行命令的地方用什么 shell：`none` 不说，用本机的；`docker` 说 `bash`。shell 工具登记的是这个 shell 的工具，所以在 Windows 上用 `docker` 时，工具叫 `bash`，不叫 `powershell`。工具的名字仍然在程序启动时定下，一次运行里不变。为 `powershell` 写的规则管不到容器里的 bash，`run(...)` 这种不指名工具的规则照常管用。

**3. 容器里的命令经标准输入交进去。** Windows 的命令行至多 32767 个字符，命令要先经过本机的 `docker.exe`，写成参数会被这个上限卡住。所以容器这一路的 bash 用一行固定的话启动，由它从输入里读出命令再执行，命令自己的输入接到 `/dev/null`。这与 PowerShell 那一路的做法相同。命令至多 120000 字节，因为容器里它最终是 bash 的一个参数。

### 容器

**4. 一个工作目录和一种模式一个容器。** 设计文档写的是每个会话或任务一个。子代理有自己的会话，按会话分，子代理就看不到父 Agent 刚装好的东西，还要各等一次启动。按工作目录和模式分，同一个目录里的会话共用一个容器。模式变了要换一套挂载，所以是另一个容器。容器在第一条命令到来时才启动。

**5. 容器的寿命系在一根管道上。** 容器的主进程是 `cat`，读本程序握着的管道（试验六）。程序正常结束时关掉管道。程序被杀掉时，系统替它关。两种情形下容器都随即消失，不需要记下容器的名字，也不需要下次启动时清理。

**6. 启动容器的参数。** `docker run --rm -i --pull never --init --name columbina-<随机> --label columbina=1`，加上 `--cap-drop ALL`、`--security-opt no-new-privileges`、`--pids-limit`，配置里给了内存和处理器的上限时再加这两项。入口换成一小段 sh：建好放记录的目录，查一下有没有 bash 和 `setsid`，印出一行 `ready` 或 `missing`，然后变成 `cat`。程序读到 `ready` 才把容器交出去用。

**7. 不替用户下载镜像。** `--pull never`。镜像不在时，命令的结果写明镜像的名字和 `docker pull` 的命令。一条命令背后悄悄下载一个吉字节的镜像，既慢又出乎意料。

**8. 按模式挂载。**

| 模式 | 工作目录 | 另外 |
|---|---|---|
| `read-only` | 只读 | |
| `workspace-write` | 可写 | 工作目录顶层已有的 `.git` 和 `.columbina` 各再只读挂一层 |
| `danger-full-access` | 可写 | 没有只读的那一层 |

只有工作目录被挂进去。`.git` 是一个文件时（工作树），把这个文件只读挂上。启动容器时还不存在的 `.git` 不挂：给不存在的路径做挂载点，Docker 会在本机的目录里把它建出来。挂载用 `--mount`，路径里有逗号或引号时按它的规则加引号。

**9. 完全访问模式下，命令仍然在容器里。** 提供者决定命令在哪里运行，模式只决定挂载。配置了 `docker` 的程序不会因为模式变了就把命令放到本机上去跑。想让命令在本机上运行，用提供者 `none`。

**10. 网络是另一个开关，打开之后强度降一档。** 缺省 `--network none`。配置里写 `network: bridge` 时用 Docker 缺省的网络。它不随模式变。有网络的容器管得住命令写什么，管不住命令把读到的东西发出去，所以这时提供者报的强度是 `partial`，不是 `full`。第 18 条因此不适用，命令照旧要问。

**11. 容器里的身份和环境。** Linux 上以本机用户的编号运行（`--user`），否则命令在工作目录里建的文件在本机上属于 root。Windows 和 macOS 上挂载的属主是虚拟出来的，以 root 运行。环境里只有 `HOME`、`LANG=C.UTF-8`、`TERM=dumb` 和配置里写明的变量，`HOME` 指向容器自己的 `/tmp` 下的一个目录。本程序的环境不带进去，密钥到不了容器里。

**12. 挂载点。** POSIX 的本机上，工作目录挂在容器里的同一个路径上，模型在命令的输出里看到的路径和文件工具用的路径是一回事。Windows 上做不到，挂在 `/workspace`。

### 运行一条命令

**13. 每条命令有自己的会话，并留下记录。** 命令是 `docker exec -i -w <目录> <容器> setsid sh -c <包装> <编号> <命令…>`。包装把会话号写进容器里的一个文件，运行命令，再把退出码写进另一个文件。编号每次调用都不同。

**14. 命令结束之后总要收一次尾。** 再做一次 `docker exec`：把那个会话里还活着的进程都杀掉，读出记下的退出码，删掉两个文件。命令正常结束、超时、调用被取消，三种情形都做，取消时这一步不被打断，自己有十秒的时限。这样工具的那句承诺照旧成立：命令启动的进程随这次调用一起结束。每条命令因此多 0.1 秒。

**15. 退出码以容器里记下的为准。** 记下了，命令就是运行过的，这个数就是它的退出码。没有记下又没有超时，是 Docker 自己出了错：结果是 `SANDBOX_UNAVAILABLE`，带上 Docker 说的话。容器不在了的时候，把它从表里拿掉，下一条命令会启动一个新的。

**16. 收尾做不成时，放掉整个容器。** 收尾在时限内没有回答，就关掉那根管道。容器连同里面的一切一起消失，这条命令的结果里写明：容器被放掉了，装在里面的东西没有了。

**17. 逃出会话的进程。** 自己另开会话的进程不在那次收尾的范围里（试验四）。它活到容器消失。容器是外面的那道边界，这一点写进文档。

### 审批与告知

**18. 被完全约束的命令不问。** `decide` 多一个参数，说明这次调用被约束的强度。顺序是：拒绝规则，本会话内的同意，询问规则，放行规则，完全访问，然后是这一条，最后才是询问。强度只对经沙箱运行的工具有意义，shell 工具向权限插件登记自己是这样的工具。MCP 服务器的工具在本机上运行，不受容器约束，照旧要问。

**19. 告诉模型命令在哪里运行。** 运行时上下文里原有"命令由谁运行"和"命令被约束到什么程度"两行。提供者再给出几行：命令在一个 Linux 容器里运行，用的是哪个镜像；容器里只有工作目录，在哪个路径上；有没有网络；装在工作目录之外的东西，程序结束就没有了。

**20. Windows 上文件工具认得容器里的路径。** 命令的输出里是 `/workspace/src/app.py`，模型多半会原样拿去读。文件接缝多一张表：某个前缀在这个会话里就是工作目录。提供者在 Windows 上登记 `/workspace`。以这个前缀开头的路径按工作目录里的相对路径处理，其余的规则不变。

**21. 引擎不在时，在第一条命令上说。** 程序启动时不等 Docker：`sessions list` 这样的命令用不着它，Docker Desktop 也可能晚一点才启动。被选中的提供者是 `docker` 时，启动之后在后台问一次引擎，问不到就记一条警告。

### 配置与测试

**22. 提供者的插件总是加载，用不用由一个名字决定。** `base` 清单加一项 `sandbox-docker`。它只登记提供者，被选中之前不碰 Docker。选它的办法有三个：环境变量 `COLUMBINA_SANDBOX=docker`，命令行选项 `--sandbox docker`，或者在补丁文件里写 `provider`。配置项如下。

| 键 | 含义 | 缺省 |
|---|---|---|
| `program` | `docker` 程序 | `docker`，在路径里找 |
| `image` | 镜像 | `python:3.12` |
| `network` | `none` 或 `bridge` | `none` |
| `env` | 给容器里的命令的变量 | 空 |
| `pids_limit` | 进程数的上限 | 2048 |
| `memory`、`cpus` | 内存和处理器的上限 | 不设 |
| `start_timeout_seconds` | 等容器就绪的时限 | 60 |

**23. 测试替身是一个假的 `docker` 程序。** 持续集成的六台机器里只有 Ubuntu 的两台有能跑 Linux 容器的引擎，覆盖率却要每台都是 100%。所以提供者的每一行都要能在没有引擎的机器上走到。替身是一个 Python 程序，认得 `version`、`run` 和 `exec` 三个子命令：`run` 印出就绪的一行并读输入直到结束，`exec` 在本机运行给它的命令并照包装的约定写下会话号和退出码，收尾的那次 `exec` 把记下的进程杀掉。它可以按测试的要求装作引擎不在、镜像不在、镜像里没有 bash。提供者的测试给它的命令是 Python 写的小程序，不依赖本机有没有 bash。

**24. 真实引擎的测试说明那几段脚本是对的。** 替身不运行包装和收尾的 sh 脚本，这两段只有真实的引擎能检验。这些测试在引擎不回答的机器上跳过，用到的小镜像不在时自己去取，取不到也跳过。它们在本机和持续集成的 Ubuntu 上运行。

## 与设计文档的差异

1. 接缝是 `run`，不是 `confine`。提供者运行命令，不只是包装。原因见第 1 条。
2. 容器按工作目录和模式分，不按会话或任务分。原因见第 4 条。
3. 用 `docker` 时命令工具是容器里的 bash，在 Windows 上也是。设计文档没有写这一点。
4. 完全访问模式下命令仍然在容器里。设计文档没有写。
5. 被完全约束的命令不问。设计文档只写了强度为 `none` 时一律要问。
6. Windows 上文件工具认得 `/workspace` 这个前缀。设计文档没有写两套路径的问题。

## 模块与接口

### `columbina.sandbox`（修改）

`SandboxProvider` 的成员变成：`strength`；`shell`，这个提供者运行命令的地方用的 shell，`None` 表示本机的；`seen_at(cwd)`，命令看到的工作目录的路径，与本机相同时是 `None`；`facts(cwd)`，给模型的几行；异步的 `run(argv, *, session, mode, cwd, stdin, timeout_seconds, overflow, max_overflow_bytes)`，交回 `process.Completed`。`Sandbox` 相应地有 `run`、`shell()`、`seen_at()`，去掉 `confine` 和 `Confined`。`Sandbox.selected` 是配置里点名的提供者。运行时上下文的监听器把提供者的 `facts` 加进去。

### `columbina.builtin_tools.shell`（修改）

三种写法各是一个 `Flavour`：名字、拆分器、描述、给模型的一行、把命令变成 `argv` 和输入的函数、命令的上限。`POWERSHELL` 和 `BASH` 是本机的两种，`BASH_ELSEWHERE` 是经输入交命令的那一种。三者在每个平台上都能导入。`NAME` 仍然是本机那一种的名字。`apply` 按 `sandbox.shell()` 选写法，选了别处的 shell 时不要求本机装着 shell。工具向权限插件登记拆分器，并登记自己经沙箱运行。

### `columbina.sandbox.docker`（新建，插件 `sandbox-docker`）

纯函数：`kept(config, mode, cwd, name, ...)` 给出启动容器的 `argv`；`mounts(mode, cwd, target)` 给出挂载；`quoted(path)` 按 `--mount` 的规则加引号；`called(name, directory, call, argv)` 和 `ended(name, call)` 给出运行和收尾的 `argv`；`unavailable(code, said)` 把 Docker 的失败变成给人看的一句话。两段 sh 脚本是模块里的常量。

`Containers` 保持容器：`async held(mode, cwd)` 交回一个可用的容器，没有就启动；`drop(container)` 放掉一个；`async close()` 放掉全部。`Docker` 是提供者：`run` 先要到容器，再运行命令，最后收尾。插件的 `apply` 登记提供者和文件接缝的前缀，卸载时关掉所有管道。

### `columbina.permissions`（修改）

`decide` 多一个参数 `held`。`Permissions.confined` 是经沙箱运行的工具名的注册表。守卫为登记过的工具取沙箱的强度，别的工具按 `none`。

### `columbina.fs`（修改）

`Fs.seen` 是一张注册表，登记的函数拿到工作目录，交回它在命令那边的路径或 `None`。`Fs.locate` 在定位之前把以这个路径开头的写法换成工作目录里的相对路径。

### 清单与启动器（修改）

`base.yml`：`sandbox` 的 `provider` 取 `${COLUMBINA_SANDBOX:-none}`，加一项 `sandbox-docker`。启动器给 `run`、对话和 `serve` 加选项 `--sandbox NAME`。
