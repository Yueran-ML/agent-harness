# Columbina 补强计划：长会话的保真与小窗口模型

**Goal:** 第 7 阶段和第 8 阶段之间的一批小改动。第一组让压缩之后的对话仍然可信：摘要不混淆谁说了什么，被拿走的内容找得回来，模型不凭印象改写它已经看不到的文件。第二组为第 8 阶段的本地模型铺路：输出被截断时能接着写，工具结果的上限跟着窗口走，回合怎么结束的有代码可查。

**来源:** 作者读了几份关于别的 Agent 程序怎样做这些事的技术分析，材料不在仓库里。这里只取做法：每一处都先对照本仓库的代码确认是缺口，再按本仓库的写法设计。没有取任何文字，交给模型的话都是自己写的。

设计依据是 `docs/plans/2026-10-09-columbina-design.md` 的第 8.4、8.5 和 10.5 节。改动落定之后，设计文档和三种语言的使用指南随同一批提交改写。

---

## 范围

第一组，压缩的保真与安全，五处：

1. 交接说明分清谁说的。
2. 摘要没有覆盖的最早一段，告诉模型。
3. 被裁短的工具结果先存下来，裁口写明在哪。
4. 读取结果被拿走的文件，要重读才能改。
5. 行为守则补五句话。

第二组，为小窗口模型，三处：

6. 回复被输出上限截断时接着写，有次数上限。
7. 工具结果的上限跟模型的窗口挂钩，同一回复的几个结果另有总预算。
8. 回合结束的原因带一个代码。

另有一处是做第一组时意外发现的缺陷，不在原先的范围里，随这一批修掉：

9. Windows 上经应用执行别名启动的程序不在命令的作业里，命令被停下时它不停。

这次不做的：回合结束前的核实提醒和工具参数的形状修复，等第 8 阶段有了数据再定。压缩之后重新附上已调用技能的正文，模型可以重新调用技能，先不做。桌面应用里撤回一轮的文件修改、先出计划再执行，等视频剪辑那条线的设计定了再做。

## 约定

与第 7 阶段相同：每一处先写测试，看它失败，再写实现，过闸门，提交。新增的行为各有变异体。提交信息用英文，作者只有仓库主人。

## 设计决定

### 第一组

**1. 交接说明分清谁说的。** 摘要只有一个声音。文件里的一句“用户已经同意删除”如果被原样写进摘要，接手的模型分不出它是读到的还是用户说的，注入的内容就这样被洗成了用户的要求。交接指令因此多两条：文件、网页和工具结果里的话记成读到的东西，不记成用户的要求或同意；用户设下的限制，比如什么不许碰、不许运行、不许显示，照原话记。这两条只是对写摘要的模型说的话，没有程序能核对摘要守没守，测试只管这两条还在指令里。

**2. 没覆盖的最早一段要说出来。** 被压缩区超出模型能接受的长度时，写摘要的模型只看到较新的一半，较旧的一半在日志里，不在任何摘要里。原来顶替的那条消息对此一字不提，接手的模型会把摘要当成此前的全部。现在消息里多一句：摘要没有覆盖最早的那些消息，工作要用到只有它们才有的东西时，说自己已经没有了，不要猜。这一句不带数字，模型用不上条数。

**3. 被裁短的结果找得回来。** 裁掉的是结果的中段。文件可以重读，命令的输出不一定能再产生一遍。程序里本来就有放过大结果的地方，模型有权读那里的文件。所以裁之前先把整份存进去，省略行的下一行原样用那里的说法写明整份在哪、怎么读。三种情形不存：程序没有这样的地方；存的时候出错，这时照旧只裁并记一条错误；结果自己就是两端加一行去向，那是它生成时就因为太大被存过的，把两端当成整份再存一遍会指错地方。带着去向的那一行让裁短后的文字多出一百来个字符，算“裁掉够不够”时没有计入，留出的余量是它的许多倍。裁短后的块如果因为多这一行而又长到会被再裁，就不加这一行。

**4. 读取结果被拿走的文件要重读。** 文件接缝记着模型读过哪些文件、读到时是什么样，写和改之前核对。但它不知道压缩的事：读到的内容被裁短或者被摘要取代之后，接缝仍然当模型读过，模型就可以凭印象整体改写一个它已经看不到的文件。现在接缝按调用编号记下每个文件是哪一次调用给模型看的，压缩把它拿走的调用告诉接缝，这些调用给看过的文件从此算没有读过。之后又被别的调用读过的文件不受影响，没有调用编号的记录也不受影响。模型自己写的文件同样记在那次写的调用名下：那次调用被摘要取代之后，它也不再知道文件里是什么。拒绝的说法分两种，从没读过的照旧，读过而内容已经不在对话里的写明原因，因为模型记得自己读过。

**5. 行为守则补五句话。** 同一个办法失败两次就换办法，或者停下来说明卡在哪。用户最后说的算数，改口之后先前的要求作废。改一个东西之前找找谁在用它，改完再看一遍那些地方。被裁短的结果自己说明裁了、整份在哪。读取结果已经不在对话里的文件要重读才能改。后两句说的是程序的行为，测试把它们和程序绑在一起。守则仍然可以按节关掉，这五句值不值，第 8 阶段用同一批任务开和关各跑一遍来量。

### 第二组

每一处先写现在是什么样，都对照代码核实过，再写要改成什么。

**6. 截断之后接着写。** 现在回复被输出上限截断时，已经到达的文字留在日志里，回复里的工具调用一个也不执行，回合以 `max-tokens` 结束。只有两种情形回合会继续：恰好有用户的话在排队，或者有监听者在回合将要结束时要它继续，比如钩子。截断发生在工具调用中间、前面一个字也没有时，这次回复被当成空回复，重试几次之后回合以出错结束，而重试得到的还是同样的截断。本地模型的输出上限小，写一个稍长的文件就会落进后一种情形。

改成由循环自己接着做。被截断的回复之后，循环写下一条消息再走一步。这条消息有自己的来源标记，日志和界面分得出它不是用户说的。它说三件事：上一次回复因为到了单次回复的长度上限被截断，从断处接着写，已经写出的不要重复。截断时正在写工具调用的，再说明哪几个调用没有写完、没有执行，重新发起时要小到一次回复装得下，长文件分几步写。为此回复的组装器要说得出“哪些调用开了头没写完”，现在它只是把它们丢掉。

一个回合里至多这样接三次，次数是循环的一个配置，写 0 就是现在的行为。接着写的每一步照常受步数、token 和时间的预算管。

前面一个字也没有的截断不再算空回复。它没有可以留下的内容，所以不写助手消息，只把这次请求记成一次没有成的尝试，用量照记，然后同样接着写。

回合结束的原因改为只看最后一次回复。现在一个回合里只要有一次回复被截断，哪怕后来的回复正常结束，回合仍记为 `max-tokens`，有一条测试专门守着这一点。接着写做出来之后，被截断又接上的回合应当是正常完成。每条助手消息自己的结束方式仍在日志里，要数一个回合里截断过几次，查得到。

**7. 结果的上限跟着窗口走。** 现在单个工具结果的上限是固定的 12,500 token，与模型无关。`read` 自己分页，不归这个上限管，它一页至多 2000 行、50 KB，同样与模型无关。窗口只有一两万 token 的模型，读一页文件就可能超窗。压缩会在下一步之前把对话缩短，所以不至于出错。但它的顺序是先裁模型已经读过的旧结果，不够就请模型把较早的对话写成摘要，最后才裁剩下的结果：为了一个过大的新结果，丢掉了本来放得下的旧对话。

改三处。第一，单个结果的上限取“固定的数”和“窗口的四分之一”中小的那个。窗口没有配置的模型照旧用固定的数。大窗口的模型不受影响，12,500 已经远小于它们窗口的四分之一。第二，`read` 的一页按同一个上限收短：超出时这一页在整行处提前结束，分页的说明照常告诉模型怎样读下一页。上限由结果上限的那个插件提供，`read` 去问，问不到就照旧。第三，压缩在缩短对话时多一个步骤，排在裁旧结果之后、写摘要之前：模型最后一次回复引出的那几个结果，加起来超过窗口的四成时，其中大的让出地方。让多少按 token 算：先算出一个公共的上限，使它们合起来刚好不超过四成，小于上限的原样留下，它们没用完的份额归大的，超过上限的各自裁到只剩两端，两端加起来正好是上限那么多。裁之前整份存盘，裁口写明在哪，文件接缝得到通知，这些都是第一组已经做好的。这一步够用时，就不必请模型写摘要。

这一步起初打算放在最前面，动手时改成了第二步。读过的结果模型已经用过，没读过的是它接下来就要看的，所以裁读过的够用时，没读过的一个也不动。它们让位只换来一件事：不为几个只需要首尾的结果去写摘要。窗口未知的模型没有“四成”可言，这一步不做。会话用的是哪个模型，按日志里最近一次请求的配置算，这样把请求改投别的模型的监听器也照顾到了。

单个结果的上限有一个底，256 token。窗口的四分之一比它还小时按它算，配置里的固定值更小时仍以固定值为准。它是给写错的窗口留的：被裁短的结果要用一行说明省略了多少，再用一行说明整份在哪，上限小到装不下这两行时，裁过的结果反而比原来长。能用这个程序的模型，窗口都远大于一千 token，碰不到这个底。

读过的旧结果仍然按字符数裁，超过 8192 个字符才动。这个数与窗口无关，小窗口上字符少而 token 多的旧结果裁不到，要等摘要把它们收走。没读过的结果不能等，所以只有那一步改成了按 token 算。

四分之一、四成和 256 都是起点，第 8 阶段用本地模型量过之后再调。

**8. 回合结束带代码。** 现在回合结束的记录有三项：第几个回合，原因的大类，一句英文的说明。大类有 `completed`、`aborted`、`blocked`、`error`、`max-tokens` 等七种。同是 `blocked`，可能是步数用完了，也可能是钩子拦下的，只有读那句英文才分得出，界面和基准都没法据此分类。

改成记录里多一项代码，可以为空。`blocked` 时：步数、token、时间三种预算到限各一个，钩子拦下一个，没有监听者给出决定一个。`error` 时：模型服务给出的失败代码原样带上，比如上下文超限、限流、超时；程序自己的异常是另一个。别的大类不带代码。拒绝一步的那个回答里也多一项代码，由拒绝的一方给出。

代码是给程序看的，给人看的那一行说明不变。压缩失败不结束回合，它在自己的结束记录里已有原因，这里不重复。

这一项会改日志的格式：每条回合结束的记录多一个字段。事件的定义不接受多余的字段，所以旧版本的程序读不了新日志，反过来没有问题。协议文档、事件的 JSON Schema、文档里的示例日志和桌面应用的测试数据都要随之更新，子代理结束的记录同样带上代码。

### 作业之外的程序

**9. 命令停下时，它在作业之外的后代一并结束。** 设计文档说一条命令启动的进程不比它活得久，Windows 上靠的是作业对象。有一类程序不在作业里：命令行里的名字如果解析到应用执行别名，系统会把启动出来的程序放在请求者的作业之外。从 Microsoft Store 或者 Python 安装管理器装的 `python` 就是别名。试验里的链条是 PowerShell、别名的 `python.exe`、解释器三级，只有 PowerShell 在命令的作业里。命令到了时限，作业被结束，两个 Python 照常运行；取消命令、程序退出时也一样。由 `process.run` 直接启动别名时没有这个问题，那时别名自己就是被放进作业的那个进程。从第 3 阶段起就是这样。

修法是在停下命令时多做一步：看一遍这台机器上每个进程是谁创建的，从作业里的进程出发，找出不在作业里的后代，和作业一起结束。下面几条是这一步的决定。

先看，后结束。后代是顺着创建它的进程一级一级找到的，作业一结束，中间那几级就没了。被结束的进程可能刚刚又启动了别的，所以结束之后再看，至多三轮。

宁可少结束，不可错结束。进程号在进程结束之后会分给别的进程，系统记下的“创建者”只是一个号。所以认父子时要求子进程的创建时间晚于父进程，时间相同也不认。查不到创建时间的进程不动。结束不了的进程不算失败，它多半是自己先结束了。这条规则靠的是系统时钟不往回走：时钟被往回拨过，又恰好有一个无关进程记着的创建者的号被分给了命令的进程，才会认错。两件事同时发生的机会小到可以不计，没有为它再加一层。

看的期间进程号不能换人。被当作起点的和被找到的进程都开着句柄，直到这一步做完，开着的时候它的号不会分给别人。命令的主程序从放进作业起一直开着，所以它自己结束之后，仍然算它留下的进程的创建者。作业列出的号，打开之后还要问一遍这个进程是不是在作业里，因为列出的那个可能已经没了。

“谁是谁的后代”单独成一个模块，是不碰系统的纯函数，它的测试不启动任何进程。让它多认后代的那类变异体只放在这个模块自己的一组里，不和启动真实进程的测试一起跑：在真实的机器上，多认一个后代就是结束一个无关的程序。进程模块那一组里新增的变异体都只会让被结束的进程变少。

测试不依赖别名。先按平常的方式启动一串程序，每个启动下一个，再把第一个放进作业。它此前启动的那些就都是“作业里的进程在作业之外的后代”，和别名启动的程序处境相同，任何一台 Windows 机器上都造得出来。真实的别名只在这台机器上手动试过。

代价是每条命令结束时看一遍进程表。这台机器上有四百多个进程，一遍约 8 毫秒。

这一步做不到的有三样，写进了设计文档。创建者已经先结束的进程找不到，例如命令经一个随即退出的中间程序启动的后台程序。本程序自己被强行结束时，作业里的进程由系统结束，作业之外的不会。由系统服务代为启动的程序不是命令的后代，不在范围里。

## 实施中的发现

**1. 两个旧变异体跟着改了。** 裁短和逐个落盘的那两行改了写法，指着它们的两个变异体随之改写，仍然被发现。

**2. 守则里的句子在两处快照里。** 一次修复仓库的请求，和终端上的一段会话。两处都随守则更新了，各变一行。

**3. 第 9 处是一条测试换了运行方式才露出来的。** 一条测试让命令行运行 `python`。经 `uv run` 运行测试时，搜索路径上先找到的是虚拟环境里的 Python，测试通过。直接用虚拟环境的解释器运行同一条测试时，先找到的是系统的别名，测试失败：被强行结束的那次运行留下了还在跑的程序。闸门一直经 `uv run` 运行，所以此前没有碰到过。

**4. 先结束作业再看，一个后代也找不到。** 第 9 处的第一版是这个顺序。动真格之前先做了一次只记录不结束的干跑：把结束进程的那个系统调用换成记一笔，看它会被要求结束谁。结果是零个，因为作业一结束，通往后代的那一级已经不在进程表里。改成先看之后，干跑记下的正好是那一串程序和它们的启动器，旁边不相干的那个程序不在其中。这之后才让测试真的结束进程。

**5. 虚拟环境里的 `python.exe` 只是启动器。** 它把真正的解释器作为另一个进程启动，并放在自己的一个作业里，那个作业里的进程放不进与它并列的另一个作业。测试要把一串程序中的某一个放进被测的作业，所以那一串程序用解释器本身启动，不经启动器。

**6. 没读过的结果起初按字符数裁，中文裁不动。** 第 7 处的第一版沿用了裁旧结果的三个数：超过 8192 个字符的结果，裁到开头 4096 加结尾 1024 个字符。只读的复查指出这在小窗口上不成立，对照代码量了一遍。按这个程序对 token 的估算，英文一个字符约 0.23 个 token，中文约 0.62 个，不带空格的一长串字母数字约 0.85 个。窗口 16,384 的模型，单个结果的上限是 4096 token，一段中文到这个上限时只有 6600 个字符，够不上 8192。一次回复要来四个这样的结果，合起来就是整个窗口，一个也裁不动，前面又没有可以写成摘要的对话，压缩什么也做不了。改成按 token 算之后，同样的四个结果各裁到四成的四分之一，有一条测试就是这个情形。

**7. 上限是分摊的，不是从最大的开始挨个裁到底。** 第一版从最大的结果开始，每个都裁到同样的固定长度，直到合起来不超过。按 token 算之后没有固定长度可用，改成了分摊：算出一个上限，小的不动，大的都裁到这个上限。这样让出去的不多于必须让的。七千和一千五的两个结果合起来只超出五百时，大的那个只少五百，第一版会把它裁到只剩一千多。

**8. 裁掉的不到五百个字符就不裁。** 裁过的结果多出两行，一行说省略了多少，一行说整份在哪。裁掉的字符比这两行还少时，结果不会变短，说整份在哪的那一行也没有地方放。所以一个结果要么不动，要么至少少 512 个字符。被裁过一次的结果不再裁第二次：它中间那一行写着整份在哪，再裁就把这一行裁掉了。

**9. 替身引擎会丢掉晚启动的命令。** 上一批改动的正式变异检查停在一条测试上：未经改动的代码上，“引擎晚启动的命令照样被停下”这一条没有通过。出错的是测试里顶替 `docker` 的那个替身程序。它把一个容器里的命令记在一张清单里，“停止”先读清单，再把清单删掉，读和删之间登记的命令就丢了，之后的“停止”再也找不到它。真的容器里没有清单，“停止”按用户结束进程，下一次自然看得到后来启动的。替身改成每个命令一个文件，“停止”只删它看到的那几个。复现它的测试让两边互相等：“停止”看过之后才启动命令，命令登记之后“停止”才往下做，不靠睡眠碰时间。

**10. 上一个提交让一个变异体没人发现了。** 同一次正式检查在 Linux 上报告了一个漏检：把“引擎仍然列着的容器”当成已经消失。上一个提交把“容器从未建成”收窄成程序明说没有建成的两种情形，原来发现这个变异体的那条测试用的是另一种失败，从此不再走到那一行。那条测试补了一种情形，手工放进这个变异体，它失败。平时只跑新增和改过的变异体，改动让旧变异体失效的情况要靠正式的全量检查才看得到。

**11. 程序自己出错的代码叫 `EXCEPTION`。** 回合以 `error` 结束时，代码原样带着请求失败的代码。模型那一层已经把自己这一侧的故障叫 `INTERNAL`，程序自己的异常要是也用这个词，两者就分不开了。

**12. 桌面应用原先靠句子给回合的结束分类。** 它把回合预算和钩子的句子逐字记在代码里。现在有代码时按代码分，句子只用来取代码说不了的两样：步数的上限是多少，钩子给的理由是什么。句子将来换了说法，丢的只是那个数，界面说“用完了步数的上限”而不带数字。没有代码的旧日志照旧按句子读：仓库里录下来的两份真实会话就是这样的日志，测试一直在回放它们。

**13. 指南里那一行输出是手改的。** 指南里 `--json` 的示例是一次真实运行的输出，那次运行在这个字段出现之前。示例的最后一行补上了 `"code": null`，与现在的输出一致，别的行没有动。

**14. 不是文字的拒绝会让 Agent 停摆。** 只读的复查指出，监听者拒绝一步时给的代码如果不是文字，回合结束的记录就写不出来，而写它的地方在处理监听者出错的那段代码之后：这个回合没有结束记录，Agent 从此不再工作。对照代码看，拒绝的理由本来就有这个问题，代码只是多了一条路。现在循环接过一个拒绝时先看这两样是不是文字，不是就按监听者出错处理，回合以 `error` 结束，下一个回合照常进行。

**15. 示例日志里没有带代码的回合。** 协议文档里的示例会话有四个回合，结束方式是完成和被用户停下，都不带代码，所以示例里这个字段都是空的。各个代码的取值写在协议文档里。没有为此给示例加一个回合：桌面应用的测试回放这份示例，逐条核对里面的内容。
