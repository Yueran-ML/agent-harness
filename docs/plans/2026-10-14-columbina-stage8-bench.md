# Columbina 第 8 阶段实施计划：基准与本地模型

**Goal:** 用能自动判分的任务量出 Columbina 做得怎样，交出设计文档第 14 节的三张表：验收基准的成功率，部件开与关的对比，本地模型各量化档的支持矩阵；另附性能与成本。

**Architecture:** 基准是仓库里的一个目录 `bench/`，不进发行包。一个任务是一个目录：给模型的话、初始的工作区、判分的办法、一份参考解。跑分器为每次尝试新建一个临时工作区，用 `columbina run --json` 在子进程里跑完这一件任务，命令在容器沙箱里执行，再按任务的办法判分，结果一行一行追加到结果文件。要额外工具的两类任务（查数据库、查数值）各有一个插件，经 `--patch` 加进组合清单。部件的开与关也是补丁。表从结果文件生成。

**Tech Stack:** 不加运行时依赖。判分用标准库：代码任务的隐藏测试用 `unittest`，在容器里跑；数据库用 `sqlite3`。本地模型用一个单独的 Ollama 实例，模型目录是已有的 `D:\ollama-models`。

设计依据是设计文档第 14 节和第 15.2 节。阶段 8 原本排在视频之后，2026-10-14 作者让先完成第 8 到 10 阶段。

## 结束标志

1. `uv run python -m bench check` 对每个任务核对两件事：初始状态判为失败，套上参考解判为通过。它是测试的一部分，不调用模型。
2. 三张表，各由一条命令从结果文件生成，写进 `docs/bench/`：
   - 验收基准：四类任务在 DeepSeek 两个模型上的成功率，带 95% 置信区间，每个任务重复 3 次。
   - 部件开关：压缩、待办、溢出预览、行为守则几项各自关掉时，成功率和 token 的变化。
   - 本地模型矩阵：Qwen2.5 和 Llama 的各量化档在同一套任务上的成功率，标出可用的档位。
3. 每次尝试留下完整的记录：会话日志、`--json` 的输出、判分的输出、用掉的 token。表里的每个数都能追到这些记录。

## 需要作者决定的事

下面几件有缺省，计划按缺省写。

| 事情 | 缺省 | 另一种做法 |
|---|---|---|
| 命令在哪里执行 | 容器沙箱（`--sandbox docker`），没有网络 | 本机加 `--permission full-access`。快，但本地小模型可能在本机上乱删东西 |
| DeepSeek 的两个模型 | `deepseek-flash` 跑全部的表，`deepseek-v4-pro` 只跑验收基准 | 两个都跑全部。部件表的花费翻倍 |
| 花费 | 先用 3 个任务试跑，量出每次尝试的 token，按单价估出全部的花费写进记录；估计在人民币 100 元以内就照计划跑 | 每一轮都先停下来等作者确认 |
| 本地模型的上下文 | 16K，Ollama 的 `OLLAMA_CONTEXT_LENGTH` | 32K。8B 的 Q8 档放不进 12 GB 显存 |

## 范围

做的：任务格式与校验，四类任务，两个工具插件，跑分器（并发、续跑、超时、记录），判分，统计与出表，单独的 Ollama 实例的启停，性能的几项测量。

不做的：设计文档提到的“工具调用修复”和“重复调用提醒”两个部件还不存在，部件表里没有它们，等表出来再决定要不要做。多机并行。云端的其他模型。

## 约定

与第 7 阶段相同：在 `_review/s5b` 里做，闸门通过之后快进本地 `main`，不推送。提交信息用英文，不加共同作者行。跑分的结果文件和记录留在仓库之外（`_review/bench_runs/`），仓库里只放出表的脚本和生成的表。同一时间只跑一项重任务：本地模型的一轮跑分独占显卡；DeepSeek 的跑分不占本机，可以和别的工作同时进行，但不和闸门同时跑，因为两者都起容器。密钥只经环境或系统钥匙串交给子进程，任何记录里都不出现。

## 设计决定

### 任务

**1. 一个任务是一个目录。** `task.yml` 写明编号、类别、给模型的话、时限、最多几步、要加的补丁、判分的办法。`workspace/` 是初始的工作区。`reference/` 是参考解：套上它的办法随类别而定。`checks/` 是判分用的东西，模型看不到。

**2. 生成的任务也落成目录。** 数据库和多步计算两类由生成器按种子生成，生成器把目录写进 `bench/tasks/`，一并提交，所以任务的内容看得见、可以比对，生成器只在要换题时再跑。

**3. 校验是测试的一部分。** `bench check` 把每个任务放进临时目录，先判一次，必须是失败；再套上参考解判一次，必须是通过。这条在闸门里跑，不调用模型，不起容器：代码任务的隐藏测试在校验时直接用本机的 Python 跑，它们只是 `unittest`。

### 四类任务

**4. 代码修改，约 15 个。** 每个是一个小 Python 仓库，问题描述里给出现象，`workspace/tests/` 里有一个看得见的失败测试，`checks/` 里有隐藏测试。判分：把隐藏测试放进容器，`python -m unittest`。参考解是改好的文件，覆盖到工作区上。难度分三档：改一行、改一个函数、跨两个文件。

**5. 文件与命令行操作，约 12 个。** 整理目录、改配置、合并文件、按规则改名。判分：比对最后的文件树和内容，规则写在 `checks/expected.json` 里，有的比对精确内容，有的只比对结构（例如 JSON 里某个键的值）。参考解是最后的文件树。

**6. 数据库查询，约 15 个。** 生成器按种子建一个 SQLite 库和一个扰动过的副本（同样的表，不同的行）。问题用自然语言。插件给三个工具：看表结构、只读查询、提交答案的 SQL。判分：提交的 SQL 在原库和扰动库上的结果集，都要和参考 SQL 的结果集相同；只在原库上对，说明是照抄了数值。查询以只读方式打开，另加授权回调，只许读。

**7. 多步工具计算，可大量生成。** 取 ReliQuant 的出题程序（作者自己的项目，`experiments/v2/gen_bank_v2.py`）的做法：工厂、商店、物流三种场景，三到六步的整数运算，每一步都除得尽。题面里的数值换成名字，模型要用插件的 `lookup` 工具一个一个查出来，最后用 `submit_answer` 交答案。判分：答案等于程序算出的值，并且每个数值都查过。先生成 30 个。

### 跑分器

**8. 一次尝试一个子进程。** `columbina run --json --profile headless --patch … --cwd <临时工作区> --provider … --model … --sandbox docker "<给模型的话>"`。子进程有自己的 `COLUMBINA_HOME`（临时目录），所以会话日志、存盘和设置互不干扰。时限到了整棵进程树被结束，记为超时。

**9. 结果是一行一条的 JSON。** 每次尝试记：任务、模型、部件的开关、第几次重复、是否通过、判分的输出、结束的原因和代码、调用次数、四种 token、用时、记录的路径。跑分器启动时读已有的结果，已经做完的尝试跳过，所以中断之后可以接着跑。

**10. 并发。** 云端模型同时跑 4 个尝试；本地模型一次一个，因为显卡只有一块。

**11. 判分在容器里。** 代码任务的隐藏测试是模型写的代码在跑，所以和模型的命令一样放进容器：`docker run --rm --network none`，工作区和隐藏测试各挂一份，测试是只读的。文件、数据库和计算三类的判分只读文件或者跑我们自己的 SQL，在本机做。

### 模型

**12. DeepSeek。** `deepseek-flash` 跑三张表，`deepseek-v4-pro` 跑验收基准（服务列出的两个模型就是这两个）。思考模式照服务的缺省，每次请求的完整配置随会话日志留下（设计文档第 16 节的未决事项）。

**13. 本地模型用单独的 Ollama 实例。** `OLLAMA_MODELS=D:\ollama-models`，`OLLAMA_HOST=127.0.0.1:11435`，`OLLAMA_CONTEXT_LENGTH=16384`，由跑分器启动和关闭，不碰作者平时用的那个实例和它的设置。Columbina 经一个只在基准的 `COLUMBINA_HOME` 里登记的服务连它。矩阵的行：Qwen2.5-7B 的 Q3_K_M、Q4_K_M、Q8_0，Qwen2.5-3B 的 Q2_K 到 Q8_0 和 FP16，Llama-3.1-8B 的 Q3_K_L、Q4_K_M、Q8_0，Llama-3.2-3B 的同一组档位。这些模型那个目录里都已经有了，不用再下载。先用 Qwen2.5-7B 试跑，把任务的难度调到能分出高下（设计文档第 16 节）。

### 统计与出表

**14. 成功率带 Wilson 95% 置信区间。** 部件表里，开与关的差也给区间，用两个比例之差的近似。token 取中位数和总数，缓存命中率是读缓存的 token 除以输入 token。

**15. 表是生成的。** `python -m bench table <结果文件>… --out docs/bench/<表>.md`。表下面写清楚：哪天跑的、哪个提交、多少次尝试、花了多少 token。

### 性能

**16. 设计文档第 14.4 节的三项。** 冷启动（`columbina run --dump-config` 和用脚本化模型跑完一件小事各自的用时）、一千步合成会话的恢复与折叠用时、内存峰值。输入全由常量合成。测量写成测试，给出宽松的预算，放进持续集成，只在超出预算很多时失败。

## 任务

1. **任务格式、加载与校验。** `bench/task.py`、`bench/check.py`、`tests/bench/`。测试：读一个任务目录；缺字段、类别不认得、补丁不在时说清楚；校验对一个好的任务通过，对“初始状态就通过”和“参考解也不通过”的任务各说出是哪一种。
2. **判分。** `bench/grade.py`：代码（容器里的 unittest，校验时用本机）、文件树、数据库、计算。各有测试。
3. **两个插件。** `bench/plugins/sqlite.py`、`bench/plugins/lookup.py` 和对应的补丁。测试：只读、拒绝写和附加别的库、结果的行数上限、查到的数值、提交答案。
4. **生成器。** 数据库和多步计算两类，按种子，结果逐字节可重现。
5. **手写的两类任务。** 代码修改 15 个、文件操作 12 个。题目和参考解可以分给子代理写，我逐个核对并跑校验。
6. **跑分器。** `bench/run.py`：子进程、超时、并发、续跑、记录。用脚本化模型的端到端测试。
7. **Ollama 实例的启停。** `bench/ollama.py`。
8. **统计和出表。** `bench/table.py`。
9. **试跑与估价。** 3 个任务在 `deepseek-flash` 上各跑一次，记下 token 和用时，估出全部的花费。
10. **验收基准、部件表、本地矩阵各跑一轮。** 结果和记录留在仓库外，表提交进 `docs/bench/`。
11. **性能测量。**
12. **文档。** 指南的三种语言加一节“基准”，README 的阶段表更新，设计文档第 14 节按实际写法改。
