# Columbina 工程报告

[English](report.md) · **简体中文**

Columbina 是一个用 Python 从零写成的 agent harness：它让语言模型作为 agent 在一个目录里读文件、搜索、改文件、执行命令，每一次调用在执行之前都要经过判定。项目分十个阶段完成。这份报告讲它怎样组成、哪些选择决定了它的样子以及各自的代价、它怎样测试，以及用 72 道能自己判分的任务量出来它做得怎样。

简要地说：验收基准上 `deepseek-flash` 通过了全部 216 次尝试，`deepseek-v4-pro` 通过了 214 次；Columbina 组合出程序不到一秒，恢复一个一千步的会话只要五分之一秒；9,700 多条测试覆盖每一行、每一个分支，另有 3,600 多个手写的变异体检验测试能否发现缺陷。

## 1. 由插件组成的内核

Columbina 的每个部件都是一个小型 asyncio 内核上的插件：模型适配器、工具、会话日志、agent 循环、终端都是。内核本身对 agent 一无所知，它只提供四样东西。

- **服务**。插件用 `provide` 提供服务，用 `use` 读取服务。它在 `inject` 里列出需要的服务，这些服务到齐时加载，其中一个撤走时卸载，回来时再加载。
- **效果**。插件经由它的上下文注册的任何东西，监听器、工具、服务，都会在插件卸载时按相反的顺序撤销。插件不用自己收尾，所以也不会忘了收尾。
- **事件**，有五种分发方式：同时交给所有监听器、并发执行、一个接一个、问到有一个应答为止、依次经过所有监听器组成一条链。一次工具调用前的检查就是这样一条链，一步是否开始的决定也是。
- **组合**。一个程序就是一份清单，即用 YAML 写的插件条目列表。清单可以扩展另一份清单，后面的层按 id 修改条目。无人值守地跑一个任务的程序，就是基础清单再加一个条目；测试和基准用几行补丁改造程序。

代价是间接。想知道一次工具调用经历了什么，要顺着事件穿过好几个插件，监听器的顺序也有影响。有两点让它可以接受。一是调用前的检查只能拒绝，别的检查拒绝了的，它不能放行，所以守卫的顺序不决定什么被允许。二是组合出来的程序随时可以打印出来（`columbina run --dump-config`），加载了哪些插件从来不用猜。

## 2. 会话日志是唯一的事实来源

一个会话是一个只追加的事件文件。发给模型的任何内容都先写进日志，每个请求都从日志推导出来。由此得到三点。

- 程序在会话中途死掉之后，会话可以接着进行：读入日志，把被打断的回合收尾，使每次工具调用都有结果，再从已有的内容发出下一个请求。
- 会话可以从它的任意一个回合复制，副本和原会话除了过去之外不共享任何东西。
- 压缩对话不丢任何东西。摘要或截短的结果只在发给模型的视图里取代较早的消息，事件本身仍然留着，凡是显示会话的地方都能显示它的全部。

代价是状态从来不能直接修改。待办清单、回合进行中收到的消息、token 计数，都是从事件折叠出来的投影。新的一种状态需要新的事件和折叠函数，而且从头重读日志时折叠必须给出同样的结果。测试会让恢复的会话从第一个事件起重新折叠，并只凭事件重建发给模型的内容。

## 3. 循环与一次调用的管线

Agent 按回合工作，一个回合由若干步组成：一步是一次模型请求，再加上回复里要求的工具调用。输入有三种进来的方式：作为任务，作为插话送进正在运行的回合，或者作为下一个回合的上下文。四个拦截点让插件决定一步是否开始、请求怎样构造、失败之后怎么办，以及即将结束的回合是否继续。回合的预算（步数、token 和时间）是这样的一个插件，长对话的压缩也是。

一次调用要经过一条管线：参数按工具的结构校验，询问守卫，规则要求时询问用户，工具在一层包装里执行，结果在模型读到之前再检查一次。不管出什么问题，都会变成一个带稳定错误码的结果交给模型。每次调用恰好得到一个结果，回合在调用中途被取消时也一样，所以日志里不会有没有回应的调用。

模型只通过 OpenAI Chat Completions 协议接入。一个适配器对接六个按名字认得的服务（DeepSeek 是其中之一）、本机上的 Ollama 和 LM Studio，以及按地址添加的任何其他服务。适配器只负责把流变成同一套词汇的分片；每次调用恰好以一个结束分片收尾、每种失败都有错误码，这些由它外面的一层保证。重试是一个插件。

## 4. 一道文件接缝和一个命令容器

有六个工具触及本机：读、写、编辑、查找、搜索和执行命令。其中五个碰文件的工具都经过同一道接缝。工具请接缝定位一个路径、对这次访问作出判定，拿到一张许可；之后文件经由许可在判定过的位置上打开或替换。判定和访问之间，途中某个目录被换成了链接，访问也不会因此挪到别处。接缝还记得模型看过哪些文件、看到时是什么状态，只有模型看到的就是文件现在的样子时，才允许替换它：模型没读过的内容，它会盲目地覆盖掉。

接缝上的限制只能拒绝，任何放宽默认设置的东西都不能推翻一条限制。权限就是这样一条限制，同时也是工具管线上一个别的插件都绕不过的守卫。三个预设决定默认允许什么，项目和用户的规则在此之上增补。

命令在沙箱里执行。一个提供者让命令在本机上执行。另一个为每个会话保留一个 Docker 容器：只挂载工作目录，本机的其他东西一概没有，除非配置给了网络否则没有网络，不带任何 capability，进程数有上限。容器的寿命恰好等于启动它的那个进程的输入流，所以 harness 被杀掉时会带走它的容器，不需要事后按记录清理。容器完全约束住的命令不再询问，只约束住一部分的命令仍要询问。

## 5. 选择与代价

| 选择 | 换来什么 | 代价 |
|---|---|---|
| 一切都是插件 | 任何部件都能用一行 YAML 去掉、替换或关掉，基准就是这样关掉部件的 | 间接，监听器的顺序要想清楚 |
| 日志是唯一的事实来源 | 会话能挺过崩溃，能复制、重放，能完整地显示 | 每种新状态都要一个事件和一个折叠函数 |
| 所有模型一个协议 | 一个适配器，测一次，对接八个按名字认得的服务和任何其他服务 | 服务在协议之外提供的能力用不上 |
| 文件只走一道接缝 | 一处判定，碰到的正是判定过的那个文件 | 每个碰文件的工具都得经过它，示例也不例外 |
| 每个会话一个容器 | 不依赖各个系统自己的沙箱也能约束命令 | 需要 Docker；没有时命令在本机执行，并且要询问 |
| 测试驱动真实的管线 | 缺陷在用户会看到的地方暴露出来 | 测试套件很大，跑一遍要几分钟 |

有些东西是有意不做的：各个操作系统自带的沙箱、常驻的 agent、工作流，以及在请求之外把会话发给服务方的任何做法。

## 6. 怎样测试

测试套件有 9,700 多条测试，覆盖程序和基准的每一行、每一个分支，覆盖率 100%，每次改动都要保持。除了单元测试，还有这几类：

- **循环测试**用脚本化的模型（按列表作答）驱动真实的管线和真实的会话文件。
- **性质测试**给 agent 随机的任务、插话和取消，检查日志里留下了什么。
- **回放测试**重放真实模型录下来的运行，工具真的执行，逐个事件比对日志。
- **屏幕测试**在模拟的终端上运行终端界面，读出屏幕上显示的内容。
- **引擎测试**启动真实的容器，检查容器里的命令够得到什么、结束后留下了什么。

覆盖率只说明一行代码运行过，不说明它做错时有测试能发现。所以又手写了 3,600 多个变异体，也就是小缺陷，逐个放进代码，每一个都必须有测试失败；没有被发现的变异体，意味着缺了一条测试。类型由 pyright 以严格模式检查，Windows 和 Linux 各查一遍。持续集成在 Windows、Linux 和 macOS 上用 Python 3.11 和 3.12 跑上面的全部检查，Linux 上需要真实 Docker 引擎的测试必须运行，不能跳过。

## 7. 基准

### 7.1 能自己判分的任务

基准有 72 道任务，分四类。每道任务有起始的工作目录、正确答案的样子，以及模型看不到的判分办法。

| 类别 | 任务数 | 要做什么 | 怎样判分 |
|---|---|---|---|
| code | 15 | 一个小 Python 项目有缺陷，有一条测试能看出来。不改测试，把它修好 | 隐藏的测试，在没有网络的容器里运行 |
| files | 12 | 整理、改名、合并、改配置、拆分、生成索引 | 对留下的文件树的规则 |
| sql | 15 | 关于一家商店的数据库的问题，只能经三个工具访问数据库 | 提交的查询在原库和一份行不同的副本上都要运行，两处都要答对 |
| compute | 30 | 三到六步的计算，每个数都藏在工具后面 | 答案，以及每个数是否都查过 |

有两类任务的设计让模型无法靠猜通过。把数据库里的数值直接写进查询的 SQL，在行不同的副本上会出错。计算题只在方括号里写出数值的名字，每个数都查过，答案才算数。随测试一起运行的校验对每道任务确认两件事：起始状态判为失败，参考解判为通过。

### 7.2 一次尝试

一次尝试在单独的进程里运行 `columbina run`，用工作目录的一份新副本，并有自己的 home。它只拿到任务给它的东西，本机的东西一样也带不进来：用户的技能和代理不进来，设置 Columbina 的环境变量也不进来；运行目录必须在任何仓库之外，否则每次尝试都会读到那个仓库的说明文件。模型的命令在容器里执行。每次尝试一判完分就写下一行结果，所以中断的运行再运行一次就会接着做。

成功率附带 95% 的 Wilson 置信区间，部件的差值附带 Newcombe 区间；测试让这两种区间都与 Newcombe 发表的算例一致。

### 7.3 结果

**验收基准**。每个任务用 DeepSeek 的两个模型各跑三次，程序的部件全部打开。成功率附带 Wilson 区间；带各行 token 数的完整表格在 [`docs/bench`](bench/README.md)。

| 模型 | code | files | sql | compute | 全部 |
|---|---|---|---|---|---|
| `deepseek-flash` | 45/45 | 36/36 | 45/45 | 90/90 | 216/216 = 100% [98%, 100%] |
| `deepseek-v4-pro` | 43/45 | 36/36 | 45/45 | 90/90 | 214/216 = 99% [97%, 100%] |

`deepseek-flash` 每次都通过了。`deepseek-v4-pro` 的两次失败在同一道题上，它的修改把英文以外的字母都当成了分词的界线。按照设计，这是每次发布的底线：发布前在 `deepseek-flash` 上跑一遍，成功率不得低于上一版。

**程序的各部分**。用 `deepseek-flash` 把四个部件逐个关掉，并告诉程序模型的窗口是 16,384 token，即本地模型的窗口：

| 关掉的部件 | 通过 | 一次尝试的输入 token（中位数） |
|---|---|---|
| 无 | 215/216 | 16,837 |
| 压缩 | 216/216 | 16,909 |
| 待办清单 | 216/216 | 15,582 |
| 结果大小上限 | 216/216 | 16,867 |
| 行为守则 | 216/216 | 11,382 |

在这些任务上，关掉哪个部件都不影响模型是否成功，而每个部件的代价都看得出来。行为守则约占一次尝试输入的三分之一，待办清单约占 7%，其中大部分读自服务方的缓存，价格是五十分之一。压缩一次也没有触发，结果只在 1,080 次尝试中的一次里被截短过：这些任务的对话都不长，让对话保持短小的两个部件没事可做，也就不花代价。四个部件都保持默认开启。行为守则防的是这些任务里没有的情形，比如不可撤回的操作和文件里夹带的指令，这类任务是下一批要加的。

### 7.4 花费与速度

三次运行共 1,512 次尝试，按 DeepSeek 的低峰价格花了 1.67 美元。`deepseek-flash` 一次尝试的输入中位数约一万七千 token，其中 94% 读自缓存，输出约六百 token，花费不到十分之一美分。

Columbina 本身很快。在作者的机器上，组合出程序用 0.96 秒，用脚本化模型跑完一件小事用 1.14 秒；一个一千步、磁盘上 3.9 MB 的会话恢复只要 0.18 秒，内存峰值 21 MB，汇总它的 token 用 9 毫秒。测试在持续集成里用宽松的预算守着这些数字。

## 8. 下一步

- **本地模型的表**。Qwen2.5 和 Llama 的各量化档，在 20 道任务上跑，窗口是 16,384 token，让对话保持短小的部件在这个窗口下才派得上用场。这些运行要独占显卡。
- **检验行为守则的任务**：不可撤回的操作，agent 读到的文件里夹带的指令。
- **`columbina doctor`**，按设计检查一台机器：密钥、模型能否应答、shell、容器。
- **桌面应用**，以及它的可用性调查。
- **PyPI**。构建、试装并发布发行包的工作流已经就绪，推一个标签就会运行。
